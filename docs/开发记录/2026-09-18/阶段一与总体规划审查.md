## 四、规划对“聪明、快、记得住”的影响

### 1. 优先调整：真实语音闭环验证偏晚

总计划 Phase 4 明确不接 TTS，Phase 6 先做长期记忆，Phase 7 才正式测首音频，Phase 9 才完整观测。对于以实时陪伴为首要目标的产品，这个顺序的风险偏高。

建议保留阶段编号，只增加 Phase 4B 的最小纵向验证：已验证输入 → 一次 LLM → 增量可播片段 → TTS → 已确认输出通道 → 起播/取消观察。不提前实现完整动作或嘴型，不绕过同房间设备寻址待确认项。完整 TTS/动作/嘴型仍在原阶段完善。

最小 typed trace 从 Phase 2 随链路增长；Phase 9 完成展示，不到 Phase 9 才补原始时间点。

历史基线只有 4 个成功回合：首 PCM 发布 P50=2339.8ms、P95=3332.26ms，TTS session sleep 约 1801–1877ms；采样混有 Web/robot 输入，且没有扬声器起播。它提示优先调查人为等待及分句/建链，而非优先削减几个 Graph 节点。不应把各指标机械相加或承诺删除等待后首响恰好减少 1.8 秒。

### 2. “聪明”主要取决于上下文和输出质量，而非增加 Agent 数

当前一次主模型调用、先短期上下文再长期记忆的方向正确。建议进一步明确：

- 当轮原始输入、明确改口和最新有效事实优先于旧摘要、旧记忆及模型猜测。
- SocialState 是可纠正的回复策略提示；允许 unknown，记录来源/更新回合，设重置或衰减规则。用户说“我不是难过”应立即覆盖旧状态，别做关键词情绪状态机。
- 控制的是无效追问，不是所有追问；关键信息不足时的一句澄清往往比盲答更聪明。
- Kernel/Persona/历史/记忆/WorldState 各有 token 预算和裁剪优先级；0–4 条记忆还需长度上限。
- 同一次流式模型输出里，SpeechDelta 不应等待完整动作 JSON/StateDelta 才放行；元数据解析失败不应阻塞已有效的文本输出。
- 普通闲聊默认 Fast；明确复杂任务保留最小显式深度入口，自动路由优化继续后置。避免“少调用模型”被实施成“所有问题都只能浅答”。

质量验证建议从现有 11 类样例扩充为可重复多轮脚本：正常表达、反例、否定、改口、插话、拒绝建议、长对话、跨会话及机器人自己的承诺。固定模型版本/参数、Persona、历史和记忆快照，保留模型原答和匿名 A/B 评分。先积累小而有效的数据集，不急于再造评测平台。

### 3. 记忆选型可行，但“后台写入”不等于“主链无等待”

LangMem 后台抽取、Store 前台查询的分工合理；官方也提供延迟/去抖的后台记忆处理方式。见 [LangMem 官方指南](https://langchain-ai.github.io/langmem/guides/delayed_processing/)。

以下是项目设计需要补齐的内容，而不是已发生的 V2 故障：

1. **检索预算**：结构化键查询优先；语义查询可能涉及 query embedding，rerank 也可能涉及额外计算/网络。分别定义预算、触发条件和截止时间；普通陪伴超时可以无记忆继续，明确依赖记忆的问题应表达不确定，而不是编造。
2. **更正/遗忘一致性**：旧后台任务晚完成，不应把已改口或已删除的事实写回来。用 source_turn/version、可验证的覆盖次序和删除标记解决；别为此引入新消息中间件。
3. **同轮可见性**：上一轮刚说完的信息通过近期 Ledger/Working State 立刻可读，不等待后台 LangMem 完成。
4. **事实来源**：区分用户明确事实、模型推断、机器人虚构表达；标注时间/来源，避免把助手自己说的话抽成用户经历。
5. **用户身份**：已有 ASR 形状没有证明可靠的 user_id 映射。设备/连接来源不等于人；Phase 2/3 应确定绑定与匿名模式，再写个人长期记忆。
6. **人格隔离歧义**：总计划的 episodes namespace 没有 persona_id。需明确它仅容纳人格无关公共经历，还是改成按 Persona 隔离；Persona 专属故事不应经 episodes 绕过隔离。
7. **后台资源竞争**：后台抽取仍消耗模型额度、CPU、SQLite 和 embedding 资源。合并相邻候选、限制并发/重试、优先服务前台，统计后台积压和前台等待。

LangGraph 的官方 `AsyncSqliteStore` 实现已经存在，并非选了不存在的组件；但项目尚未安装接入，仍应在 Phase 6 前完成目标版本、Python 3.11、macOS/Windows 的小规模安装/CRUD/向量查询/删除一致性验证。见 [官方源码](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-sqlite/langgraph/store/sqlite/aio.py)。

特别注意版本选择：官方公告指出 `langgraph-checkpoint-sqlite <3.1.1` 的 namespace 前缀匹配可能跨边界，3.1.1 修复。接入时选包含该修复的兼容版本，并测试 `user1/user12`、大小写及特殊字符边界；**当前 Phase 1 未使用该包，不属于现存运行漏洞**。见 [官方公告](https://github.com/langchain-ai/langgraph/security/advisories/GHSA-47pj-3jcm-6whg)。

### 4. 实际已播事实和取消语义必须提前落定

总计划 Phase 3 要求 cancel 后 spoken_text 正确，但真实 TTS 在 Phase 7，Phase 0 又明确缺设备播放证据。这应拆成两级验收：Phase 3 做状态/回执模拟契约；真实接入后做设备端验收。

- 严格区分 planned、generated、published、acknowledged played；发到 Room 不等于用户听见。
- 没有播放证据时使用 unknown/估计标记，不把完整发布文本伪装成 spoken_text。
- 小脑 cancel 必须匹配当前 robot/turn/generation；排队的旧 TTS、嘴型、动作和迟到 StateDelta 在输出或提交前再次核验 generation。
- 本地取消任务与设备真实停播分别测量。已有 <30ms 指标只到 local cancel，不覆盖设备缓冲区。
- 不做完整全双工仍然需要处理 ASR 文本到达后的取消/改口；阶段一 FIFO 不应直接成为最终会话策略。后续定义新输入是排队、合并、替换还是打断，并规定过期丢弃。

### 5. Checkpoint、Ledger 和观测不应混成同一种“异步落库”

总计划正确地把 Ledger 视为真实事实，把 checkpoint 视为工作状态；还要说明下一轮读到哪个版本，以及重启如何处理半完成回合。

目前 Recorder 是可丢弃观测：队列满会丢，写失败后 task_done，后续成功会清除 last_error。它可以用于诊断 Trace，但不应直接复用来写必需会话事实或用户删除请求。为观测补累计失败/丢失计数与有界关闭策略即可，不必现在实现整个持久化平台。

LangGraph 持久化可选 sync/async/exit，分别在下一步前、下一步并行、退出时保存；所以“使用 AsyncSqliteSaver”本身不证明只有末尾一次磁盘工作。Phase 3/4 按恢复要求选模式并测总成本，不盲目关闭持久化换速度。见 [官方 Durability 定义](https://reference.langchain.com/python/langgraph/types/Durability)。

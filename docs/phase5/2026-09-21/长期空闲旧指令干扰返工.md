# Phase 5｜一小时后“喜欢喝茶”仍回复“退下”的交互返工

## 现象和归属

用户在一小时前说“退下吧”，本轮说“我喜欢喝茶”，模型却以“这就退下”开头。截图能确认旧指令干扰，但不能仅据截图确认是否存在旧 response 音频残留。需同时查本轮 ASR item / response ID / Room 播放队列及模型生成文字。

## 本次代码处理

1. 单主模型 Prompt 明确一次性的“退下/安静/暂停说话”当轮执行即结束，新发言应回应新话题；不把持续偏好或本来应保持的 Chat 历史一起抹掉。
2. Realtime 在连续 15 分钟没有业务交互且无活跃听、答、播时，下一次接收超时检查安全重建 Provider Session（不改变 Chat/Persona/Robot），从 SQLite 当前会话已确认历史按原 8 轮/3000 字符限额注入。一个空闲周期只主动重建一次；新用户轮次才重新计时，不制造每 15 分钟一次的反复重连。正常网络中断继续走原指数退避。
3. 有可靠 `created_ms` 的历史轮次，超过 15 分钟则把“约 N 分钟/小时前的历史发言，非当前指令”仅写入向模型注入的文本；SQLite 与界面原话不变。实际注入标记受 3000 字符预算约束；无可信时间戳不猜时间。诊断快照分别展示原话和 Provider 文本。
4. 本轮仍保持 Qwen Realtime 原生对话/Function Calling，外置 TTS、Room、ForcedAligner、20 轮本地历史和全量 SQLite 不改；不串联外置 LLM 或创建新记忆服务。

## 现场复测

- 新 Chat：说“退下吧”，完成后空闲 60 分钟，再说“我喜欢喝茶”。核对 `session.idle_recycle`、本轮 ASR final、response ID、`text.delta`、设备播出的文本是否一致。预期新轮正常承接喝茶，不重复退下。
- “安静”后一分钟继续说话、长故事打断、误判 Hold/Resume、多机器人各自等待并重连；不能丢正在播放的 TTS，不能把旧 Chat 的历史注入新 Chat。
- 对话缓存真实时间、模型最终回应、端到端首响仍需现场记录；mock 回归不等于模型语义质量实测 PASS。

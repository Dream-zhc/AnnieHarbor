# 字级动作与嘴型同步协议

> **2026-10-22 起暂停使用 `action_prepare`。** 用户确认嵌入式只执行 `type=action_trigger`，坏笑等五个表情发 `action_prepare` 时设备不动（当天 `smirk` 停在 `published_unknown`，同期 `action_trigger` 都有 `device_finished` 回执）。现在带 `anchor_text` 的动作改发与普通动作完全相同的 `action_trigger`（`script_id/offset_ms=0/conversation_id/anchor_source`），时机是“回复里已经出现目标词”且“本轮第一帧 PCM 已发出”二者都满足时。下文 `phoneme_anchor_v1` 只是嵌入式将来支持按字执行时的预留合同；在那之前表情只能做到“随回复开口”，做不到落在具体某个字上。见 [对话动作、短句与嘴型同步](../开发记录/2026-10-22/对话动作短句与嘴型同步.md)。

当前版本：`phoneme_anchor_v1`（2026-10-09，预留）。同一机器人归属一个 Room；不更改 TTS、嘴型模型或音频播放速度。本仓库完成云端发包，不包含嵌入式消费实现；真实执行需设备联调。

## 1. 消息与职责

1. **主脑**：Realtime Function Calling 选择 `script_id`、`anchor_text`、可选 `anchor_occurrence`。五个夸张脚本 `surprise/smirk/proud/skeptical/shy` 必须提供准确的 `anchor_text`。
2. **主脑文本流**：收到真实回复 `response.text.delta` 后积累 Unicode 原文，确认目标词及第几次出现；立刻向对应 `reb_main` **仅发一次** `action_prepare`。工具调用早于目标词时只在 Runtime 内部暂存，**不发送无字索引的消息**；没有目标词时超时撤销。不等待 PCM、ForceAligner 或播放回执，不猜 `at_sample`。
3. **独立 ForcedAligner**：照旧从 `reb_tts` 获取 **同一份** TTS PCM + 原文，向 `reb_sam` 推送带 `char_index / stream_epoch / start_sample / end_sample` 的 `mouth_script`，不直接发布动作。对于 `speech_sample_v1` 的嘴型结果，算出后尽快发出，不按估计墙钟延后。
4. **嵌入式**：同时订阅 `reb_main`、`reb_sam` 和已使用的音频流。缓存 `action_prepare` 并按 `conversation_id + stream_epoch + anchor_char_index` 找到对应 `mouth_script`，以 **设备真实已播放采样游标** 在 `start_sample` 位置触发一次。既不按消息抵达时间，也不按主脑时间戳执行。

## 2. 唯一云端预约包

下面是协议示例，`context_before/context_after` 只能来自 **已经生成** 的真实文本，不允许填猜测后文：

```json
{
  "type": "action_prepare",
  "ts": 1791538723947,
  "data": {
    "script_id": "surprise",
    "conversation_id": "example-turn",
    "anchor_source": "robot_main_brain",
    "timing_mode": "phoneme_anchor_v1",
    "stream_epoch": 2,
    "anchor_text": "好家伙",
    "anchor_char_index": 0,
    "anchor_occurrence": 1,
    "context_before": "",
    "context_after": "，",
    "action_id": "example-call-id",
    "late_policy": "drop"
  }
}
```

- `anchor_char_index`：整个 **实际回复** 中目标词首字的 Unicode 码点索引，从 0 开始，标点和空格均计入；重复出现时按 `anchor_occurrence` 选择从左至右非重叠的第 N 次。
- `context_before/context_after`：首字前最多 6 个码点、目标词末字后最多 6 个 **已生成** 码点；仅供诊断和接收端辅助验证，不能代替字索引或驱动时钟。流开头/后文尚未到达时可为空。
- `conversation_id + stream_epoch`：与其音频及 `mouth_script` 一致；`action_id` 用于幂等，每轮一个动作，不得重复执行。不同 Room 的消息不能互相匹配。
- 不携带 `at_sample`：采样点必须来自设备订阅的、相同流中 `timing_source=qwen3_forced_aligner*` 的 `mouth_script.start_sample`，不得以字数、均分句长或云端发送时钟推算。
- 新包不带无意义的旧 `offset_ms`。`late_policy=drop` 由最终接收端执行。
- `ts` 为服务器建包时间，不是声学目标时刻，也不能代替设备的播放游标。

**兼容性边界：** 未提供 `anchor_text` 的普通脚本仍沿用旧 `action_trigger`（首 PCM）；有字锚点的脚本只使用新 `action_prepare`，不会额外发送旧 `action_trigger`。旧设备如不理解新消息，应忽略它，**不能**将其视为立即运动指令。

## 3. 嵌入式调度合同

1. 收到 `action_prepare`，校验 `script_id` 白名单、Room、`conversation_id`、`stream_epoch`、非负整数 `anchor_char_index`、`action_id`。允许先于音频或 `mouth_script` 到达；有界缓存，超时淘汰。
2. 收到 `mouth_script`，确认 `timing_mode=speech_sample_v1`、相同 `conversation_id + stream_epoch`、`char_index=anchor_char_index`、`char=anchor_text` 的首码点、`sample_rate=24000`、`start_sample < end_sample`。原有模型 `timing_source` 校验照旧；不使用旧无原文索引的嘴型。音素先到则可保留有界短期索引缓存，支持乱序。
3. 对齐后，以扬声器 **已播放** 的采样计数比较 `start_sample`。如果已经超过该值，丢弃动作并记录 `late`；如果尚未到达，按该游标预约。当本地播放回调跨过该采样点时恰好触发一次。同一个 `action_id` 的重传不会重复触发。
4. HOLD 时游标暂停、动作不触发；RESUME 时从原游标继续；STOP / 打断 / 换流 / epoch 变更立即清理所属未执行预约和索引缓存。已经启动的物理电机能否中止，另按设备能力处理。
5. 只接到动作、没有有效音素，或只接到音素、没有动作，都不能猜时点执行。旧动作保留旧行为，但不与新的 `action_prepare` 混执行。

## 4. 时序、证据与边界

- `action_prepare` 的云端发布完成就是云端下发成功，不等待嵌入式消费再让 LLM 回答；这**不代表动作在物理设备上完成**。
- 联调每轮至少关联：`action_prepare.ts` 与 Room 成功发布状态；`mouth_script` 实际产生/发布时刻与 `start_sample`；设备收到动作或音素时的 `played_sample_count` 和实际触发/丢弃事件。不同机器墙钟不直接作精确延迟比较；以同一个设备播放时钟判定是否赶上。
- **提前下发并不能消除声学算法的延迟。** 若第一字在 ForcedAligner 识别出它以前已经播放，设备必须丢弃。当前侧车日志曾观察首个嘴型比所标注的字起始时刻晚约 391ms；尚无可证明硬件在目标字之前收到两条消息的实测证据。
- 首字可能晚到、`anchor_text` 可能根本未生成、实时回复也可能在 TTS 开始后才调用动作工具；这几种情况均不人为延迟或重播语音，只能正确撤销或丢弃动作。若希望更高成功率，模型应在自然上下文下选择**较后的**目标词，但不能伪造它已经说过的字词。

## 5. 联调输入

```text
小安妮，说“哇，这也太厉害了”，在“厉”的声音出现时做 surprise。
小安妮，说“厉害，真的厉害”，在第二个“厉害”开始时做 surprise。
小安妮，动作准备后我突然打断，验证旧 epoch 的动作不得再执行。
让设备对音素/动作消息分别制造网络延迟，验证乱序缓存和 late_policy=drop。
```

设备端的接收调度逻辑、真实扬声器游标与电机回执不在本仓库，本协议只定义实现与验收条件。

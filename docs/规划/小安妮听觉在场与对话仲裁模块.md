# 小安妮「听觉在场与对话仲裁」独立模块规划

> 日期：2026-10-08
> 状态：**专项设计，未开工实施**。这是一个独立模块的一阶段规划，**不追加到既有 Phase 1–11 路线图，不重开已暂停的 Phase 10/11**。
> 范围：待机监听、唤醒、连续对话、指向性判断、多人旁听、误打断、安全发声准入。模型训练、正式部署属于本专项的后续里程碑，当前未实施。

## 1. 目标和用户可见效果

目标不是「不断听到声音就讲话」，而是做到 **始终具备声学在场感、恰当时候理解语言、在明确许可下参与交谈**。

1. 用户说「小安妮，今天想聊聊」能一次说完；不需要喊完名字等待第二次说话。
2. 唤醒后可多轮对话，回答播完后有短追问窗口，不每句话都重复唤醒；对话正在进行时不被固定秒数截断。
3. 机器人播放期间可以被真正的问题打断；「嗯、对」等附和不导致错误取消。
4. 别人与用户交谈，机器人保持安静；不因为某句像问句就擅自执行动作、天气工具或记忆写入。
5. 休眠时仍能知道「有人在说话、环境有活动」，但**无法仅凭唤醒模型知道说话的具体语义**；只有取得音频理解授权时才向云端提供语音。
6. 每机器人独立Room、会话、状态、回执、超时、记录；机器人A的唤醒、扬声器回执不能改变B的门控。
7. 工作台明确显示监听范围：仅声学检测 / 正在云端理解 / 正在回复，不能把“在线”显示成“已经理解了环境”。

## 2. 对同行方案的判断

- **Alexa**：平常先做唤醒判定；唤醒后才向云端发送音频，且可能附带唤醒词之前的短片段。Follow-Up允许免唤醒追问；Amazon明确承认它可能误收旁人讲话。官方：https://digprjsurvey.amazon.com/csad/help/node/201602230
- **Google Look and Talk / Quick Phrases**：在特定硬件、用户授权和目标用户匹配条件下，让注视或特定短语代替唤醒词。不是“任何旁人一说话都由助理回应”。官方：https://blog.google/products-and-platforms/products/assistant/assistant-io-2022/
- **LiveKit Agents**：区分VAD、语义轮次、有效打断、backchannel和误打断后续播；其自适应中断能力受到运行环境与实时模型控制方式约束，不能未经兼容测试直接插入当前Qwen链路。官方：https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling/
- **LiveKit Wakeword**：检测关键词而非ASR；约2秒16kHz PCM窗口的无状态推理由调用方缓冲。不能代替识别说话对象、意图和语言含义。官方：https://github.com/livekit/livekit-wakeword/blob/main/docs/export-and-inference.md
- **Qwen-Audio Realtime**：smart_turn提供语音开始、结束、无效轮、ASR增量/最终、ambient转写、response与工具调用事件。它**只对收到的PCM起作用**；ambient不是“谁在对小安妮说话”的权威凭据，smart_turn有效轮也不是用户授权。官方：https://help.aliyun.com/zh/model-studio/qwen-audio-realtime-server-events 、https://help.aliyun.com/zh/model-studio/fun-audiochat-client-events

## 3. 最关键的架构选择：待机不等于云端一直听懂

### 3.1 三种独立运行模式

| 模式 | 房间PCM去向 | 会知道什么 | 谁能让机器人讲话 | 默认 |
| --- | --- | --- | --- | --- |
| **A 标准陪伴待机** | Room→内存环形缓存→KWS（可加VAD）；**不发送休眠PCM到Qwen** | 有声音/有人说话/唤醒词命中；不知普通闲聊内容 | 小安妮唤醒、有效FOLLOWUP、显式触发的可信设备/视觉事件 | **默认** |
| **B 延长连续交谈** | 已唤醒且开放会话内，PCM→Qwen smart_turn | ASR、轮次、附和、实时问题和语音情绪线索 | Runtime仲裁后的本轮/下一轮；超时、明确结束即回A | **唤醒后短时自动** |
| **C 授权环境理解（实验）** | 用户显式打开后，限定时间段把环境PCM发给专门的无动作/不播报的观察路径，**不复用可触发动作的主聊天会话** | 在授权窗口可获得部分语义和语境 | 只生成候选环境事实/提示，**默认不主动讲话、不写记忆、不执行工具**；再次授权或强可信交互触发才升级 | **默认关闭** |

**物理约束：想在待机时知道“刚才别人具体说了什么”，必须处理其音频并做ASR/语音理解。** 没有这样的运算就只能知道“附近有人讲话”。不能同时要求“永不向任何语义模型送待机PCM”与“准确理解全部待机谈话”。模式C是有成本和隐私要求的可选产品能力，不在本专项首版默认启用。

模式C仅预留**业务需求和授权边界**，不立即建立第二条ASR/LLM常驻链路。第一阶段先做A+B，等真实测试后再决定是否追加C的独立实验；不准拿现有smart_turn直接全时收音再仅靠最终ASR过滤，因为自动response、工具和云端上下文副作用已经可能发生。

### 3.2 拟定实时数据通路

```text
robot-a / roomv2 / reb_mic ─┐
                            ├─ Room PCM (原格式，20ms/640B)
robot-b / roomv3 / reb_mic ─┘     ├─ PerRobot AudioRing + 原有AudioInputGate
                                 ├─ Shared ONNX KWS + 轻量声学活动检测
                                 └─ Attention / Dialogue Arbiter（每头独立）
                                      │ 未准入：留在内存，限长淘汰
                                      │ 准入：带epoch + 预缓冲PCM
                                      ▼
                              原 Qwen-Audio Realtime smart_turn
                                      ├─ ASR / ambient / speech / response / tool事件
                                      ▼
                              发声与动作二次准入（禁止旁人误触发）
                                      ├─ 现有TTS + ForcedAligner + Room
                                      └─ 现有Tool / Ledger / Memory
                                            ↑
                                      speaker真实drained
```

始终共享**模型权重**，不共享机器人音频时钟、PCM缓存、KWS连续命中状态或Session epoch。实现优先保持单Runtime，不引Redis/新常驻sidecar/第二套通用事件总线。

## 4. Qwen事件能提供什么：权威边界

| Qwen/Room事件 | 可获得的状态信息 | 应触发的决策 | 不能推断 |
| --- | --- | --- | --- |
| 本地KWS评分/命中 | 可能喊了“小安妮” | 候选唤醒，经抖动/阈值校验进入WAKE_WAIT | 谁在叫、是否已经提出完整问题 |
| 本地VAD活动（需要时才加） | 可能有人在讲话 | 维护唤醒前缓存、声学在场 | 讲话内容、是否是命令 |
| `input_audio_buffer.speech_started` | 已上送音频出现语音活动 | ACTIVE或候选打断；准备HOLD | 是否有效打断、是否目标用户 |
| `speech_stopped(reason=turn_invalid)` | 无效轮判定 | 无Chat/动作，候选HOLD恢复 | 所有短句都不重要 |
| `input_audio_transcription.delta/completed` | 确认前缀/最终ASR，可能带有限语音线索 | 更新准入回合的文字与展示 | 最终转写之前没有response；精确说话人身份 |
| `ambient_audio_transcription.*` | Qwen认为不是正式对话的环境转写 | 仅瞬时诊断；必要时恢复播放 | 不能转成Chat、提醒、工具或长期记忆 |
| `response.created/text.delta/response.done` | Qwen开始与结束生成、文字输出 | 绑定本轮身份并再次确认发声许可 | 用户已经听到回答 |
| `response.function_call_arguments.done` | 候选动作/工具指令 | 校验当轮授权、Room、epoch、允许动作集 | 模型决定调用就代表设备动作获许可 |
| Room `tts.playback.held/resumed/stopped/drained` | 经过校验的实际播放状态 | HOLD/恢复/打断；**仅speaker drained开启FOLLOWUP** | PCM发送完成=用户实际听完 |

Qwen `turn_detection` 只能在首次发送音频前配置；如实验声纹，首次 `session.update` 的 `voiceprint_audio_urls` 最多支持5个公网可访问样本。必须先评估身份可信度、存储授权和个人数据风险；不作为强制用户认证方案。

## 5. 推荐的产品状态与计时器

业务状态用一个每机器人独立的 `DialoguePresence` 持有；SPEAKING/HOLD是**并行播放子状态**而不是在SLEEP链上复制一套主状态机。

| 状态 | 进入 | 退出及计时（候选初值，实测调整） |
| --- | --- | --- |
| `SLEEP` | 初始化、授权撤销、明确退下、超时 | KWS有效命中→`WAKE_WAIT`；始终采PCM到短内存缓存 |
| `WAKE_WAIT` | 唤醒词确认、轻量LED/目光/提示音，不强制LLM回复 | 5秒内**开始**有效问题→`ACTIVE`；仅喊名字→超时休眠；不能在用户已经开始讲话时截断 |
| `ACTIVE` | 有效语音被正式准入 | 持续整段语音及Qwen推理；不以单一30秒绝对时限砍断长句。Qwen无响应/网络中断单独用错误看门狗 |
| `FOLLOWUP` | 对应轮次的真实 `speaker drained` | 8秒内有效新语音→`ACTIVE`；无目标语音→`SLEEP`；**语音已开始的情况下应允许完成** |
| `CLOSED`（事件而非独立常驻状态） | 用户说退下、拒绝、管理员停麦、服务关闭 | 立即收口、清空相关临时PCM与响应授权，稳定转到`SLEEP` |

建议可以在已经明确持续聊天的场景把FOLLOWUP动态延长到12–15秒；**仅当已经存在可信的活跃会话或朝向/参与证据时允许**，禁止由旁人任何声音无限重置计时器。参数需根据现场误回复率与连续聊天体验调优。

时钟统一使用服务器单调时间；speaker收尾事件必须绑定 `robot_id/room_id/turn_id/stream_epoch/playback_id/source`。时钟到期先撤销准入epoch，迟到的ASR/文本/Tool/TTS帧不得漏执行。

### 首版验收门槛（目标，不代表已有实测）

- 非授权状态下：**0次**TTS、Tool、持久化Chat及记忆写入；包括回合过期、迟到response和重连。
- 室内主场景唤醒召回≥90%、误唤醒≤0.2次/小时、KWS完成触发P95≤500ms（以实际音频末尾为计时起点）；需足量独立负样本才能评估。
- 唤醒+问题同一句至少100段人工核对首句完整性；失败不以“模型回答也合理”代替。
- 原有20ms/640字节协议、原PCM队列新鲜度规则、TTS真实回执、单头嘴型、Room六通道不改变；性能门槛还须在双头实测中验证。
- 打断HOLD确认/无效恢复、speaker drained计时、双头互不串音；真实硬件和浏览器模拟分别记证据，不冒充。
- 每个任务分别最小Git提交并收工检查Git状态；不得覆盖当前大屏工作区未提交修改。

## 8. 模块落点、保留范围和不做事项

- **拟新增最小模块**：`apps/runtime/src/annie_runtime/presence.py`（监听层级、交互状态与发声授权），可独立单测；已有`wakeword.py`只做KWS检测；已有`realtime.py`只接事件和读门控结论。不复制TurnCoordinator、不增加新的Graph或消息总线。
- **推理边界**：模型加载/第三方ONNX SDK调用最终迁至 `packages/annie-adapters` 中必要的适配接口；配置使用现有config/.env规则，模型仅存var/。
- **展示**：只复用现有 `web/` React工作台。保留临时诊断数据，但不留在Chat历史或Memory。
- **保留**：Qwen-Audio 3.0 Realtime Flash作为普通聊天主脑、现有独立TTS/ForcedAligner、两个独立Room及6通道、20轮近期上下文和永久SQLite、现有事件/提醒/动作许可。
- **本阶段不做**：第二套常驻ASR、用LLM逐帧判指向、声纹强认证、未经授权长时间云端录音、自动保存旁人讲话、扩建同Room多声源、双头嘴型、独立React前端或重启Phase10/11。

## 9. 设计需要遵守的三个边界

1. **“待机知道有人说话”≠“待机知道他说了什么”**。可在不开Qwen情况下具备存在感、响应唤醒、处理可信传感器事件，但无法准确跟上房间中全部谈话内容。
2. **“Qwen认为这是有效语音”≠“用户授权机器人说话”**。发声、工具、持久化、记忆必须分别受Runtime的同一回合许可约束，不能把LLM自动生成当作授权。
3. **“不会每句重新唤醒”≠“永远免唤醒”**。追问窗口与可信注意力信息可扩大自然交谈范围；长期无人互动后必须退回有明确触发条件的待机。

**推进门槛**：本文件是设计成果。先经VP-A定稿后开展VP-B训练；训练数据/资源、硬件播放协议或希望默认运行模式C的授权语义未确认时，只暂停相关分支，不假装已接线或达标。

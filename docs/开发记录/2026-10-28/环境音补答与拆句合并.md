## 原因

1. **环境音进不了唤醒门。** 阿里云 Qwen-Audio Realtime 服务端事件文档写明，`conversation.item.ambient_audio_transcription.*` 的 `item_id` 是 “A standalone temporary ID, not associated with any conversation item”，与 `input_audio_buffer.speech_started` 的 item_id 不是一回事。日志也表明环境音片段前没有 `speech_started`：
   - 今天 144 个 turn_invalid 只有 1 个草稿为空；
   - 环境音终稿到达后的 0.6 秒等待里，从没有新的 `speech_started` 打断它。

   补判后的话走 `transcript_accepted(text, 临时ID)`，唤醒门里没有这段话的候选（实测 `_candidate=False`），于是被拒（`unadmitted_transcript`），而且不记日志。上午的测试先发 `speech_started` 再发同 ID 的环境音终稿，不是云端的真实顺序，所以测试通过、真机全丢。
2. **环境音拆成的两段合不上。** 合并靠后半段的 `speech_started` 触发（`_carry_dropped_call`），后半段也是环境音时没有这个事件，两段就各判各的。有些后半段在前半段还没判完时就到了，这时会直接覆盖前半段的补判状态，前半段被丢掉。
3. **补问撞上用户开口就断线。** 文档写明 `speech_started` 到 `response.done` 之间不允许 `response.create`。补问前的 0.6 秒等待里用户又开口时，云端拒绝请求，代码却按未知错误抛出，导致整个实时会话重连。

## 修改

- **旁听补答准入**（`presence.py`）。新增两个方法：
  - `overheard()`：环境音等待判断时，像 ASR 宽限一样保持窗口打开。刚唤醒的 5 秒窗口不会在判断途中关上。
  - `overheard_accepted(text)`：点名，或决策模型判对她说的环境音，凭这一结论获得回答许可。它不要求、也不占用语音候选，正在说的新一句不受影响。
- **环境音补答走旁听准入**（`realtime.py`）。环境音补判的终稿带 `_overheard` 标记，准入时改用 `overheard_accepted`。补判后仍被唤醒门拒绝时，新增一行 `recovery_unadmitted` 日志，这类问题不再无声无息。
- **环境音拆句合并**：
  - 前半句已出终稿、还在等待或判断时，后半段环境音的第一条增量（`_her_voice_audible()` 为假时）或终稿（不是她的回声时）把前半句转成待合并（`_continued_after_drop`），合成一句再判断、回答一次。
  - turn_invalid 只有草稿、终稿未到时不合并，以免同一句被拼两遍。
- **补问被拒不断线**：
  - `_answer_recovered_call` 的 `response.create` 带 `event_id`。
  - 云端以 `invalid_value` / “while user is speaking” 拒绝它时，不再抛出；这一轮记为 `cancelled`（`cancel_source=user_speaking`），整句作为已准入的前半句等待用户说完，合起来回答，不再二次判断。
  - 新增日志 `recovered_answer_deferred`。
- **日志字段**：
  - `ambient_heard` 新增 `joined_chars`（并入的前半句字数）、`deltas` 与 `delta_ms`（这段环境音第一条增量到终稿的毫秒数，用来确认增量是否边说边来）。
  - 环境音因另一段语音未结束被忽略时，记 `ambient_ignored reason=speech_pending`。

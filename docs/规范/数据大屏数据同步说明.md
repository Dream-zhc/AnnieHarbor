# 数据大屏数据同步说明

日期：2026-10-14。给外包数据大屏。页面由外部项目做，本仓库不再把 `/?view=cockpit` 当作大屏交付。

大屏只连现有 Java Room，不另开 Annie 的 8780 接口。一台机器人一个房间：`annie-a` → `roomv2`，`annie-b` → `roomv3`。当前根地址是 `ws://192.168.1.47:8090/robot`，以 `config/rooms.toml` 为准。

数据分两路：

- **设备通道**：视觉、麦克风、扬声器已经在发的内容。大屏直接订阅。
- **`reb_display`**：系统内部事件。同一房间上单独一条，只给大屏。异步发送，不进实时对话那条链路。

大屏对所有通道都只订阅、不回写。

## 1. 先看订哪条

| 大屏要显示 | 连接 | 现状 |
| --- | --- | --- |
| 说话中、句末识别、环境里听到但没进对话的字 | `reb_voice` | 已在发 |
| 扬声器是否在播 | `reb_voice`（旧播放器也可能在 `reb_main`） | 已在发 |
| 麦克风开/停 | `reb_voice` | 已在发 |
| 人脸框、物体框 | `reb_visualdata` | 已在发 |
| 摄像头画面 | `reb_vision` | 已在发 |
| 画面描述 | `reb_visualllm` | 已在发 |
| 环境声音波形 | `reb_mic` | 已在发 |
| 小安妮音频里夹带的文本、表情指令 | `reb_tts` | 已在发 |
| 动作指令 | `reb_main` | 已在发 |
| 嘴型 | `reb_sam` | 已在发 |
| 逐字 ASR、小安妮回复正文、唤醒状态、轮次、动作执行到哪一步、在线/异常 | `reb_display` | Annie 已异步写入 |

主画面先订四条现成的：`reb_voice`、`reb_visualdata`、`reb_vision`、`reb_visualllm`。字幕和唤醒等内部状态再订 `reb_display`。波形、动作、嘴型按需加。

## 2. 每条连接都一样

```text
ws://<房间主机>:8090/robot/<room_id>/<通道名>
```

例：`ws://192.168.1.47:8090/robot/roomv2/reb_voice`

连上后先收到：

```json
{"type":"WELCOME","ok":true,"room":"roomv2","robotId":"reb_voice"}
```

`room` 是 `roomv2` 或 `roomv3`。`robotId` 是通道名，例如 `reb_voice`，不是 `annie-a`。

然后发送并等待 ACK：

```json
{"type":"SUBSCRIBE","data":{"types":["*"]}}
```

`WELCOME`、`ACK` 只是握手。断线后重新握手。两台机器人各连各的房间。

`reb_mic`、`reb_tts`、`reb_vision`、`reb_sam` 流量大。大屏画不过来就丢旧帧，只留最新一条。

## 3. 设备通道里已经有的

认不出的 `type` 丢掉。

### `reb_voice` 说话、句末文本、播放回执

用户状态由 Annie 异步写入，类型是 `voice.interaction`。积压超过 32 条会丢，对话不等它。

```json
{
  "type": "voice.interaction",
  "description": "用户语音识别最终文本",
  "ts": 1728870000000,
  "data": {
    "sender": "brain",
    "trigger_source": "qwen_realtime",
    "event": "transcript.done",
    "robot_id": "annie-a",
    "item_id": "这句话的编号",
    "conversation_id": "这一轮的编号",
    "text": "今天天气怎么样"
  }
}
```

| `data.event` | 大屏 |
| --- | --- |
| `speech.started` | 点亮「说话中」。`text` 一般为空 |
| `speech.stopped` | 熄灭「说话中」 |
| `transcript.done` | 这句定稿。用 `data.text` 替换访客字幕，最长 256 字 |
| `transcript.ambient` | 环境里识别出的字，没有进入对话 |
| `transcript.ambient_promoted` | 这句环境语音后来被收进对话。同样读 `data.text` |

`item_id` 把开始、结束和文本归到同一句。`conversation_id` 是一轮对话，开始说话时可以是 `null`。别的 `data.event` 不要当字幕。

扬声器回执也在这条上。旧播放器可能把同样的内容写到 `reb_main`，按 `data.playback_id` 去重。

```json
{
  "type": "tts.playback.started",
  "data": {
    "protocol_version": 1,
    "conversation_id": "这一轮的编号",
    "stream_epoch": 1,
    "playback_id": "这次播放的编号",
    "source": "speaker",
    "sender": "speaker",
    "sample_rate": 24000,
    "played_sample_count": 0,
    "seq": 1
  }
}
```

| `type` | 含义 |
| --- | --- |
| `tts.playback.started` | 扬声器已开始播 |
| `tts.playback.progress` | 进度。`played_sample_count` 是 24kHz 累计采样 |
| `tts.playback.held` / `resumed` | 按住 / 恢复。另有 `command_seq` |
| `tts.playback.stopped` | 被停止。可有 `reason` |
| `tts.playback.drained` | 这一轮播完 |

只有 `source` 为 `speaker` 才显示「机器人正在说」。`browser_test` 是网页试听，不能当成扬声器，也不能把已经亮着的扬声器状态清掉。`tts.playback.hold`、`resume`、`stop` 是发给播放器的命令，不是回执。

麦克风开停：

```json
{"type":"mic.capture.started","data":{"sender":"microphone"}}
```

`mic.capture.stopped` 字段相同。这只表示采集端报了开或停。有人在说话看 `speech.started`。

### `reb_visualdata` 人脸框和物体框

画框只读这一条。

```json
{
  "type": "vision.perception",
  "kind": "face",
  "tracks": [
    {"name": "person-a", "bbox": {"x1": 1, "y1": 2, "x2": 10, "y2": 20}, "expression": "中性"}
  ],
  "from": "vision",
  "ts": 1728870000000
}
```

| 字段 | 含义 |
| --- | --- |
| `kind` | `face` 人脸，`object` 物体，`gesture` 手势 |
| `tracks[].bbox` | `x1,y1,x2,y2` |
| `tracks[].name` | 人脸轨迹名 |
| `tracks[].label` | 物体类别，例如 `cup` |
| `tracks[].expression` | 有就显示这个字，没有不要编情绪分 |
| `gesture` | `kind` 为 `gesture` 时的手势对象 |

新的一条替换旧框。框叠在 `reb_vision` 的画面上。协议只确定这四个数字，示例是整数；没有写明是像素还是 0 到 1。和画面对不齐时以视觉端当前输出为准，不要在前端换算坐标系。

旧消息 `type` 可能是 `face`、`object`、`gesture`。没有 `tracks[].bbox` 的那一帧不画框。

### `reb_vision` 摄像头

图像，不是框。裸 JPEG/PNG，或二进制帧：前 2 字节大端类型名长度，接着 UTF-8 类型名，后面是图像。没有帧就显示「待连接」。

人脸框不要套到别的视频上。若展厅另有 LiveKit，那是另一台服务；除非确认和 `reb_vision` 是同一个摄像头、同一套坐标，否则框只画在 `reb_vision` 上。

### `reb_visualllm` 画面描述

```json
{
  "type": "visualllm",
  "description": "画面中一人坐在桌前，右手拿着麦克风，桌面有电脑。",
  "schema_version": 2,
  "facts": {
    "subjects": [
      {"id": "person_1", "kind": "person", "attributes": ["坐着"], "action": "右手拿着麦克风", "position": "桌前", "confidence": 0.94}
    ],
    "relations": [{"subject": "person_1", "relation": "holds", "object": "mic_1"}],
    "uncertainties": [],
    "changes": []
  }
}
```

`description` 直接上屏，新消息替换旧的。超过 10 秒没有新消息，改显示「视觉信息未观测」。

`facts` 可以没有。有的话：`subjects` 是这一帧的人和物，`id` 只是跟踪号，不是姓名；`position` 是文字位置，不是框。`relations` 用 `subject`、`relation`、`object` 引用这些 id。`confidence` 是看清楚的程度，0 到 1，可缺。

### `reb_mic` 环境音

先收到 `mic.start`，再收二进制 `MIC_AUDIO`：16kHz、单声道、S16LE、20ms、640 字节。

```json
{
  "type": "mic.start",
  "data": {
    "audio": {
      "codec": "pcm_s16le",
      "sample_rate": 16000,
      "channels": 1,
      "frame_ms": 20,
      "bytes_per_frame": 640
    }
  }
}
```

这是麦克风原始输入，环境和人声混在一起，没有分贝，也没有单独的环境分轨。只用来画波形，不要把声音写回房间。环境里识别出的字在 `reb_voice` 的 `transcript.ambient`。

### `reb_tts` 合成文本和表情

音频主路径。每一帧都带这段要说的字，同一段 `text` 会重复出现，文本没变就不要追加。

```json
{
  "type": "tts",
  "ts": 1728870000000,
  "data": {
    "text": "今天适合出门。",
    "audio": "<base64 PCM>",
    "format": "pcm_s16le",
    "sample_rate": 24000,
    "channels": 1,
    "conversation_id": "这一轮的编号",
    "turn_id": "这一小段的编号",
    "final": false,
    "stream_epoch": 1
  }
}
```

只要字幕就读 `data.text`，不必解码 `data.audio`。`final: true` 只表示这段合成结束。扬声器播完看 `reb_voice` 的 `tts.playback.drained`。

表情是另一条 JSON，值只有 `喜`、`怒`、`哀`、`乐`、`中`：

```json
{"type":"expression","ts":1728870000000,"data":{"expression":"喜","turn_id":"这一轮的编号","source":"robot_main_brain"}}
```

这是指令，不是脸上已经做完。

### `reb_main` 动作指令

```json
{
  "type": "action_trigger",
  "ts": 1728870000000,
  "data": {
    "script_id": "listen_tilt",
    "offset_ms": 0,
    "conversation_id": "这一轮的编号",
    "anchor_source": "robot_main_brain"
  }
}
```

`script_id` 是动作名，例如 `listen_tilt`。显示「已下发」。没有电机完成回执。播放回执若出现在这里，解析方式和 `reb_voice` 相同。

### `reb_sam` 嘴型

`type` 为 `mouth_script`。用 `at_sample` 对齐扬声器回执的 `played_sample_count`（24kHz）：游标到了就切 `viseme`。同一轮看 `conversation_id`。没有消息就不要按字数编口型。跟不上就丢。

## 4. 系统内部事件：`reb_display`

唤醒、逐字识别、小安妮回复正文、这一轮开始和结束、动作走到哪一步、在线还是异常，都在 Annie 进程里。这些不写进 `reb_voice`。`reb_voice` 只管说话检测、句末文本和播放控制，再塞内部事件会跟打断、暂停抢同一条通道。

所以在**同一个** `roomv2` / `roomv3` 上单独加一条只给大屏的 JSON 通道：

```text
ws://192.168.1.47:8090/robot/roomv2/reb_display
ws://192.168.1.47:8090/robot/roomv3/reb_display
```

握手与第 2 节相同，`WELCOME` 里的 `robotId` 应为 `reb_display`。不新建 `roomv4`，也不在 Annie 上再开一个端口。地址写在 `config/rooms.toml` 的 `display`。

Annie 用独立任务往这条通道推，队列最多 32 条，满了丢掉最旧的；逐字识别和回复正文只保留最新一条。发送失败只记日志。用户说话、合成和播音都不等待这条通道。

大屏只收到下面一种业务消息。中间结果用新的替换旧的，不必排队播完历史。

```json
{
  "type": "display.event",
  "description": "用户语音识别中间文本",
  "ts": 1728870000000,
  "data": {
    "sender": "brain",
    "robot_id": "annie-a",
    "room_id": "roomv2",
    "event": "transcript.delta",
    "item_id": "这句话的编号",
    "text": "今天天气",
    "stash": "怎么样"
  }
}
```

公共字段是 `sender`、`robot_id`、`room_id`、`event`。下表是每种 `event` 多出来的字段。

| `event` | 大屏怎么用 | 额外字段 |
| --- | --- | --- |
| `transcript.delta` | 访客字幕的中间结果。`text` 是这句已经稳定的字，整段替换；`stash` 是还没稳定的尾巴，可以灰色接在后面 | `item_id`，`text`，`stash` |
| `transcript.final_preview` | 即将定稿的预览，仍可能被改掉 | `item_id`，`text` |
| `text.delta` | 小安妮回复正在变长。`text` 已是整段，直接替换 | `turn_id`，`text`，`delta` |
| `text.done` | 这轮回复的正文结束 | `turn_id`，`text` |
| `turn.started` | 一轮对话开始 | `turn_id`，`user_text` |
| `turn.done` | 一轮结束。`status` 为 `completed`、`cancelled`、`failed`、`discarded` | `turn_id`，`text`，`status` |
| `wake.state` | 唤醒灯。状态见下表 | `enabled`，`state`，`candidate_speech`，`deadline_remaining_ms`，`last_keyword`，`error` |
| `action.state` | 动作或表情指令的进度。`real_device_executed` 固定 `false` | `call_id`，`turn_id`，`action_kind`，`action_value`，`status`，`generation` |
| `session.ready` | 实时模型已连上，显示在线 | 无 |
| `session.error` | 实时模型异常 | `error` |

`wake.state` 的 `state`：

| 值 | 显示 |
| --- | --- |
| 未启用（`enabled` 为 false） | 免唤醒 |
| `SLEEP` | 休眠，等待唤醒 |
| `WAKE_WAIT` | 已唤醒，等待提问。`candidate_speech` 为 true 时显示正在听 |
| `ACTIVE` | 对话进行中 |
| `FOLLOWUP` | 等待追问。`deadline_remaining_ms` 是剩余毫秒，到点由服务端自己改状态 |
| `error` 非空 | 唤醒异常，显示 `error` |

`action.state` 里 `action_kind` 为 `action`（肢体脚本）或 `expression`（`喜怒哀乐中`）。`action_value` 是脚本 id 或表情字。`status` 为 `published_unknown`、`send_unknown`、`queued`、`awaiting_audio_anchor`、`awaiting_text_anchor` 时，表示指令已发出或还在对齐。`cancelled_before_send`、`rejected_late`、`conflict_or_cooldown` 表示没按预期发出。`generation` 与当前进程不一致的旧指令丢掉。文案写「指令状态」，不写「设备已经做完」。

句末定稿仍以 `reb_voice` 的 `transcript.done` 为准。`reb_display` 的中间结果只负责让字幕早点动。两边用 `item_id` 对上同一句；定稿到达后不再显示这句的 `stash`。

`reb_display` 不重复发送音频、人脸框、画面和扬声器回执。那些继续看第 3 节的原通道。

## 5. 两边都没有的

这些保持空白或「未观测」，不要填设计稿里的数：

| 项 | 原因 |
| --- | --- |
| 访客姓名、声纹是谁 | 不进大屏消息。`person_1` 不是姓名 |
| 记忆原文 | 不下发 |
| 情绪百分比 | 没有。只有框上可选的表情字，和 `reb_tts` 的五档表情指令 |
| 独立环境分贝、三路分轨波形 | 没有。波形只来自 `reb_mic` |
| 头部角度、动作已做完 | 没有设备回执 |
| 健康分、注意力 | 没有这种分数 |

## 6. 优先级

实时对话的顺序是：`reb_mic` 进声音，Annie 调云端，`reb_tts` 出音频，`reb_voice` 收扬声器回执并做暂停、恢复。大屏是旁路。

`reb_display` 更靠后：独立任务、队列满就丢、失败不影响开口。大屏渲染慢，也只丢自己的帧，不向任何通道回发 PCM 或控制。

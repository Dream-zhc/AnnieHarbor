## 1. V2 的真正目标

V2 不以“接入 LangGraph”“模块拆得更多”“Agent 更复杂”为成功标准。

最终目标是把小安妮做成一个适合真实机器人实时交互的陪伴型 Brain：

1. **接得快**：PCM持续送入Realtime，语义轮次结束后尽快产出第一个可播句。
2. **接得住情绪**：低落、委屈、烦躁、开心等场景先承接人的状态，而不是机械分析或马上给建议。
3. **懂连续上下文**：指代、改口、继续刚才、未完成话题、机器人自己的承诺都能正确延续。
4. **记得对的东西**：只在真正相关时使用长期记忆，不以召回数量作为“聪明”的指标。
5. **人格稳定**：每个 Chat 固定 Persona；不同 Persona 的语言、社交距离、幽默和追问方式有稳定差异。
6. **知道什么时候少说**：不是每轮都追问，不把陪伴做成模板化心理咨询。
7. **复杂问题仍然能升级能力**：需要多步骤编排时才进入 Complex Task Path，不拖慢普通陪伴回合。
8. **一个项目并发多个机器人头**：同一个 V2 Runtime 可同时运行多个机器人实例，支持订阅同一个或不同的 WebSocket 房间；每个头独立处理事件、维护会话并输出语音与动作。

因此 V2 的基本产品公式是：

```text
低延迟
+ 正确上下文
+ SocialState
+ Persona
+ 少而准的长期记忆
+ 合适的模型路由
= 陪伴型“聪明感”
```

## 2. 已确认的范围

### 2.1 输入与模型分工

- **主对话入口：机器人经Room传来的PCM。** Audio Input Gate只做来源/格式/开关/限流与背压，不再串接本地ASR、独立LLM或第二套语义断句模型。
- **Web文本入口保留**，用于调试与产品文本交互，进入同一机器人Realtime Session；旧ASR文本协议仅作为显式兼容/回放输入，不再定义主链。同一段语音不能同时经PCM和ASR文本触发两次回复。
- **Qwen-Audio 3.0 Realtime Flash**（目标模型ID `qwen-audio-3.0-realtime-flash`）负责语音理解/ASR、smart_turn、陪伴对话、Persona和Function Calling；只使用文本输出接后续链。
- **Qwen-Audio-3.0-TTS-Flash**（目标模型ID `qwen-audio-3.0-tts-flash`）独立生成PCM；保留ForcedAligner与viseme映射，不使用Realtime自带语音作为第二路播报。
- 本地ASR/KWS/VAD、Pipecat、额外意图/情绪/规划模型不进入首版；远端smart_turn与边听边说进入本轮目标，但设备回声、打断和播放事实必须单独验收。

Robot / Chat / Persona / generation隔离

## 4. 总体架构：三条路径，一处发声协调

### Realtime Hot Path

```text
Robot → Room PCM → Audio Input Gate → Qwen-Audio 3.0 Realtime Flash
                                      ├─ ASR / smart_turn
                                      ├─ 对话理解 / Persona / 最终表达
                                      ├─ Function Calling → 本地执行器
                                      │                     ├─ ActionArbiter → 动作/表情
                                      │                     └─ 简单Tool → 结果回写Realtime
                                      └─ Text Stream → 有界可播片段
                                                       ↓
                                          Qwen-Audio-3.0-TTS-Flash
                                                       ↓ PCM
                                              ┌────────┴────────┐
                                              ↓                 ↓
                                             Room      ForcedAligner + 对应文本
                                                                 ↓
                                                          Viseme映射 → Room
```

### Event Path

```text
Sensor / Vision / Timer / External Event
                ↓
           Event Router → WorldState
                ↓
           Speak Policy
          ↙            ↘
   Context Only       Need Response
       ↓                   ↓
有界动态上下文         SpeakRequest
（不触发推理）              ↓
                      TurnCoordinator
                            ↓
                注入事件 → response.create
                            ↓
                    Realtime最终表达
```

压力连续变化只更新状态；摸头可请求响应（去抖/冷却后）；微笑通常只补上下文；提醒到期可请求响应。它们是产品默认策略，不把每帧传感器数据变成会话消息。

### Complex Task Path

```text
Realtime Function Calling / Event Router
                  ↓
       已确认需多步骤的Complex Task
                  ↓
               LangGraph
                  ↓
         Tools / Memory / Workflow
                  ↓
          Structured Result
                  ↓
    SpeakRequest → TurnCoordinator
                  ↓
 conversation.item.create → response.create
                  ↓
      Realtime Persona化最终表达
                  ↓
          同一独立TTS/嘴型出口
```

函数调用结果用关联call_id的工具结果回写；事件结果用带来源的事实注入，二者不冒充用户原话。SpeakRequest是内部数据，不是新增Room wire类型；它可携带工具调用关联，避免重复注入。无须开口的结果只提交状态。

| 组件 | 唯一职责 | 明确不做 |
|---|---|---|
| Realtime | 理解、对话、Persona、语义工具选择、最终表达 | 直接控制设备或决定本地发布资格 |
| LangGraph | 复杂任务事实、状态、工具编排、暂停/恢复 | 普通聊天、最终小安妮式回复、直接TTS |
| Event Router | 来源归一、robot归属与事件分发 | 每个事件都启动Graph或模型 |
| Speak Policy | 价值、时效、冷却与是否值得开口 | 生成自然语言回复 |
| TurnCoordinator | 当前是否可发声、请求仲裁、取消与generation | 重做smart_turn或新增规划模型 |
| TTS / ForcedAligner | 独立音频合成 / 对齐后映射嘴型 | 对话理解或动作决策 |

这些是职责边界，不要求每个框必建新包/服务；热链继续单Python主进程和短异步调用路径。

### 4.1 多机器人头并发（第一版必备）

**这是已确认需求，不是后续扩展项。** 一个 `brainv2/` 项目、一个 Python 主进程必须能够并发运行多个机器人头，不采用“一个头一份项目”的部署方式。这里的机器人头是独立的逻辑运行实例，以稳定且唯一的 `robot_id` 标识，与房间、用户、Chat 和 Persona 分开建模。

同一 Runtime 必须支持：

1. 多个机器人头订阅同一个 WebSocket 房间，接收相同房间事件；按显式订阅与路由规则决定哪些实例处理，不隐式只交给一个全局 Brain。
2. 多个机器人头分别连接不同房间，房间 URL 和协议可以相同，具体房间绑定可以不同。
3. 同一房间PCM仅按明确来源/广播配置送入对应头；广播可由各订阅头独立响应；定向音频、兼容ASR文本、Web输入、小脑cancel/action和设备事件只进入指定实例。

最小链路：

```text
Room WebSocket event
        ↓
RoomProtocolAdapter（保持现有外部协议）
        ↓
显式房间订阅 / 目标匹配 / 广播 fan-out
        ↓
RobotRuntime[robot_id]（多个实例异步并发）
        ↓
独立 Realtime Session / TurnCoordinator / Ledger / TTS / ActionArbiter
        ↓
按 robot_id 绑定的 Room / 设备输出目标发布
```

**实例配置**放在 V2 的 `config/robots.toml`：每个实例至少声明 `robot_id`、启用状态、房间连接与订阅、输入匹配与广播规则、输出设备或连接绑定、默认 Persona，以及 `listen_enabled` / `publish_enabled`。`room_id` 表示明确的房间连接身份，不能只用相同 URL 代替房间身份；`robot_id` 不能直接等同于 `room_id`。

**事件归属与同房间边界：**

- Adapter 将连接绑定、现有设备标识和目标字段转为内部 `robot_id` / `room_id`；不为内部多实例设计擅自修改外部协议。
- 同房间定向事件只投递给命中的机器人；同房间广播事件向显式订阅的机器人各投递一次，不把广播去重成“只有一个机器人收到”。
- 无目标且未配置为广播的事件必须记录未路由原因，不猜测目标。小脑 cancel 必须关联机器人及当前 `turn_id` / `generation`，不得取消其他头的回合。
- 同房间多头输出必须有可验证的设备标识、目标字段或独立输出连接绑定；Phase 0 核实接收端如何区分音频、嘴型、动作和取消消息。若现有协议缺少这些能力，将差距列为联调前置项，明确单独确认的协议变更或输出通道方案，不宣称仅靠内部 `robot_id` 就能区分接收端。
- 避免自身输出回流成为新输入；重连去重按房间来源事件身份与 `robot_id` 组合处理，去重状态有界，不能抑制其他机器人对同一广播的合法处理。

**状态隔离与并发：**

- 每个机器人独立拥有Audio Input Gate、Realtime Session与session_epoch、TurnCoordinator、当前回合与generation、取消令牌、输出队列、按需Task/checkpoint、SocialState、WorldState、Ledger和ActionArbiter；同名 Chat/Persona 不构成共享 runtime 的理由。
- 同一头按现有回合、打断规则协调，不同头使用独立异步任务并发；不使用一个覆盖所有头的全局回合锁。TTS/LLM 阻塞调用不得阻塞整个事件循环。
- Provider 客户端、SQLite 连接管理和无状态 Adapter 可复用，但可变回合状态不可共享。使用实例级有界队列、超时和取消，避免一个头积压拖垮其他头；共享 Provider 限流与 SQLite 写入资源应公平调度并记录等待时间。
- 单机器人失败隔离：某个头断线、TTS/LLM 超时或被取消，不重置其他头的会话与输出；共享房间连接重连仅影响依赖该连接的订阅实例，并恢复订阅。
- 默认每个机器人隔离长期记忆；仅在显式配置共享范围时，允许同一用户的 Global Fact 或同一 Persona Memory 跨头共享，不能把设备状态、短期上下文和关系状态隐式混用。
- Dashboard、Developer、forensic 和 latency trace 都带 `robot_id` / `room_id`，支持选择机器人和查看各实例健康状态。

并发目标沿用单进程、本地 SQLite、原生异步任务的最小实现，不因此新增 Redis、Kafka、复杂事件总线或分布式调度框架。共享房间入口是否复用连接，以协议支持和实测为准；入口复用不改变逐机器人投递语义。

## 5. Realtime Hot Path：默认陪伴路径

普通寒暄、情绪倾诉、安慰、连续闲聊、轻量追问与简单事实回复直接由Realtime完成，**正常聊天禁止经过LangGraph**。

- 不等待ASR最终文本再发给另一个LLM；转写用于Ledger、展示与评测，不成为音频主链第二入口。
- 无工具回合只有Realtime响应，不额外串联intent/emotion/planner/memory judge；发生Function Calling时允许必要的工具结果续推理，单独统计，不能用“一次模型调用”约束破坏工具协议。
- 文本增量及时放行；分句具有最大长度和最大等待，不能等完整回复、完整动作JSON或Graph结果再开启TTS。
- 本地状态/队列提交顺序明确，非关键日志/记忆整理异步后置；共享Provider容量按头公平，禁止全局回合锁。
- 目标是尽快说出自然、有上下文的第一反应，而不是每轮长答案。语义转写错误与对话错误分开评分。

测量PCM入口/上送、轮次事件、首文本、首可播段、TTS首PCM、Room发布及设备起播；smart_turn判轮、应用排队和外置TTS时间分别列出，详见第24节。

## 6. Complex Task Path：按需升级

只有需要多步骤、多工具、记忆组合、可暂停/恢复或复杂事件处理时才进入LangGraph。普通动作/表情/单工具不进Graph；问题“很难”不自动等于需要工作流，先证明多步骤状态的必要性。

Realtime通过一个明确的复杂任务工具提交目标与必要参数；Event Router只把命中已实现工作流的事件交给LangGraph。任务异步执行，返回成功/失败/取消、事实、来源与任务状态，不生成最终Persona文案。长任务先回写已受理的结构化状态；后续完成作为带task_id的事件申请发声，不重复完成同一call_id。

复杂任务可以使用额外推理模型，但其额度、超时、取消和资源等待与热链隔离。结果回到发起的robot/user/persona/chat/session绑定，不能无条件注入“当前最新Session”；会话切换、结果过期或任务取消后重新评估或丢弃，并保留原因。

Phase 8仅选择一个真实需要状态编排的工作流证明链路；Phase 11再做复杂任务模型/策略A/B。普通陪伴不因Graph、checkpoint或强模型故障停摆。

## 7. SocialState：陪伴质量核心状态

V2 新增轻量 `SocialState`，但不能新增一个专门情绪 LLM。

建议状态：

```text
user_affect
conversation_mode
relationship_tone
response_need
question_pressure
humor_level
advice_readiness
```

示例：

```text
user_affect = negative
conversation_mode = emotional_support
response_need = empathize_first
question_pressure = low
advice_readiness = false
```

SocialState 来源：

```text
明确规则
最近 Conversation Ledger
Persona 状态
Realtime当前回合可获取的明确状态信号（可选，不强制文本流同时输出复合JSON）
```

禁止为 SocialState 每轮额外调用一个模型。

SocialState 的目的不是给机器人贴心理学标签，而是帮助回答控制：

```text
先接住还是先解决
该不该追问
能不能开玩笑
回复应该多长
是否避免立即建议
```

### SocialState 的更新与纠正

状态允许`unknown`，每条判断带来源和更新回合；用户明确表达/纠正优先于旧状态及模型推断。Chat/Persona切换必须按隔离规则重置；情绪等暂态需要明确的衰减或失效条件，不跨会话默认沿用。迟到的StateDelta须核验turn/generation后提交。

规则只整理明确事实与回复策略，不做关键词驱动的复杂情绪状态机。减少的是无效追问；完成用户目标必需的澄清仍应进行。Phase 3先测更新规则，Phase 4/5再用真实对话评估表达效果。

## 8. LangGraph的新职责边界

```text
LangGraph = 事实 + 状态 + 流程 + 工具编排
Realtime = 理解 + 对话 + Persona + 最终表达
```

LangGraph不再拥有普通回合的hydrate/gather/generate/commit主链，也不负责实时音频或设备发布。仅在有真实复杂任务的Phase 8引入必要节点与AsyncSqliteSaver；没有任务就不建Graph/表/空壳。

最小任务链按实际业务构建：读取任务状态 → 执行必要Tools/Memory步骤 → 提交结构化结果。结果包含task_id、所属会话、状态、来源与时效；例如业务事实载荷可以是：

```json
{
  "event": "room_temperature_high",
  "temperature": 31.8,
  "severity": "mild",
  "suggestion": "可以提醒用户开空调"
}
```

单个温度阈值本身由普通事件规则处理，无须为了上述例子启动Graph；只有结合多源事实、任务状态或工具编排时才进入复杂路径。结果是Evidence，不是system指令或已执行动作；Realtime可以自然表达为“有点热起来了，要不要把空调开一下？”。

持久化只面向工作流：接入时声明checkpoint写入时机、恢复和失败语义；恢复前核验任务绑定和副作用执行记录，不能重放已发送音频/动作或重复创建提醒。任务副作用有稳定幂等键；进程崩溃后的不确定执行不得当作未执行盲目重试。Graph完成不代表机器人已经说出结果。

Ledger、语音会话和播放回执的提交生命周期独立于Graph；下一轮直接看见用户更正/取消，不等待Graph结束。普通聊天验收以Graph调用数为0为硬门槛。

## 9. Chat / Persona / Memory 隔离

### 9.1 Realtime Session与按需Task隔离

逻辑会话键：

```text
{robot_id}:{user_id}:{persona_id}:{chat_id}
```

每个逻辑会话绑定独立Realtime Session；重连增加session_epoch，并映射Provider session/response/item/call身份与本地turn/generation。切用户/Chat/Persona先取消旧输出并切会话，不沿用旧上下文；同Persona revision更新仅更新会话指令。

复杂工作流thread_id在上述身份上增加task_id，避免同一会话两个任务共用checkpoint；仅在复杂任务启动时创建。

Robot / Chat runtime 严格隔离：

```text
history
pending inquiry
unresolved topic
short-term commitments
SocialState
```

Working Memory 与 Long-term Memory 必须分开：

```text
Realtime Working Memory
  = Realtime会话有界上下文
  + 本地Ledger / SocialState / WorldState相关快照
  + TurnCoordinator运行状态

Complex Task Working State（按需）
  = LangGraph State + AsyncSqliteSaver + task_id隔离checkpoint

Long-term Memory
  = LangMem 负责 extract / update / merge / delete
  + AsyncSqliteStore 负责持久化与查询
  + sqlite-vec 只负责需要语义检索的 namespace
```

Realtime Session不是持久化真源；重连只重建已确认的有界上下文，不能重发旧PCM、旧response.create或旧副作用。Checkpoint不保存完整历史聊天。最近真实对话、`assistant_spoken_text`、cancel/interrupted 等事实继续以 Conversation Ledger 为准；Graph State 只保存当前回合真正需要的有界工作状态。

长期记忆 namespace 必须由 `robot_id` 与显式共享配置决定。默认按机器人隔离；显式共享时也必须限定用户和 scope，禁止因为同一 `user_id` 就隐式跨机器人共享 Persona 或 episodic memory。

第一版 namespace 采用最小固定结构：

```text
("memory", robot_scope, user_id, "semantic")
("memory", robot_scope, user_id, "persona", persona_id)
("memory", robot_scope, user_id, "persona", persona_id, "episodes")
```

Episodic memory默认随Persona隔离，避免人格专属故事经公共episodes泄漏。确需跨人格复用的客观事实，经显式筛选后进入semantic scope；暂不新增第二套公共经历库。所有读取都采用服务器侧确认的完整scope，不接受模型自行扩大范围。

Phase 2/3须明确`user_id`绑定：来源设备、Room连接和显示姓名不自动代表同一自然人；未知身份使用隔离的匿名会话，不写具名用户长期记忆，不跨Chat/机器人合并匿名历史。绑定/解绑及切换用户有回归测试；采用哪种可信身份输入由真实协议和产品确认。

thread_id各身份段使用明确校验或无歧义编码，覆盖分隔符碰撞；namespace检索覆盖前缀相似、大小写和特殊字符，不只测试完全不同的名字。

### 9.2 Global User Memory

保存稳定、可复用的用户事实与偏好。结构化字段优先 exact lookup；只有模糊表达、近义偏好或无法稳定键控的内容才进入 semantic search。

### 9.3 Persona / Episodic Memory

Persona memory 保存：

```text
用户对这个人格的反馈
Persona 专属关系状态
Persona 专属故事
```

Episodic memory 保存过去真正有复用价值的经历摘要，不保存完整逐字聊天。

召回按 scope 分开：

```text
Structured / Global Search
+ Current Persona Search
+ Episodic Search（仅在当前问题需要时）
        ↓
dedupe / rerank / relevance filter
        ↓
Context Packet
```

## 10. Memory 的陪伴原则

Memory 不是召回越多越好。

普通回合：

```text
Recall candidates
    ↓
relevance filter
    ↓
0~4 条进入 Prompt
```

很多普通回合 0 条 Memory 是正常的。

禁止把以下内容长期写进 Long-term Memory Store：

```text
当前槽位
当前 HOLD
最近几轮逐字聊天
临时视觉
机器人当前动作
短时情绪
```

它们分别属于Ledger / Realtime Working State / WorldState / SocialState。

LangMem 只运行在回合结束后的后台记忆整理链，不进入 Companion hot path。已实现的简单记忆查询由Realtime工具或受预算约束的上下文更新直接读Store；复杂记忆组合才进入LangGraph，不在每轮前强制检索；禁止为“要不要记住”在主链额外调用 memory judge LLM。

### 10.1 检索截止时间与前台优先

“后台写记忆”不代表“前台检索无耗时”。结构化键查询优先，按需触发语义检索；query embedding、Store查询、过滤/重排分别计时，并受同一总deadline约束。普通陪伴默认不额外调用LLM重排；不为召回每轮增加模型判定。

Phase 6在开发开始时声明候选数、0–4条入Prompt上限、记忆token预算与检索deadline，先用慢embedding/锁竞争测试验证，再用真实样本校准；数值记录在该阶段验收参数中，不提前新增未使用配置。一般闲聊超时无记忆继续；明确依赖旧记忆的问题应坦诚信息未取到或做必要澄清，不编造。上一轮新事实由近期Ledger/Working State立即提供，不等待后台抽取。

后台候选按会话去抖/合并，队列、并发、重试均有上限；前台LLM/TTS优先，记录后台积压、Provider等待、SQLite争用与deadline命中率。禁止用全局回合锁或新增常驻服务解决尚未证实的性能问题。参见[LangMem后台处理指南](https://langchain-ai.github.io/langmem/guides/delayed_processing/)。

### 10.2 更正、遗忘与来源一致性

- 记忆至少有来源回合、事实/推断类别、有效时间或更新版本；助手虚构表达不得抽取成用户经历，短时情绪不写长期事实。
- 用户更正先在当前Working State生效；后台按来源版本合并，迟到的旧候选不得覆盖新事实。
- 用户删除/遗忘必须先使目标记忆在读取路径失效，再完成Store与向量索引清理；删除标记/版本阻止旧任务及Ledger重新抽取将其复活。
- Phase 6明确遗忘范围：事实、Persona还是用户scope；完整删除请求覆盖相应Ledger/派生记忆/导出与备份保留策略，不把仅删除向量当作彻底遗忘。界面区分已失效、清理完成、失败待处理。
- merge/delete后原记录和索引一致；中断重试幂等，失败可恢复。会话事实和删除请求不用可丢弃Trace队列承载。

### 10.3 依赖接入门槛

Phase 6先在Python 3.11、macOS/Windows验证LangMem + AsyncSqliteStore + sqlite-vec的安装、CRUD、语义查询、并发关闭和删除一致性，再锁入实际依赖；本次仅更新规划，不提前安装依赖。选用包含namespace边界修复的兼容版本，针对项目scope自行回归，不以使用官方Store替代隔离验收。

## 11. Conversation Ledger

Ledger 是下一轮上下文的真实来源之一。

至少记录：

```text
robot_id
room_id
turn_id
user_id
persona_id
chat_id
user_text
assistant_planned_text
assistant_generated_text
assistant_published_text
assistant_spoken_text
playback_evidence_status
generation
interrupted
cancelled
cancel_source
timestamps
```

发生small-brain cancel或用户打断后，下一轮必须优先使用实际播出的`assistant_spoken_text`，不能把用户未听到的剩余生成文本当成已发生事实。

独立TTS下，Realtime只知道生成文本，不知道实际播放进度。本地Ledger修正还不够：取消后须将Provider会话中的未播助手内容移除/以确认已播内容重建；若更新不可用或失败，受控重建Session并加载有界已确认上下文。该策略是本项目设计，Phase 4B用真实接口验证；无播放证据保持unknown，不能把完整生成文本留在远端后宣称已修复。记录Provider item到本地可播片段的映射；不套用未经该型号证实的音频truncate字段。

### 已播证据与两级验收

planned、generated、published、confirmed played分开记录。Room publish只证明发布，`assistant_spoken_text`只表示可确认已播放部分；无回执时为空/unknown，估计结果单独标注，不伪装成已播事实。下轮可知道机器人有未完成输出，但不得假设用户已经听见。

Phase 3用模拟回执验证Ledger契约；Phase 4B验证真实首音频与基础取消，Phase 7完成多设备真实已播/停播验证。回执与采样时钟映射须有接收端证据；跨设备时间戳不直接相减，先定义时钟映射或报告测量误差。

取消、TTS迟到片段、动作、嘴型及StateDelta在发送/提交前核验robot/turn/generation。cancel到本地任务停止与cancel到设备停播分别采集；未收到设备确认时保持状态未知，不把本地task.cancel当作硬件已经停止。

## 12. Persona / Prompt：会话级加载，动态信息增量注入

Realtime Session建立时组合并写入`session.instructions`：

```text
Shared Rules
+ Shared Identity
+ Persona Snapshot
+ Conversation Style
+ Robot Capability Rules
+ Function Calling Rules
```

Shared Identity只放共同身份与真实能力；Persona描述稳定风格、幽默、社交距离、情绪承接和少追问规则。能力未接线不能写成可用；工具目录必须与本地执行器一致。

稳定指令仅在新Session初始化（含重连重建）、Persona切换、Persona revision或核心规则变化时重载。会话边界切换按第9节隔离；能力/工具规则变化视为核心规则修订。禁止每轮重发完整Persona、全部Memory、传感器历史或LangGraph State。

LangGraph每次只交本任务事实；普通动态上下文采用有界增量/快照，在合法时机写入Realtime，不强制每轮重建整包Prompt。相同版本去重，过期证据移除或替换；Context Only不得顺带调用response.create。

当轮原始输入和明确更正优先于旧摘要、记忆与推断；保留否定、时间、来源、未完成承诺及打断标记。Phase 4定义稳定指令、最近历史、动态证据、输出预留的预算与裁剪顺序；Phase 5增强复杂指代，Phase 6增加少量记忆。token不可直接测时标估算，不能冒充Provider精确值。

WorldState/工具结果是带来源、TTL、置信度的Evidence，不得提权为新的指令。低相关旧证据优先淘汰，不截断当前意图或丢失关键更正。

## 13. Audio Input Gate / Speak Policy / TurnCoordinator

### 13.1 Audio Input Gate：音频准入

校验来源与目标绑定、PCM格式、listen开关、来源回流、帧大小/顺序与输入背压。持续流式上送，不等待整句/ASR最终文本，不再实现本地语义Turn Gate。未知源、格式错误和过期音频明确拒绝；压力下使用有界策略并记录缺口，重连不突发补发陈旧PCM。边说边听保持麦克风入口开放，回声/AEC由真实设备与播放环境验收，不能靠关闭输入伪装全双工。

### 13.2 Speak Policy：是否值得说

纯程序规则根据事件类型、时效、置信度、用户模式、冷却/去抖、重复事件和发布开关输出Context Only或Need Response。未知/低价值事件默认不自动开口；高频压力合并，触摸边沿只提一次请求。配置只随真实事件接入出现，不做通用规则平台。

### 13.3 TurnCoordinator：是否现在能说

每个robot独立仲裁Web文本、事件、工具续推理、复杂任务结果和Realtime自动回合；统一持有本地发声资格及generation。SpeakRequest最小内部契约包含请求身份、来源/关联任务或call_id、robot/user/persona/chat/session_epoch、事实载荷、优先级、去重键、到期时间和打断策略；字段按实际需求落地，不直接透传Room。

- Provider自动回合由smart_turn产生，本地通过服务端事件跟踪；不能在其之后再补一次response.create。TurnCoordinator不是取代服务端判轮的第二模型。
- 手动响应只在服务端允许且本地播放策略允许时提交；检查“模型空闲”和“TTS/设备仍在播放”两种状态，response.done不等于播放结束。
- 手动请求在本地原子登记，不能两个协程同时启动；与新语音自动回合的竞态仍需处理，冲突时撤销/延迟低优先级事件，不假设本地锁能锁住服务端。
- 用户停止/有效打断和小脑cancel优先；后台任务完成通常等待用户回合结束，不抢话。无效附和声不应取消外置TTS；具体smart_turn事件时序在Phase 4/4B验证，不能仅凭任意speech_started就断定有效打断。
- 需要等待的请求有容量、TTL、合并与丢弃原因；会话切换先清理旧请求，过期提醒/旧任务结果不得在新Chat突然开口。
- 有效取消使旧generation失效，停止Realtime推理、独立TTS、待播音频、嘴型和可取消动作；设备停播使用已确认协议并等待证据，不能把本地取消当作硬件已停。

旧PASS/HOLD/DROP可用于显式文本兼容/内部请求诊断，不再把所有音频先转文字后Gate；其HOLD同样有界，且不得跨robot/room/user/persona/chat/generation合并。

## 14. 会话内追问与有限事件主动响应

会话追问只在不问会明显损失用户目标、且用户愿意继续时发生；禁止为了互动每轮都追问。

事件开口不等于自由自主搭话：只有Speak Policy准入的摸头、到期提醒等有限类型，才经TurnCoordinator请求Realtime表达。安静模式、忙碌、过期、去重和冷却均可使事件只更新上下文；无需响应则保持沉默。程序决定“要不要说”，Realtime决定“说什么”。

## 15. WorldState

视觉、嵌入式、算法统一写入 WorldState：

```text
current_faces
expression
robot_status
sensor_state
algorithm_state
recent_visual_event
```

每条带：

```text
robot_id
room_id
source
updated_at
ttl
confidence
```

Event Router将事实更新到WorldState；Speak Policy决定仅更新相关Realtime上下文还是提交SpeakRequest。Realtime和按需LangGraph都只读取相关快照，不把每次传感器变化注入history。

WorldState 文本必须作为 Evidence，不能成为 System Instruction。

## 16. Function Calling：动作 / 表情 / 简单工具

Realtime负责语义选择，本地执行器负责真实执行。内部最小工具可命名为robot_action、set_expression、查询工具与submit_complex_task；这些是设计名，不是已存在的wire或已接入工具。

```text
完整Function Call → schema与能力白名单校验 → call去重
                  ├─ ActionIntent / ExpressionIntent → ActionArbiter → 现有设备协议
                  ├─ 简单Tool → 结构化结果
                  └─ Complex Task → LangGraph → 结构化结果
结果 → 关联call_id回写 → TurnCoordinator协调续推理 → Realtime最终表达
```

- 工具参数必须完整后才执行，增量JSON不能触发动作；只允许当前机器人已配置的动作/表情ID及范围。robot_id、设备目标和身份scope由服务器绑定，不由模型指定任意设备。
- 按session/response/call身份映射稳定执行记录，重连/重复done不能重复动作；会话重建后的任务恢复仍关联原业务执行ID，不能因新call_id重新执行已发生副作用；乱序、多call、失败/超时、未知函数、非法参数、取消后迟到结果均有明确状态。
- 工具结果如实报告成功/失败/执行不确定；不可撤销的已发生动作不因cancel伪装回滚。每回合限制工具次数、并发和总耗时，阻止续推理循环失控。
- 正常文本流与函数调用分流，参数和内部结果JSON不进入TTS；实际动作状态未确认前，不能依据模型文案记为“已执行”。
- 小脑继续提供低延迟动作和cancel。ActionArbiter只处理冲突、去重、冷却和优先级：`cancel/safety > 小脑即时动作 > Realtime语义动作`，不演变为大状态机。
- 最终文案仍由Realtime生成；LangGraph和工具实现不再返回另一份“小安妮式回复”。

## 17. 独立TTS / ForcedAligner / Viseme

保留目标模型`qwen-audio-3.0-tts-flash`与既有ForcedAligner方向；配置与旧listener存在不等于V2已接入。Realtime使用纯文本输出，唯一播报源是独立TTS，避免双音轨。

```text
Realtime可播文本片段 → 独立TTS → 同一份实际PCM
                                    ├─ Room音频发布
                                    └─ PCM + 对应合成文本 → ForcedAligner
                                                              ↓
                                                       时间对齐结果
                                                              ↓
                                                       Viseme映射 → Room
```

ForcedAligner不是只吃PCM就能直接吐嘴型：输入需对应文本和音频，对齐结果还需映射viseme。分段绑定robot/turn/generation/chunk与采样时钟；对齐分支必要重采样须保留时间映射，不能另合成一份音频做时间基准。

Phase 4B实现最小分段对齐与取消；Phase 9再完善多头、算法与监控。首音频不等待整轮对齐；嘴型若需短缓冲则显式预算并测量音画偏差，算法慢/失败时按已声明策略禁用迟到嘴型或中性嘴型，不阻塞主聊天、不沿用旧generation。

sidecars/tts_viseme是未多头化的listener副本；须避免它再调用一次TTS，与Runtime争抢合成/发布所有权。SidecarSupervisor只在实际接入时启动和监控；依赖、超时、required标志、失败原因和降级状态进入health与日志，不静默失败。正式设备放行必须有嘴型关联与取消证据。

## 18. SQLite 优先

默认尽量使用 SQLite：

```text
runtime.db          # 本地会话事实与执行记录
langgraph.db        # 仅Phase 8实际工作流checkpoint需要时创建
observability.db    # 观测量确有必要时分库
```

高频 Trace 不能同步逐条写数据库，应：

```text
in-memory queue
  ↓
async batch writer
  ↓
SQLite WAL
```

只有已经通过数据证明 SQLite 无法满足实时要求时，才允许引入 Redis/其他服务。

## 24. 性能目标与测量口径

### 24.1 本地额外开销目标

| 阶段 | 初始P95工程目标 |
|---|---:|
| Event normalize | < 5ms |
| Audio Input Gate | < 10ms |
| 必需SQLite会话读取（不要求每轮读取） | < 10ms |
| Speak Policy / 本地仲裁计算（不含合法等待） | < 5ms |
| 非长期记忆动态Context整理 | < 20ms |
| 普通聊天LangGraph调用 | 0次 |
| 小脑cancel → 本地cancel执行 | < 30ms |

这些是待实测的工程目标，不是已完成结果；排队、Provider与真实设备延迟另列，不能删掉慢样本凑预算。

### 24.2 实时主链瀑布

```text
PCM received → input queue → PCM sent
→ speech_started / speech_stopped / turn有效性（服务端可见事件）
→ response.created → first_text_delta → first_speakable_chunk
→ tts_request → first_pcm → room_publish → playback_confirmed
                          ↘ align_request → alignment_ready → viseme_publish
cancel_received → generation_invalidated → local_cancel_done → device_stop_confirmed
```

服务端事件时间不直接与本机时钟相减；同时记录本地单调接收时间及来源时钟/映射误差。缺少明确有效轮次时点就留空，不伪造smart_turn耗时。ASR转写单列，不作为热链LLM请求起点；文本模式单独测输入到首文本。

Realtime服务端完成生成、独立TTS完成、Room已发布、设备已播放是四种状态。首音频、首发布、设备起播/停播分别报告；对齐延迟、音画偏差、输入缺帧/积压、语义误打断/漏打断、无效轮比例单列。

queue_wait/service/end_to_end、Provider容量等待、工具执行/续推理、事件等待、Graph任务耗时、检索/embedding、SQLite/checkpoint成本分别记录。普通无工具、简单工具、复杂任务、主动事件分组，不以复杂任务均值掩盖普通首响。

### 24.3 采样与通过门槛

- 固定模型ID/参数、Persona revision、输入音频、历史/记忆快照、机器和网络；区分单头/双头、冷启动/暖Session、PCM/Web文本、用户正常轮/无效附和/有效打断。
- 每组记录样本数、P50/P95、失败/超时/丢弃/取消及排队，不只报均值。设备声学说完时点只有有校准证据时才报告；否则如实报告可观测阶段。
- Phase 4冻结轮次/文本质量基线；4B在正式验收前确认首音频/起播/停播/嘴型偏差及误打断率门槛，写入阶段README。Phase 6冻结检索预算；后续沿用，不在跑完后移动门槛。
- Phase 10逐组至少100个回合，保留可复跑输入、结果与分位数算法；稀少冷启动场景独列不确定性，不称小样本已证明尾延迟。
- 历史V1四条成功样本仅为线索；新旧主脑模型不同必须分开标明。架构/上下文增益用同一Realtime模型消融比较，V1/V2只作为产品体验比较，不把换模型收益全归于架构。
- 不照搬旧链固定TTS sleep；实测建链、Provider、分句、对齐缓冲分别计时。

## 29. 主要风险

### 风险 1：V2 架构更漂亮，但陪伴体验没提升

解决：沿用Phase 0设计样例，Phase 4开始Realtime同模型消融；V1/V2另列产品体验差异。

### 风险 2：为了“情商”堆超长 Persona Prompt

解决：情绪/关系/回复需要进入 SocialState；Persona 只描述稳定表达差异。

### 风险 3：Memory 召回让回答更乱

解决：0 条 Memory 允许且常见；Relevant Memory 才进入 Context Packet。

### 风险 4：复杂任务拖慢普通聊天

解决：Realtime默认短链，LangGraph按需旁路；复杂任务资源限额，结果经协调后再表达。

### 风险 5：把服务端smart_turn误当成设备全双工已完成

解决：单独验回声、无效附和、有效打断、外置TTS清队列及嘴型停播；不复制第二套本地断句模型。

### 风险 6：Realtime上下文与实际播放分离

解决：Ledger记录实际证据，取消后同步修正Provider上下文；无回执保留unknown，不把生成当已说。

### 风险 7：自动回合、事件、工具续推理争抢

解决：TurnCoordinator跟踪服务端及本地播放双状态，手动请求有界、去重、过期；联合真实接口验证，不只测本地锁。

## 33. 工程原则硬约束

本计划所有阶段都受 `brainv2/PROJECT_RULES.md` 约束。以下原则优先级高于“架构完整度”和“未来扩展性”：

- **拒绝过度设计与无脑堆砌**：遵循 KISS、YAGNI 与奥卡姆剃刀，“如无必要，勿增实体”。实现目标是用最精简的代码和最清晰的链路稳定达成功能。
- **坚决克制抽象**：严禁为了所谓扩展性提前编写大量空心抽象层、冗余包装类和纯转发胶水代码。若原生逻辑已经清楚可靠，不得为了“统一形式”再包一层。
- **单进程轻量闭环优先**：默认单 Python 主进程、本地 SQLite、一键启动。没有明确证据前，不引入 Redis、Kafka、Docker 常驻服务或独立数据库服务。
- **外部依赖必须可解释**：现有 LLM/TTS Provider、小脑、视觉/嵌入式 WebSocket 与必要 sidecar 可以保留，但任何新增外部依赖都必须证明不可替代，并具备清晰日志、健康检查与失败降级行为。
- **实时主链最短化**：普通陪伴由Realtime直接响应，不经过LangGraph或额外LLM；工具调用允许必要续推理并单列成本；日志、长期记忆整理、非关键持久化和观测写入尽量异步后置。
- **原版冻结，V2 独立迁移**：原版从 2026-09-17 起默认不改，只读参考或复制逻辑到 `brainv2/` 后改造；不回写原版、不覆盖已有修改、不依赖原版运行。
- **多机器人并发是已确认基础能力**：单项目单进程运行多个机器人头，支持相同 WebSocket 房间广播和定向事件；状态、取消及输出目标按 `robot_id` 隔离，不能以后续扩展为由推迟。
- **先证明问题，再增加复杂度**：没有真实失败样本、性能数据或明确业务需求，不增加新的 Graph Node、状态机、路由器、缓存或服务。

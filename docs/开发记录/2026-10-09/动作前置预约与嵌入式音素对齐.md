# 动作前置预约与嵌入式音素对齐

## 问题与目标

用户要求不再等云端 ForcedAligner 对齐后才发动作；设备持续订阅同一 Room 的 `reb_main` 和 `reb_sam`，由设备自己根据嘴型流的真实声学索引和实际扬声器播放采样点执行。不得发送不带目标字位置的“空预约”。

旧轮 `0cb6722c...` 的真实声学首字为 560ms，侧车首嘴型发生于首 PCM 后 951ms，存在按字发送消息太晚的确定风险；没有设备采样游标回执，不能宣称已赶上。

## 变更

- `SpeechOutput.generated_text` 捕获 Realtime 的原始流式回复，身份切换时清空；`response.text.delta` 送入语音通道后，直接唤醒 ActionCoordinator 检查是否出现完整目标词。
- 对带 `anchor_text` 的动作，只在实际生成文本中定位 Unicode 原文索引，并异步发出一条 `action_prepare`。没有索引就只在 Runtime 内部等待；不再等待 `viseme.aligned`、`start_sample`、PCM 首帧或硬件回执。
- 新包使用 `timing_mode=phoneme_anchor_v1`、`conversation_id`、`stream_epoch`、`action_id`、`script_id`、`anchor_text`、`anchor_occurrence`、`anchor_char_index`，附已生成文本中锚点前后最多六个码点；**没有 `at_sample`、`offset_ms`**。
- 普通未带锚点的脚本仍保持旧 `action_trigger` 首 PCM 协议；五种夸张表情依旧强制明确 `anchor_text`。两种消息不重复下发。
- SQLite 继续使用原动作表，新增等待状态 `awaiting_text_anchor` 与过期状态 `expired_no_text_anchor`；兼容恢复历史 `awaiting_word_alignment`，不把旧进程预约遗漏在待处理列表。
- 保留撤销、幂等、冷却、跨会话与双机器人隔离，设备端必须对照真实 `reb_sam` 和本地播放游标执行、超时/迟到/停止时丢弃；设备代码不在本仓库，尚未完成物理验收。

## 证据与风险

- 2026-10-09 云端软件检查：带锚点动作在没有音素、没有 PCM 时就能提前发出带确定字索引的消息；同词重复按指定出现次数匹配；无目标文本不发包；不同 Room 不串路；取消、切流、关闭、网络不确定均不冒认硬件完成。测试只证明模拟 Room 的发布时序，**不证明设备执行成功**。
- 即使提前预约，首字 ForcedAligner 的计算仍可能比音频播放落后。设备必须缓存动作/音素的乱序消息，以 `played_sample_count` 触发或 `late_policy=drop` 丢弃，不允许以服务器时间、抵达时间或字符等分推定音素时刻。
- 三个联调时间证据：云端 `action_prepare.ts` 与发布结果；`reb_sam` 的 `mouth_script` 实际到达、`start_sample`；嵌入式实际收包时的 `played_sample_count` 和动作触发或丢弃回执。接收端证据缺失时不能标“字级同步已通过”。
- 部署需要同时更新嵌入式 `action_prepare` 处理；仅升级云端，旧设备应忽略新消息，**五个新式字级动作不会被旧设备执行**。现场 Runtime 不自动重启；已有工作区含其它项目并行修改，不整体提交。

# 性格切换修复、对话可调配置与决策模型接入

> 2026-10-14。用户反馈“换一个性格 → 你选一个 → 那你换吧”切换不过去，并要求补齐可通过对话调整的配置，同时评估决策模型、未唤醒时的 ASR、TTS 情绪控制、非 LLM 动作触发和视觉 JSON 格式。本文记录修复、真实云端评测，以及用户确认后实施的决策模型接入（判断对谁说话、自动表情动作）、对话后旁听、被丢弃点名提问的补发和唤醒词近音规整。TTS 情绪和视觉 JSON 仍是方案，未实施。

## 1. 性格切换修复（已实施）

**根因**：切换校验只看**当前这句话**里有没有“换成××性格”或性格名。用户说“你选一个”“那你换吧”属于把选择权交给机器人，被判为没有明确请求而拒绝；模型拿到拒绝后只能说“系统不让换”。另外，请求的正好是当前性格时，同样返回拒绝，而不是“本来就是它”。

**修复**：

- 机器人问过“要哪种”或刚切换过之后的 120 秒内，用户说“你选/你挑/随便/那你换吧/就它/好”时，接受模型从选项中挑的那个；否定（“别换”“不要”）和不在选项里的风格仍然拒绝。
- 用户只说“换个性格”、没有点名时，允许模型挑一个与当前不同的风格，也可以选择先问。
- 请求的正好是当前风格时，直接返回 `already_selected`，不需要明确请求。
- 拒绝结果明确要求模型不要换个名字重复调用，而是问一句。

**真实云端复现（3.1-plus，从怨种搭档起步）**：“换一个性格。”→“你选一个。”→“那你换吧。”→“换个性格吧。”→“你挑一个呗。”五步每步只调用一次工具，最终依次切到自然陪伴、活泼俏皮、机灵互怼、温柔知心，没有拒绝和反复重试。

## 2. 对话可调配置（新增 `update_chat_preference`，已实施）

取值都是封闭枚举（城市除外），按 Chat 保存在 `conversation_social_state`；当前这句话必须真的提到该设置才会生效，外部事件不能修改。

| 设置 | 可选值 | 例句 | 生效方式 |
| --- | --- | --- | --- |
| 追问频率 `question_pressure` | active / normal / low / none | “别老追问我” | 重建性格指令 |
| 幽默程度 `humor_level` | none / low / normal / high | “正经一点” | 交谈提示 |
| 回答长短 `reply_length` | short / normal / detailed | “以后回答简短一点” | 重建性格指令 |
| 语速 `speech_rate` | slower / normal / faster | “说慢一点” | TTS rate 0.92 / 1.10 |
| 音量 `speech_volume` | quieter / normal / louder | “声音大一点” | TTS volume 42 / 58（合成层只能小幅调整） |
| 自发表情动作 `spontaneous_motions` | on / off | “别老做表情动作了” | 指令 + 运行时拦截未被明确要求的动作 |
| 默认城市 `home_city` | 城市名 | “我住在上海，以后查天气默认上海” | 不说城市时查它 |

已有的对话可调项：性格风格、TTS 音色（`select_voice`）、语言/方言偏好（设置/清除）、本轮语气（`select_reply_style`）、休眠（`enter_sleep`）、提醒、记忆遗忘/更正。

真实云端验证：“以后回答简短一点”“说慢一点”“别老做表情动作了”“我住在上海……”均调用成功；关闭自发动作后，“我中了五百万”触发的惊讶表情被拦截，回复没有提及失败；设置默认城市后，“今天天气怎么样”返回了上海的天气。

## 3. 决策模型评测（`decision-model-preview`）

接口 `POST https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1/systemone`，三种题型为 `choice`（多选一）、`noul`（是否题，返回“是”的概率）、`score`（有序量表）。不生成文字，目前限时免费，RPM 1200。

| 评测 | 样本 | 结果 |
| --- | --- | --- |
| “这句话说给谁听”（choice：机器人/他人/自言自语或媒体/不确定） | 20 句，10 句对机器人说、10 句不是 | 18/20 正确；对机器人说的 10/10 都识别出来，误判 2 句（谈论机器人的那句、机器人答完后夫妻对话的那句） |
| “机器人该不该回应”（noul） | 同上 20 句 | 不可用：多数非机器人语句也给出 0.7 以上的概率 |
| 选表情动作（choice，7 个选项含 none） | 8 句 | 8/8 正确，难过时选 none |
| TTS 情绪与强度（choice + score） | 8 句 | 合理：中奖为兴奋/明显，挨批评为低落安慰/轻微 |
| 延迟 | 30 次 | 服务端 P50 约 41～47ms；客户端 P50 约 276～287ms，P95 约 296～314ms |

结论：问题必须写成带标准的选项题，宽泛的是非题不可用。客户端约 0.28 秒，主要是网关和网络开销，接入时不能串在首响主链上，需要并行或只在拿不准的场景调用。


## 4. 判断“是不是对机器人说的”（已实施）

用户确认接入。地址只放根 `.env` 的 `ANNIE_DECISION_URL`（含业务空间），未配置时整套不启用；`ANNIE_ADDRESSEE_ENABLED` 默认开。

- **何时调用**：无唤醒模式下每句识别终稿都问；唤醒模式只在追问窗口里问。点名“小安妮/安妮”的句子走快路径，不调用。
- **不推迟首响**：Realtime 照常生成回复，但事件先暂存；判定为对机器人说，就放行暂存内容；判定为不是，就撤回暂存回复，删掉这句用户消息和回复，唤醒窗口按无效语音处理，并发布 `transcript.ambient`（`reason=not_addressed`）。
- **只用选项，不用置信度**：真实多人对话里判对的句子置信度低到 0.18，所以只看选了哪项。`unclear` 只在机器人 15 秒内刚问过问题时算作对它说；决策模型超时或出错一律放行（宁可多答，不漏答）。
- **输入**：最近 6 行对话（含旁人说的话）、当前句、画面描述、距机器人上一句的秒数和上一句是否在提问。
- **延迟**：HTTP 长连接保持 300 秒（默认 5 秒会让每次都重新握手），用户开始说话时预热（60 秒内最多一次）。

**真实云端 A/B（3.0-flash，10 句：5 句对机器人、5 句旁人对话/打电话/笑声）**：

| 配置 | 正确 | 误回复 | 漏回复 | 决策耗时 |
| --- | --- | --- | --- | --- |
| 无判断（原行为） | 5/10 | 4 | 1 | — |
| 接入决策模型 | 10/10 | 0 | 0 | 343～470ms |

## 5. 表情动作改为“状态驱动 + 决策模型”（已实施）

用户同意放宽“动作经 Function Calling”。配置决策模型且 `ANNIE_AUTO_EXPRESSION_ENABLED`（默认开）时：

- 大模型不再拿到 `perform_action` / `set_expression` / `preview_action`，人格指令改为“动作与表情由系统根据对话自动执行”，消除带动作回合多出的 0.6～1 秒工具往返。
- **用户点名的动作**（点头、摇头、看左右、眨眼，以及“做个害羞的表情”这类）：运行时直接识别，不调模型、不受冷却限制；普通动作随第一段音频触发，表情锚定到回复里的词。“别/不要/停”开头的否定不触发。
- **“随便做个动作”**：决策模型在全部已启用动作里选一个（没有“不做”选项）。
- **自发表情**：回复出现完整句子或满 14 字后，决策模型在 none / 惊讶 / 坏笑 / 得意 / 怀疑 / 害羞中选，置信度 ≥0.55 才做；锚定到回复后面的词，给 0.3 秒的决策留出时间；20 秒冷却；用户关闭“自发表情动作”后不做。
- **状态信号**：`reb_voice` 的 `voice.interaction` 新增 `turn.started`（开始思考）和 `tts.first_published`（开始说话），`data.interaction_state` 为 `listening / thinking / speaking / idle`，供设备自己做听、想、说时的微动作。**设备端是否使用该字段未验证。**

**真实云端（3.1-plus，9 句）**：中奖→惊讶、被夸→害羞、外星人→怀疑、放错糖→坏笑，难过和科普选 none；“点个头”随首段音频 0ms 触发；“做个害羞的表情”锚定到词；“随便做个动作”选了点头。9/9 行为正确。遗留：3.1-plus 偶尔误调 `select_persona_style`（约 0.8 秒，运行时拒绝，不会真的换性格）。

## 6. 对话后旁听（已实施，默认关闭）

用户让我评估后自定。选择：

| 方面 | 决定 | 理由 |
| --- | --- | --- |
| 识别 | 云端 qwen3-asr-flash-realtime，复用现有 `AcousticSidecar` | 本地 sherpa-onnx 中文流式准确率不够，旁听内容要能被问起 |
| 时机 | 仅唤醒模式；机器人回复完成后 3 分钟窗口；能量门 -45 dBFS，有声音才上传 | 全天转写家庭对话既费钱又涉隐私；有用的上下文集中在刚聊完的几分钟 |
| 保留 | 只在内存，最多 20 行、180 秒；休眠指令、会话切换、停止时清空；不入库、不进长期记忆 | 最小保留 |
| 使用 | 决策模型判断对谁说话时作为上下文；大模型只能通过 `recall_overheard` 工具按需读取 | 见下方实测 |

开关 `ANNIE_AMBIENT_LISTEN_ENABLED`，代码默认关闭。

**实测发现并修复的问题**：

1. 侧车按需建连约需数百毫秒，`max_lag_ms=500` 让首帧在连上前就过期（`lag_exceeded`，发送 0 帧）。旁听不追求低延迟，改为允许积压 3 秒、队列 150 帧。
2. 能量门拖尾 0.5 秒短于 ASR 服务端 VAD 的 0.8 秒静音判停，句子一直等不到终稿。拖尾改为 1.2 秒。
3. 起初把旁听内容写进 session 指令，机器人能答出“你们刚才说周末要去爬山，还打算叫上小李”，但措辞会变成“刚才旁边的人在说”，而且旁听内容每次都无条件送进大模型。改为 `recall_overheard` 工具按需读取：只有用户问起时才送，指令不随旁听变化；工具结果要求说“你们刚才说……”。代价是这类问题多一次约 0.8 秒的工具往返。

**工具选择实测（3.1-plus，文字输入以排除判停干扰，两轮一致 6/7）**：

| 用户说 | 预期 | 结果 |
| --- | --- | --- |
| 我们刚才说周末要去干嘛？ | 查 | 查了，“你们刚才说周末去爬山，还打算叫上小李一起去香山” |
| 刚才说的那个地方你去过吗？ | 查 | 查了，“你们刚才说要去香山爬山……我没去过” |
| 你觉得叫上他合适吗？ | 查 | 没查，反问“得看叫谁呀”（不瞎猜，可接受） |
| 你叫什么名字 / 讲个冷笑话 / 今天星期几 | 不查 | 都没查 |
| 香山离这儿远吗？ | 都可以 | 没查，直接回答 |

语音全链路（假唤醒 + 真实云端 ASR/Realtime/决策模型）也跑通过：旁人两句均被转写，唤醒后调用工具答对。

## 7. 被 smart_turn 丢弃的点名提问自动补发（已实施，用户确认）

**现象**：Qwen smart_turn 会把一部分点名提问判为 `turn_invalid`，不回复。识别是完整的，含“小安妮”；“我们刚才说……”这类像人和人说话的句子最容易被丢，“今天天气怎么样”也出现过。关闭旁听、两个模型、ACTIVE 状态下都会出现，与旁听无关；原运行时一直信任 `turn_invalid`。

**云端行为实测（原始 WebSocket）**：判无效后约 0.8 秒，云端仍推送同一条语音的 `conversation.item.input_audio_transcription.completed`，文字完整；这条语音**不留在**云端对话里——只发 `response.create` 会回答上一轮的内容，`conversation.item.delete` 会返回 “Cannot find item” 的 error 事件（运行时收到 error 会断开重连）。

**做法**：

- 判无效时，若这句是本地 KWS 刚确认唤醒后的第一句，或识别草稿里点了名，就标记为可补发；唤醒状态保留候选和识别宽限期，不让窗口在终稿到达前过期。
- 终稿到达后再等 0.6 秒安静。期间用户又开口，说明云端是在句中停顿处切断的（实测见过“小安妮，我们”被单独判无效而用户还在说），就取消补发，把这半句并到下一句前面；下一句若被正常回复则不再补发，若也被判无效则用合并后的整句补发。
- 补发：正在播放或生成的旧回复按插话打断；按正常语音轮次建轮、显示和入库；把终稿作为文字消息加入对话，再 `response.create`。发布 `turn.recovered`，日志 `turn_recovered robot=… turn=… chars=…`。
- 不补发：没点名也不是唤醒后第一句的、只有称呼或附和的、“退下”类休眠指令（休眠指令照常生效，被判无效也能让机器人休眠）。
- 判过无效的语音项记入 `_dropped_audio_items`，任何路径都不再对它发删除请求。

**真实云端（3.1-plus，假唤醒 + 合成语音）**：

| 句子 | 结果 | 说完到首字 |
| --- | --- | --- |
| 小安妮，我们刚才说周末要去干嘛？（4 次） | 4 次都被判无效，4 次补发成功 | 3.6～4.1 秒（云端约 2.5 秒才判无效） |
| 小爱你，今天天气怎么样？ | 被判无效，补发成功 | 3.6 秒 |
| 小安妮，我们……嗯……刚才说周末要去干嘛？（带停顿，6 次） | 2 次补发、4 次云端正常回复，均答对 | — |
| 你叫什么名字 / 讲个冷笑话 / 香山离这儿远吗 | 正常回复，未触发补发 | 1.0～1.8 秒 |

补发的回复明显偏慢，主要耗在云端判定无效的约 2.5 秒上，但比不回答好。带停顿的句子在本轮修复前跑过 2 次，均没有转写也没有回复，之后 6 次未复现，原因未查明。句中切断后合并的路径由单元测试覆盖，实测中未遇到。合成语音与真人的判无效比例可能不同，需统一实测时用 `turn_invalid` / `turn_recovered` 日志统计。

## 8. 一语即达时唤醒词被识别成“小爱你”（已实施）

**现象**：本地 KWS 已确认“小安妮”，但 Qwen 识别写成“小爱你，今天天气怎么样”“小爱，你今天天气怎么样”“小阿妮，……”，页面、对话历史和记忆里都是错的名字。之前只在提示词里告诉大模型这些近音是在叫它，文字本身没改。

**业界做法**：唤醒词是控制信号，由本地 KWS 判定，不以云端识别出的文字为准。常见三种处理：一是按 KWS 给出的唤醒词结束位置裁掉音频或文字，展示和理解的都只有唤醒词后面的请求；二是把句首识别错的称呼规整成标准名字；三是给识别加热词偏置。本项目的 sherpa KWS 不给唤醒词结束的采样点，预录音频为了不丢问题开头会带上唤醒词，所以无法按时间裁剪；Qwen Realtime 是否支持热词，公开协议里没有确认，不猜字段。

**做法**：在运行时把句首称呼规整为“小安妮”，覆盖识别预览、终稿、轮次文字、历史和记忆；云端自己保存的那份转写不改，由原有提示词兜底。

- 有 KWS 证据时（唤醒后的第一句），句首的“小/晓/筱 + 安/爱/艾/阿 + 妮/尼/你/呢……”都算称呼，包括不带标点的“小爱你今天……”、停顿落在中间的“小爱，你今天……”（改成“小安妮，今天……”）和丢了最后一个字的“小爱，今天……”；“你”后面跟“好/们”时保留，因为“小安你好”可能是“小安妮 + 你好”。
- 没有 KWS 证据时（追问窗口、无唤醒模式），只改实测出现过的近音，而且后面必须有停顿（如“小爱你，……”）；“小爱，你吃了吗”“我小爱你”不改。
- 键盘输入的文字从不改写。每次规整发布 `wakeword.call_normalized`（只含原称呼 3～4 个字），计数见快照 `wake_calls_normalized`。

**实测**：合成“小爱你，今天天气怎么样”，云端识别为“小爱，你今天天气怎么样”或“小爱你今天天气怎么样”，页面显示为“小安妮，今天天气怎么样”或“小安妮今天天气怎么样”。

  - 每个人：`track_id`、`subject_id`、`facing_robot`、`gaze_on_robot`、`mouth_moving`（0～1 概率）、`distance_m`、`bearing_deg`（机器人正前方为 0，左负右正），以及只在用户同意人脸登记后才填的 `known_person`；

  接入后可作为“对谁说话”的输入（面向机器人、嘴在动的人是说话人）。

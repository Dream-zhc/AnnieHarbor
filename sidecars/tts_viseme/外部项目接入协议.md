# 独立嘴型服务：其他项目接入与心跳协议

本文按当前 `qwen_stream_room_g2pw.py` / `service_win.ps1` 的**已实现行为**整理。其他项目不必引入旧主项目的 Python 包；只需按房间协议发送真实 TTS 和（可选）LLM 流式文本，订阅嘴型及健康消息。本文件随整个 `tts_viseme/` 目录搬迁。

## 1. 部署边界与房间

```text
项目 A / 机器人播放端 ──┬── reb_tts：实际待播放的 TTS PCM / 打断
                      └── reb_sam：llm_delta / brain_health / viseme_control
                                                   │
                                             WebSocket 房间服务
                                                   │
独立 Windows tts_viseme ── 订阅 reb_tts + reb_sam ───┤
                         └── reb_sam：mouth_script / mouth_sync_summary / viseme_health
```

当前默认地址（示例，改成实际房间服务 IP）：

```text
ws://192.168.1.47:8090/robot/room/reb_sam
ws://192.168.1.47:8090/robot/room/reb_tts
```

Windows 独立目录内执行 `start_win.bat 192.168.1.47:8090`；也可以设置 `TTS_VISEME_SAM_WS_URL` 和 `TTS_VISEME_TTS_WS_URL` 后直接执行 `start_win.bat`。**传入命令行地址优先于环境变量**。服务向每个房间发 `{"type":"SUBSCRIBE","data":{"types":["*"]}}`；日志 `connected + subscribed` 表示已发送订阅请求，**不是房间服务器的独立 ACK**。两个 WebSocket 各自重连。

主项目的 TTS、播放器及嘴型服务应指向同一套房间；不要使用指向各自本机的 `127.0.0.1` 跨机器连接。嘴型服务**不合成 TTS、不播放 PCM、不要求本地 HTTP 健康端点**，关闭主项目不应关闭嘴型进程；关闭独立服务窗口会终止服务。

## 2. 外部项目发送什么

### `reb_sam`：流式正文（可选，但利于提前 G2P）

```json
{"type":"llm_delta","sender":"project_a","conversation_id":"project-a-turn-001","turn_id":"project-a-tts-001","seq":1,"text":"你好","final":false,"ts":1780000000000}
{"type":"llm_delta","sender":"project_a","conversation_id":"project-a-turn-001","turn_id":"project-a-tts-001","seq":2,"text":"","final":true,"ts":1780000000100}
```

`conversation_id` 标识一轮播放会话，`turn_id` 标识对应的 TTS 段/流；保持两种房间消息中的 ID 对应，同一会话 `seq` 递增。`llm_delta` 只用于提前缓存，**实际发声文本以 `reb_tts.data.text` 为准**；只发 LLM 文本而没有真实 PCM，不能生成可信声学嘴型。主项目当前使用的 `sender=robot_brain` 并不是服务的强制校验字段，外部项目可设置自己的 `sender`。

### `reb_tts`：真实 PCM（必需）

```json
{
  "type":"tts",
  "data":{
    "audio":"<真实 pcm_s16le 字节的 base64>",
    "format":"pcm_s16le",
    "sample_rate":24000,
    "channels":1,
    "text":"你好",
    "conversation_id":"project-a-turn-001",
    "turn_id":"project-a-tts-001",
    "seq":1,
    "stream_epoch":1,
    "final":false
  }
}
```

每块 PCM 按实际播放顺序发送，使用真实采样率/声道（上例 24000 仅示例；服务也支持 22050 等）。`audio` 是 **JSON 中 `data.audio` 的 base64 字符串**，不是原始二进制 WebSocket 帧。一个流结尾发送 `data.final=true`；可以是携带最后 PCM 的帧，也可以是没有 `audio` 的最终帧。`data.text` 要与本段真实 TTS 对应；不要把未播报的 LLM 草稿当成发音文本。`reb_sam` / `reb_tts` 的 `seq` 是各自的序号，**不要求两者相等**。

打断 / 清空时，及时发送下列已识别的任一控制：

```json
{"type":"tts.playback.clear","data":{"conversation_id":"project-a-turn-001","stream_epoch":2}}
```

或含 `"data":{"stop":true,"conversation_id":"project-a-turn-001"}` 的 TTS 控制。相同会话的 `stream_epoch` 变化也会触发旧声学时间轴重置。尽量始终带 `conversation_id`，避免空 ID 导致当前状态被整体清空；**服务不会代替播放器停止真实扬声器**。

### `reb_sam`：可选开关

```json
{"type":"viseme_control","sender":"project_a","enabled":true,"ts":1780000000000}
```

`enabled=false` 会让当前服务停止产出口型并清空待发事件。这是**服务全局开关**，目前没有按项目隔离；其他项目共享同一个服务/房间时不要各自随意发送关停消息。

## 3. 嘴型服务输出什么

### `reb_sam`：`mouth_script`（逐音节）

```json
{
  "type":"mouth_script","sender":"stream_room_v7","initiator":"tts_viseme",
  "conversation_id":"project-a-turn-001","turn_id":"project-a-tts-001",
  "stream_id":"tts-viseme-v7-project-a","seq":1,
  "char":"你","pinyin":"ni3","viseme":"i","script_id":4,
  "sample_rate":24000,"at_sample":2400,"start_sample":2400,"end_sample":4800,
  "at_ms":100.0,"duration_ms":100.0,
  "timing_source":"qwen3_forced_aligner_online","ts":1780000000500
}
```

上例是**字段示意，不是一次实际对齐测量或保证的时间戳**。`script_id` 当前映射：`a=1`、`o=2`、`e=3`、`i=4`、`u=5`、`ü=6`。机器人或独立播放器应依据自身**同一条 PCM 播放流**的 `played_sample_count >= start_sample` 触发；不要用接收时的墙钟、`ts` 或累计 `duration_ms` 再造第二套时钟。`at_sample` 是起始样本别名；`end_sample` 给出音节结束边界。

同一 `stream_id + seq` 可在**尚未发出**时被更好的在线/最终对齐替换，已发出的过去时间轴不得回改。打断/断线后废弃过期嘴型，不追发旧事件。服务只接受 `qwen3_forced_aligner*` 的权威时间结果发布，G2PW 只负责读音和嘴型类别；静音不能伪造为前一个字的持续时间。整段完成另有 `mouth_sync_summary` 用于观测声学对齐情况，**不是播放 ACK**。详细字段见同目录 `PROTOCOL.md`。

## 4. 双向心跳与离线判定

两者在 `reb_sam` 广播 JSON：

```json
{"type":"brain_health","sender":"project_a","status":"ready","ts":1780000000000}
```

```json
{
  "type":"viseme_health","status":"ready","pid":1234,
  "sam_connected":true,"tts_connected":true,
  "sam_subscribed":true,"tts_subscribed":true,
  "aligner_backend":"qwen_asr","brain_heartbeat_age_ms":1200,
  "mouth_enqueued":10,"mouth_send_completed":10,"mouth_dropped":0,
  "reason":null,"ts":1780000002000
}
```

| 谁发送 | 现有周期 | 谁接收 / 现有作用 |
| --- | --- | --- |
| 外部主项目 `brain_health` | 参考当前实现：约 2 秒，当前主项目在发送队列空闲时触发，持续繁忙可能延后 | Windows 记录最近一次收到主项目心跳的**本机单调时间**，在 `viseme_health.brain_heartbeat_age_ms` 中报告；**目前不因此停止嘴型、也没有按 `sender` 区分不同项目的独立故障判断** |
| Windows `viseme_health` | 约每 2 秒（`reb_sam` 已连通后） | 其他项目按**自己的收到时刻**判断是否新鲜；当前主项目大于 5 秒判断心跳过期，初次等待约 20 秒后判断缺失，网页顶部约每 2 秒刷新 |

外部项目接入可采用如下状态机（其中 5 秒/20 秒是**当前主项目的展示阈值**，并非房间服务保证）：

```text
口型功能显式关闭                     → 关闭（不是服务离线）
未收到 viseme_health 且启动 <20 秒   → 等待心跳
从未收到心跳且等待超过 20 秒        → 离线
最近心跳距本机接收时间 >5 秒        → 离线
心跳新鲜但双房间未 ready/connected  → 通信异常
心跳新鲜且 status=ready、双房间已连 → 在线
```

**不要用 Windows 传来的 `ts` 直接减 Mac/其他主机时间**；机器时钟可能不同。`mouth_script` 或历史对话存在并不能证明嘴型进程在线。`mouth_send_completed` 只表示嘴型服务的 WebSocket `send()` 返回，**不等于房间已向机器人交付、扬声器已播放、舵机已执行**。要确认物理闭环，需要机器人另报播放/执行回执，目前这些回执不属于此服务的健康协议。

## 5. 断线、重启与多项目同时接入的边界

- 两个房间各自自动重连，最初等待约 `0.5s`，上限 `5s`（可设置 `TTS_VISEME_RECONNECT_MIN_SEC` / `TTS_VISEME_RECONNECT_MAX_SEC`）。服务启动脚本在 Python **非零退出**后 5 秒重试；关闭窗口、正常停止不会由其他项目拉起。
- 断线/打断时清空未发送嘴型，**不会在重连时补发过去的音节**。外部项目应继续新 PCM/新会话，不应重放过期音频。
- **现已支持同一进程并发接入恰好两组独立房间 A/B，仍只加载一个 ForcedAligner 和一个 G2PW 转换器。** 每组有自己的 `VisemeEngine`、`_active_cid`、PCM、`viseme_control`、心跳接收时间、发包队列、`MouthSendPacer` 和两个重连 WebSocket；A 打断/断线不能清空 B。唯一共享的模型推理采用 FIFO **串行**调用，不承诺同时发音时零排队。
- **不能把两个项目塞进相同房间**来实现隔离。A/B 的四条完整 WS URL 必须两两不同；每组收到自己房间的事件，返回自己对应的 `reb_sam`。共享单实例监听端口 `37659` 仍有效，**不要同时启动第二个嘴型进程**。
- 当前能力是 A（+可选 B）再加若干**附加房间**（默认 `roomv2,roomv3`，见下文），不是多人同房间的复用层；每组内仍一次一个活跃 TTS 会话。音频/嘴型重放及机器人硬件 ACK 仍需要原有播放端负责。
- 同一项目迁到新目录，不必修改 Python 代码路径；在新 Windows 重建 `.venv`，复制 `G2PWModel/` 和 `models/forced_aligner/` 真实模型文件。新项目只要使用同一房间协议，不需要引用这个服务的源代码。

### 同一 Windows 服务启动两组房间

两项目使用**不同房间服务器**时，在独立嘴型目录执行：

```bat
start_win.bat 192.168.1.47:8090 192.168.1.48:8090
```

项目 A 订阅第一台的 `reb_sam/reb_tts`，项目 B 订阅第二台的 `reb_sam/reb_tts`。如果两项目使用**同一台房间服务器**，则：

```bat
start_win.bat 192.168.1.47:8090 192.168.1.47:8090
```

第二组自动使用 `/robot/room/reb_sam_b`、`/robot/room/reb_tts_b`，**项目 B 自身必须也发送/订阅这两个 _b 房间**；不要只改嘴型侧。

如果 B 房间名称不是 `_b`，可在启动前设置**完整**环境变量 `TTS_VISEME_SAM_WS_URL_B` 和 `TTS_VISEME_TTS_WS_URL_B`（直接执行无位置参数的 `start_win.bat`），或运行 Python 入口的 `--sam-url-b` / `--tts-url-b` 指定完整 URL。A 的环境变量保持 `TTS_VISEME_SAM_WS_URL`、`TTS_VISEME_TTS_WS_URL`。只提供 B 的一个 URL 或两个项目共享任一 URL，都会在模型加载前报错。

服务向**各自**的 `reb_sam` 发送带 `project_id: "A"` 或 `"B"` 的 `viseme_health`、`mouth_script` 和 `mouth_sync_summary`；外部项目按自己的房间判断心跳，不要汇总两边为一个在线状态。健康消息另含 `aligner_queue_depth`、`aligner_inference_completed`、`aligner_max_wait_ms`（共享模型上的队列/统计量，不能用于推断任一机器人的真实播放 ACK）。两路同时发音总算力需求仍约为两路之和，Windows 上的双路真实延迟和 RTX 4060 负载仍需现场测量。

### 附加房间：同时监听 room / roomv2 / roomv3

默认在 A 的同一台房间服务器上**额外**监听 `roomv2`、`roomv3`：把 A 地址 `/robot/room/reb_sam` 中的房间段替换得到 `/robot/roomv2/reb_sam`、`/robot/roomv2/reb_tts` 等。每个附加房间与 A/B 一样是完全隔离的一组（独立会话、PCM、发包队列、心跳），共享同一个 ForcedAligner 串行推理；哪个房间来了真实 TTS PCM 就为哪个房间出嘴型，`mouth_script` / `viseme_health` 只发回该房间自己的 `reb_sam`，`project_id` 为房间名（如 `roomv2`）。

- 改列表：启动前设置 `TTS_VISEME_EXTRA_ROOMS=roomv2,roomv3,roomv4`，或 Python 入口 `--extra-rooms`；设为空字符串即关闭附加房间。
- `start_win.bat <host:port>` 换主机时，附加房间跟随 A 的主机。
- 同一房间只能有一个嘴型发布者：若主项目本机也启动了自己的嘴型 sidecar 监听同一房间，需关掉其一，否则机器人会收到重复 `mouth_script`。

## 6. 最小验收

依次检查：Windows 出现 ForcedAligner / G2PW ready → `reb_sam`、`reb_tts` 连接 → 收到定期 `viseme_health` → 新项目发一轮真实 `tts` PCM 和 `final` → `reb_sam` 收到匹配 `conversation_id` 的 `mouth_script` / `mouth_sync_summary` → 按播放器已播放样本对齐 → 停 Windows 服务约 5 秒后新项目显示离线 → 重启后恢复在线。最后另验收扬声器和机器人实际嘴型执行回执。

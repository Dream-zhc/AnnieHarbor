# 板端主项目启动脚本

> 2026-10-21。用户要求：给两块机器人板（143 obj 娃娃、188 大头）的麦克风和扬声器程序各做一个 sh 启动脚本，嵌入式把它和机器人主项目绑定，主项目启动时把我们的程序拉起来。

## 做了什么

- 新增 `room-speaker/annie-audio.sh`，两块板都部署在 `/home/sunrise/annie-room-audio/annie-audio.sh`（与仓库同一份）。命令：`start`（默认）/ `stop` / `status` / `log [行数]`。用法、退出码和 Python 调用示例见 [room-speaker/README.md](../../../room-speaker/README.md)“给机器人主项目调用”。
- `start` 先停本程序在本板的旧实例再拉起新实例（与 Brain 启动器“同一旧实例先终止”的规则一致），约 7 秒返回，退出码 0 成功、1 失败（附原因与最近日志）。可重复、并发调用（`flock` 排队），板上始终一份。
- 装了 `annie-room-audio` 服务的板子交给 systemd（`systemctl restart`，保留异常重启和“被接管后保持停止”）；没装服务就 `nohup setsid` 后台运行，日志 `logs/room-audio.log`。root 调用时后台模式仍以目录所有者 `sunrise` 运行。
- 识别“本程序进程”只认：工作目录是脚本所在目录，且前两个参数是 `python speaker.py` 或 `sh start.sh`。命令行里碰巧含这些字的 shell、编辑器、主项目进程都不会被停。
- 两块板接同一 Room 时，后 `start` 的接管、先开的自动退出（原有 `head.py` 机制），所以哪台机器人的主项目启动，哪台就是当前机器人头。开机自启保留不变。

## 两块板的现状（嵌入式需要知道）

| 板子 | 主项目启停 | 音频服务 |
| --- | --- | --- |
| 192.168.1.143 obj 娃娃 | `anni-board-button`（root）按 BCM12 启动键 `Popen` 拉起 `/home/sunrise/1020smallEncoder/anni/app/main.py` | 测试后恢复为停止（10:19 被 188 接管后一直是停止状态），开机自启仍开 |
| 192.168.1.188 大头 | 同上，主项目 `/home/sunrise/0922/anni` | **Jieli USB 麦克风（`USB Composite`）15:56 被拔掉**（内核日志同时有 DOV 重新插入），服务每 8 秒因找不到麦克风重启；14:22 也出现过一次。等用户确认是插回麦克风还是改用 DOV 自带麦克风 |

主项目代码里有自己的 ALSA 采集/播放模块（`modules/voice/audio_capture.py`、`audio_playback.py`）。绑定后若主项目也打开同一块 USB 声卡，后打开的一方会失败，需嵌入式关掉主项目自己的音频。

## 验证（真机）

| 场景 | 结果 |
| --- | --- |
| 143 后台模式（复制目录、测试房间 `roomtest-script`、不参与接管，不影响 roomv2） | sunrise 启动 6 秒返回 0，`status`=0；再次 `start` 停旧起新；两个 `start` 同时调 2 轮都只剩一份；`stop` 后 `status`=3；root 启动后进程属主为 sunrise |
| 143 systemd 模式（真实目录、roomv2） | sunrise `start` 7 秒返回，`已订阅 reb_tts/reb_voice`、麦克风已连接；重复 `start`、root `start`（模拟启停键服务）各换一个新 PID；先手动 `sh start.sh` 起一个前台实例再 `start`，旧实例被停、只剩 systemd 的 MainPID；`stop` 后 inactive，`is-enabled` 仍为 enabled |
| 188 失败路径（麦克风已拔） | `start` 返回 1，输出“启动失败（状态 activating；systemd 会每 5 秒自动重试）”和含 `输入设备“USB Composite”匹配到 0 个` 的日志 |

测试中发现并修掉的两个问题：

1. 最初用 `pgrep -f speaker.py` 找旧实例，会把命令行里带 “speaker.py” 字样的 shell 也算进去——测试时停掉了我自己的 SSH 测试会话（没有碰到其它程序）。改为按工作目录 + 前两个参数精确识别。
2. `flock` 的锁句柄被后台拉起的 python 继承，下一次调用会一直排队。改为 `flock -o`。

另外，后台模式下刚启动 4 秒就被并发的第二个 `start` 停掉时，紧接着重开 USB 麦克风有一次无提示退出（之后 2 轮未复现），后台模式停掉旧实例后先等 1 秒再起。systemd 模式不受影响（失败会自动重启）。

回归：`tests/test_room_head.py` 新增脚本语法、与 `install-service.sh` 同一服务名、`flock -o`、错误命令退出码 2。

### 稳定性改进（都来自 188 今天的真实日志）

| 问题 | 原来 | 现在 |
| --- | --- | --- |
| 启动时声卡不在 | 退出码 1，systemd 每 8 秒重启，每次打印整张设备表（188 当天重启 135 次） | 程序里等待：先把所有声卡找到再统一打开；日志记一次设备表，之后每分钟一行；插好后自动开始，重启次数 0 |
| 运行中 USB 断开 | 麦克风没数据时进程内重开，PortAudio 断言 `PaAlsaStream_Initialize` 崩溃（SIGABRT），停止回执发不出去 | 麦克风 5 秒没数据或扬声器 5 秒没回调：先发 `tts.playback.stopped` / `mic.capture.stopped`（`reason=device_lost`）和机器人头断开，退出码 75，由 systemd 重启后重新枚举声卡；不再进程内重开 |
| 判定掉线后退出慢 | 关闭失效的声卡流卡了 38 秒 | 回执发完直接退出进程，由系统回收声卡 |
| 双板时坏声卡抢房间 | — | 声卡真正出数据（扬声器有回调、麦克风有采样）后才宣布机器人头；等设备期间不连 Room；“启动时间”从设备打开后开始算，所以插回麦克风的板子仍按“后启动”接管 |

### 真机验证（143，USB 授权开关模拟拔插，USB 复位模拟插回）

- 拔麦克风：5 秒后“麦克风没有数据…停止并退出”，退出码 75，立即退出；重启后“等待设备：输入设备“AB13X USB Audio”匹配到 0 个”；插回后 12 秒内自动打开两块声卡、连上 roomv2，之后数据正常，服务重启 1 次。
- 拔扬声器：5 秒后“扬声器 5 秒没有回调…”，同样退出、等待、插回后自动恢复。
- 只读订阅真实 roomv2/reb_voice 6 秒：`robot.head.active` 4 条、`mic.capture.progress` 6 条（`room_connected=true`、峰值 -37.5 dBFS）、`speaker.presence` 3 条。
- 188：缺 Jieli 麦克风，服务在等设备，不刷日志、不重启、不进 Room。
- 注意：只用 USB 授权开关“插回”时 AB13X 会 `Input/output error`（`arecord` 同样失败），程序按“没数据”每 10 秒重启；做一次 USB 复位后正常。这是模拟方式的副作用，真实拔插不经过授权开关。
- 测完 143 恢复为停止（开机自启仍开），188 保持在等麦克风。

# Phase 5 复测前返工：打断、在线嘴型、首响、座舱

## 本轮代码范围

- 真实语音确认后，即使旧 `response.done` 已先完成、旧 `turn_id` 已清空，只要独立 TTS 尚未结束，仍取消旧音频并请求删除跟踪到的未播 Qwen 助手消息项；旧消息无 ID 或服务端删除未确认时不标记“净化完成”。旧生成事件不得抢占新轮。保留真实说出的用户事实，未知播放游标不虚构已说半句。
- ForcedAligner 保留原音素模型与真实 PCM；连续无新音素时基于新增音频递增重试间隔，有成功结果后恢复原频率，既有超长未解析音频预算保护保留；不声称这能消除模型加载和最终对齐峰值。
- TTS 无断句首段达到最少 `first_chars` 时即可排队；保留短句超时兜底、单 Provider task、Room 20ms PCM 及采样时钟流控，避免用删光控速换取虚假低延迟。
- 座舱手动向上滚动停止跟随，增加回到最新入口，顶栏显示当前听/想/说/暂停状态并收窄诊断栏；保留之前并行前端布局/配置修改。

## 未作为已经解决的事项

- Room 接收和监听代码原本就是 1s 起始、最高 15s 的指数退避；没有“固定 0.5s 死循环”的代码证据，本轮未制造另一套重连管理器。
- 360ms 不是所有 TTS 回答都会付出的固定等待，240ms PCM lead 不是首包睡眠；保留有界缓冲并测首可播包与设备确认，不能简单相加报告中的估算数。
- 真人 Room、Mac/Win 物理扬声器与 AEC、服务端 Qwen 删除确认、ForcedAligner 模型耗时和整机压力需现场复测。`tts.playback.drained` 只有真实 speaker 回执才证明完整播出；浏览器试听不能替代。

## 人工复测

同一 Room 只开一路麦克风；对比原 Demo 与当前 Harbor：静置启动、长句连续 20s、回答播到一半插话、“茶→改成咖啡”、误打断恢复、滚动查看旧消息、切换机器人。收集 Room first-publish、真实 speaker start/stop、LLM 首字、TTS first-audio、嘴型 ALIGN/ALIGN_BACKLOG、CPU/内存压力与 P50/P95；无现场数据不得宣布延迟与卡顿达标。

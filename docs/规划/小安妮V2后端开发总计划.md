## 先看这里：业务边界与阶段效果

**用户已确认（2026-09-18，本期固定）：一机器人一独立房间，一房间整套六通道，一路PCM输入。**

```text
机器人A ↔ roomv2 ↔ main / tts / mic / visualdata / vision / sam
                     └─ mic只承载A的一路PCM输入 → A的会话
机器人B ↔ roomv3 ↔ main / tts / mic / visualdata / vision / sam
                     └─ mic只承载B的一路PCM输入 → B的会话
```

- 六个通道是一个机器人所在Room的完整外部接口，不是六个机器人或六个独立业务房间。通道短名对应既有`reb_*`路径；保存原有配置，按阶段启用。
- 一个机器人同时只绑定一个独立Room；一个Room只归属一个机器人；Room的`mic`按一路连续PCM音频流处理，不等于只收一帧。多个机器人靠不同Room隔离，不靠同一房间里猜设备目标。
- **本期不做同房间多机器人、多路PCM混音/说话人分流、广播fan-out或通用设备寻址框架。** roomv2/roomv3是当前示例，不写死只支持两个机器人；每新增机器人仍绑定自己的Room。
- **本阶段未启用 ≠ 配置无用 ≠ 可以删除。** 六通道、已确认的Provider/动作/视觉/嘴型等后续资产必须保留；删除、迁移字段或改变业务含义先问用户。
- 单路PCM是已确认业务前提，不伪装成协议已能检测两个发布者。若现场出现第二音源/房间串流，记录异常并询问部署归属；不自动混流，不新增猜测的source/target字段。

## 1. V2 的真正目标

V2 不以“接入 LangGraph”“模块拆得更多”“Agent 更复杂”为成功标准。

最终目标是把小安妮做成一个适合真实机器人实时交互的陪伴型 Brain：

1. **接得快**：PCM持续送入Realtime，语义轮次结束后尽快产出第一个可播句。
2. **接得住情绪**：低落、委屈、烦躁、开心等场景先承接人的状态，而不是机械分析或马上给建议。
3. **懂连续上下文**：指代、改口、继续刚才、未完成话题、机器人自己的承诺都能正确延续。
4. **记得对的东西**：只在真正相关时使用长期记忆，不以召回数量作为“聪明”的指标。
5. **人格稳定**：每个 Chat 固定 Persona；不同 Persona 的语言、社交距离、幽默和追问方式有稳定差异。
6. **知道什么时候少说**：不是每轮都追问，不把陪伴做成模板化心理咨询。
7. **复杂问题仍然能升级能力**：需要多步骤编排时才进入 Complex Task Path，不拖慢普通陪伴回合。
8. **一个项目并发多个机器人头**：同一个 V2 Runtime 可同时运行多个机器人实例，每个机器人绑定不同的独立Room及其整套六通道；每个头独立处理事件、维护会话并输出语音与动作。

因此 V2 的基本产品公式是：

```text
低延迟
+ 正确上下文
+ SocialState
+ Persona
+ 少而准的长期记忆
+ 合适的模型路由
= 陪伴型“聪明感”
```

## 2. 已确认的范围

### 2.1 输入与模型分工

- **主对话入口：机器人经Room传来的PCM。** Audio Input Gate只做来源/格式/开关/限流与背压，不再串接本地ASR、独立LLM或第二套语义断句模型。
- **Web文本入口保留**，用于调试与产品文本交互，进入同一机器人Realtime Session；旧ASR文本协议仅作为显式兼容/回放输入，不再定义主链。同一段语音不能同时经PCM和ASR文本触发两次回复。
- **Qwen-Audio 3.0 Realtime Flash**（目标模型ID `qwen-audio-3.0-realtime-flash`）负责语音理解/ASR、smart_turn、陪伴对话、Persona和Function Calling；只使用文本输出接后续链。
- **Qwen-Audio-3.0-TTS-Flash**（目标模型ID `qwen-audio-3.0-tts-flash`）独立生成PCM；保留ForcedAligner与viseme映射，不使用Realtime自带语音作为第二路播报。
- 本地ASR/KWS/VAD、Pipecat、额外意图/情绪/规划模型不进入首版；远端smart_turn与边听边说进入本轮目标，但设备回声、打断和播放事实必须单独验收。

### 2.2 切换V1前必须具备

```text
Room PCM与Web文本 → 独立Realtime Session
Audio Input Gate / Event Router / Speak Policy / TurnCoordinator
Robot / Chat / Persona / generation隔离
Conversation Ledger与中断后服务端上下文修正
有界Realtime上下文 / SocialState / LangMem长期记忆
Function Calling动作、表情、简单工具与按需复杂任务入口
Qwen-Audio-3.0-TTS-Flash + ForcedAligner + Room音频/嘴型输出
小脑WebSocket cancel/action与本地ActionArbiter
传感器/视觉/定时/外部事件的有限主动响应
LangGraph结构化结果与暂停/恢复（只为已选定复杂任务接入）
基础Dashboard / Developer / forensic / latency
单进程双头并发与真实设备定向输出/停播验收
```

普通天气查询可作为简单工具，已确认到期提醒可作为事件；复杂提醒编排才进入LangGraph。用户已追加确认：空闲约60秒、有新鲜且稳定的人物存在证据时，可按需运行独立Qwen + LangGraph评估主动交谈；这属于Phase 8后续8C范围，不等于已实现。开放式代理与通用调度平台仍不建设。

## 3. 不可破坏的 External Contract

V2 内部可以重写，但现有外部联调协议原则上不变：

```text
Room WebSocket message type
字段名称与语义
TTS/音频相关房间消息
mouth_script / 嘴型消息
动作 script_id
小脑 cancel/action 协议
视觉/算法输入协议
嵌入式输入/输出协议
已有 timing 语义
```

所有外部协议都必须通过 Adapter 隔离。

禁止业务模块自行拼 Room JSON。

```text
Domain Event
    ↓
RoomProtocolAdapter
    ↓
Existing External Protocol
```

Phase 0已有Golden Fixtures继续锁定已证实的兼容行为。PCM成为主入口是本次明确调整，但不是对未知wire的授权猜测：Phase 2已实测`reb_mic`控制面catalog登记`MIC_AUDIO BinaryFrame`而未登记`mic.start`，因此Gate不得依赖`mic.start`作为网络前置；真实Room测试PCM数据面结果见Phase 2记录，物理麦克风仍待人工验收；归属按独占Room连接，不再为输入索取帧内设备ID。没有wire序号/时间就区分本地计数与接收时间，不冒充远端元数据。沿用TTS/嘴型/动作出口；确需协议变化时单列协商，不改写历史fixture假装已经兼容。

## 4. 总体架构：三条路径，一处发声协调

### Realtime Hot Path

```text
Robot → Room PCM → Audio Input Gate → Qwen-Audio 3.0 Realtime Flash
                                      ├─ ASR / smart_turn
                                      ├─ 对话理解 / Persona / 最终表达
                                      ├─ Function Calling → 本地执行器
                                      │                     ├─ ActionArbiter → 动作/表情
                                      │                     └─ 简单Tool → 结果回写Realtime
                                      └─ Text Stream → 有界可播片段
                                                       ↓
                                          Qwen-Audio-3.0-TTS-Flash
                                                       ↓ PCM
                                              ┌────────┴────────┐
                                              ↓                 ↓
                                             Room      ForcedAligner + 对应文本
                                                                 ↓
                                                          Viseme映射 → Room
```

### Event Path

```text
Sensor / Vision / Timer / External Event
                ↓
           Event Router → WorldState
                ↓
           Speak Policy
          ↙            ↘
   Context Only       Need Response
       ↓                   ↓
有界动态上下文         SpeakRequest
（不触发推理）              ↓
                      TurnCoordinator
                            ↓
                注入事件 → response.create
                            ↓
                    Realtime最终表达
```

压力连续变化只更新状态；摸头可请求响应（去抖/冷却后）；微笑通常只补上下文；提醒到期可请求响应。它们是产品默认策略，不把每帧传感器数据变成会话消息。

### Complex Task Path

```text
Realtime Function Calling / Event Router
                  ↓
       已确认需多步骤的Complex Task
                  ↓
               LangGraph
                  ↓
         Tools / Memory / Workflow
                  ↓
          Structured Result
                  ↓
    SpeakRequest → TurnCoordinator
                  ↓
 conversation.item.create → response.create
                  ↓
      Realtime Persona化最终表达
                  ↓
          同一独立TTS/嘴型出口
```

函数调用结果用关联call_id的工具结果回写；事件结果用带来源的事实注入，二者不冒充用户原话。SpeakRequest是内部数据，不是新增Room wire类型；它可携带工具调用关联，避免重复注入。无须开口的结果只提交状态。

| 组件 | 唯一职责 | 明确不做 |
|---|---|---|
| Realtime | 理解、对话、Persona、语义工具选择、最终表达 | 直接控制设备或决定本地发布资格 |
| LangGraph | 复杂任务事实、状态、工具编排、暂停/恢复 | 普通聊天、最终小安妮式回复、直接TTS |
| Event Router | 来源归一、robot归属与事件分发 | 每个事件都启动Graph或模型 |
| Speak Policy | 价值、时效、冷却与是否值得开口 | 生成自然语言回复 |
| TurnCoordinator | 当前是否可发声、请求仲裁、取消与generation | 重做smart_turn或新增规划模型 |
| TTS / ForcedAligner | 独立音频合成 / 对齐后映射嘴型 | 对话理解或动作决策 |

这些是职责边界，不要求每个框必建新包/服务；热链继续单Python主进程和短异步调用路径。

### 4.1 多机器人头并发（第一版必备）

**这是已确认需求，不是后续扩展项。** 一个 `brainv2/` 项目、一个 Python 主进程必须能够并发运行多个机器人头，不采用“一个头一份项目”的部署方式。机器人头是独立逻辑运行实例，以稳定且唯一的 `robot_id` 标识；每个机器人同时绑定且只绑定一个 `room_id`。`robot_id` 与 `room_id`语义不同，但当前产品配置是一对一绑定。

同一 Runtime 必须支持：

1. 多个机器人头分别连接不同Room，例如`annie-a → roomv2`、`annie-b → roomv3`；各Room使用同一套通道协议。
2. 每个Room内保留完整六条通道：`reb_main / reb_tts / reb_mic / reb_visualdata / reb_vision / reb_sam`，这些通道共同属于该Room对应机器人。
3. `MIC_AUDIO`本身没有已证明的robot/target字段，因此Phase 2输入归属直接由“当前WebSocket连接属于哪个`room_id`”确定；不同Room的PCM不得交叉投递。

最小链路：

```text
Room[room_id]/reb_mic BinaryFrame
        ↓
RoomProtocolAdapter（保持现有外部协议）
        ↓
room_id → robot_id 一对一绑定
        ↓
RobotRuntime[robot_id]（多个实例异步并发）
        ↓
独立 Realtime Session / TurnCoordinator / Ledger / TTS / ActionArbiter
        ↓
该 robot_id 绑定的同一个 Room 六通道
```

**实例配置**放在 V2 的 `config/robots.toml`：每个实例至少声明 `robot_id`、唯一绑定的`room_id`、默认 Persona，以及 `listen_enabled` / `publish_enabled`。`config/rooms.toml`保存Room服务根地址、通道名及已核实的roomv2六条完整URL；其它Room按同一通道结构生成对应URL。

**事件归属与Room边界：**

- Adapter把已建立的Room连接直接绑定到内部`robot_id` / `room_id`；不为MIC_AUDIO增加不存在的wire target字段。
- 本期每个Room只归属一个机器人，房间归属不因关闭listen而变成共享。配置重复绑定应明确报错；现有实现覆盖情况由阶段回归核验，不在规划中标为已实现。每Room只消费一路PCM，不新增多发布者分流协议。
- 小脑cancel、Web文本和后续事件进入Runtime后仍必须带明确机器人上下文，不得取消或污染其它机器人回合。
- 避免自身输出回流成为新输入；Room重连时清除该机器人旧PCM队列和stream状态，重新从新连接首帧开始。

**状态隔离与并发：**

- 每个机器人独立拥有Audio Input Gate、Realtime Session与session_epoch、TurnCoordinator、当前回合与generation、取消令牌、输出队列、按需Task/checkpoint、SocialState、WorldState、Ledger和ActionArbiter；同名 Chat/Persona 不构成共享 runtime 的理由。
- 同一头按现有回合、打断规则协调，不同头使用独立异步任务并发；不使用一个覆盖所有头的全局回合锁。TTS/LLM 阻塞调用不得阻塞整个事件循环。
- Provider 客户端、SQLite 连接管理和无状态 Adapter 可复用，但可变回合状态不可共享。使用实例级有界队列、超时和取消，避免一个头积压拖垮其他头；共享 Provider 限流与 SQLite 写入资源应公平调度并记录等待时间。
- 单机器人失败隔离：某个头断线、TTS/LLM 超时或被取消，不重置其他头的会话与输出；该机器人Room的连接重连只恢复该机器人订阅，不重置其它Room实例。
- 默认每个机器人隔离长期记忆；仅在显式配置共享范围时，允许同一用户的 Global Fact 或同一 Persona Memory 跨头共享，不能把设备状态、短期上下文和关系状态隐式混用。
- Dashboard、Developer、forensic 和 latency trace 都带 `robot_id` / `room_id`，支持选择机器人和查看各实例健康状态。

并发目标沿用单进程、本地 SQLite、原生异步任务的最小实现，不因此新增 Redis、Kafka、复杂事件总线或分布式调度框架。通用连接实现可以复用代码，但不同Room的连接、输入流与状态独立，不建设共享房间fan-out。

## 5. Realtime Hot Path：默认陪伴路径

普通寒暄、情绪倾诉、安慰、连续闲聊、轻量追问与简单事实回复直接由Realtime完成，**正常聊天禁止经过LangGraph**。

- 不等待ASR最终文本再发给另一个LLM；转写用于Ledger、展示与评测，不成为音频主链第二入口。
- 无工具回合只有Realtime响应，不额外串联intent/emotion/planner/memory judge；发生Function Calling时允许必要的工具结果续推理，单独统计，不能用“一次模型调用”约束破坏工具协议。
- 文本增量及时放行；分句具有最大长度和最大等待，不能等完整回复、完整动作JSON或Graph结果再开启TTS。
- 本地状态/队列提交顺序明确，非关键日志/记忆整理异步后置；共享Provider容量按头公平，禁止全局回合锁。
- 目标是尽快说出自然、有上下文的第一反应，而不是每轮长答案。语义转写错误与对话错误分开评分。

测量PCM入口/上送、轮次事件、首文本、首可播段、TTS首PCM、Room发布及设备起播；smart_turn判轮、应用排队和外置TTS时间分别列出，详见第24节。

## 6. Complex Task Path：按需升级

只有需要多步骤、多工具、记忆组合、可暂停/恢复、复杂事件或空闲主动交谈的按需规划时才进入LangGraph。普通动作/表情/单工具不进Graph；问题“很难”不自动等于需要工作流，先证明多步骤状态的必要性。

Realtime通过一个明确的复杂任务工具提交目标与必要参数；Event Router只把命中已实现工作流的事件交给LangGraph。任务异步执行，返回成功/失败/取消、事实、来源与任务状态，不生成最终Persona文案。长任务先回写已受理的结构化状态；后续完成作为带task_id的事件申请发声，不重复完成同一call_id。

复杂任务与主动交谈候选可以按需使用独立Qwen推理模型，但其额度、超时、取消和资源等待与热链隔离。结果回到发起的robot/user/persona/chat/session绑定，不能无条件注入“当前最新Session”；会话切换、结果过期或任务取消后重新评估或丢弃，并保留原因。实际可调用的模型ID须配置并验证，不以口头名称冒充当前已接入能力。

**统一边界：** Runtime的唤醒式调度器决定何时评估、现场条件、冷却和最终发声许可；LangGraph只在唤醒后编排独立Qwen/相关记忆与事实，返回`NO_SPEAK`或带依据的候选话题/结构化意图，不能直接发布音频；Realtime继续负责当前用户的普通交谈与最终Persona表达。用户重新说话时普通热链不等待Graph，尚未发出的主动候选失效。不能把一个Graph挂起一分钟来替代Runtime定时器。

Phase 8仅选择一个真实需要状态编排的工作流证明链路；Phase 11再做复杂任务模型/策略A/B。普通陪伴不因Graph、checkpoint或强模型故障停摆。

## 7. SocialState：陪伴质量核心状态

V2 新增轻量 `SocialState`，但不能新增一个专门情绪 LLM。

建议状态：

```text
user_affect
conversation_mode
relationship_tone
response_need
question_pressure
humor_level
advice_readiness
```

示例：

```text
user_affect = negative
conversation_mode = emotional_support
response_need = empathize_first
question_pressure = low
advice_readiness = false
```

SocialState 来源：

```text
明确规则
最近 Conversation Ledger
Persona 状态
Realtime当前回合可获取的明确状态信号（可选，不强制文本流同时输出复合JSON）
```

禁止为 SocialState 每轮额外调用一个模型。

SocialState 的目的不是给机器人贴心理学标签，而是帮助回答控制：

```text
先接住还是先解决
该不该追问
能不能开玩笑
回复应该多长
是否避免立即建议
```

### SocialState 的更新与纠正

状态允许`unknown`，每条判断带来源和更新回合；用户明确表达/纠正优先于旧状态及模型推断。Chat/Persona切换必须按隔离规则重置；情绪等暂态需要明确的衰减或失效条件，不跨会话默认沿用。迟到的StateDelta须核验turn/generation后提交。

规则只整理明确事实与回复策略，不做关键词驱动的复杂情绪状态机。减少的是无效追问；完成用户目标必需的澄清仍应进行。Phase 3先测更新规则，Phase 4/5再用真实对话评估表达效果。

## 8. LangGraph的新职责边界

```text
LangGraph = 事实 + 状态 + 流程 + 工具编排
Realtime = 理解 + 对话 + Persona + 最终表达
```

LangGraph不再拥有普通回合的hydrate/gather/generate/commit主链，也不负责实时音频或设备发布。Phase 8已以单次提醒的最小StateGraph落地；该流程目前由业务SQLite保存checkpoint，尚非原生AsyncSqliteSaver。后续主动交谈规划复用按需Graph职责，但不能将“异步”误称为已实现主动调度或原生持久恢复；没有候选就不调用独立Qwen或创建Graph任务。

最小任务链按实际业务构建：读取任务状态 → 执行必要Tools/Memory步骤 → 提交结构化结果。结果包含task_id、所属会话、状态、来源与时效；例如业务事实载荷可以是：

```json
{
  "event": "room_temperature_high",
  "temperature": 31.8,
  "severity": "mild",
  "suggestion": "可以提醒用户开空调"
}
```

单个温度阈值本身由普通事件规则处理，无须为了上述例子启动Graph；只有结合多源事实、任务状态或工具编排时才进入复杂路径。结果是Evidence，不是system指令或已执行动作；Realtime可以自然表达为“有点热起来了，要不要把空调开一下？”。

持久化只面向工作流：接入时声明checkpoint写入时机、恢复和失败语义；恢复前核验任务绑定和副作用执行记录，不能重放已发送音频/动作或重复创建提醒。任务副作用有稳定幂等键；进程崩溃后的不确定执行不得当作未执行盲目重试。Graph完成不代表机器人已经说出结果。

Ledger、语音会话和播放回执的提交生命周期独立于Graph；下一轮直接看见用户更正/取消，不等待Graph结束。普通聊天验收以Graph调用数为0为硬门槛。

## 9. Chat / Persona / Memory 隔离

### 9.1 Realtime Session与按需Task隔离

逻辑会话键：

```text
{robot_id}:{persona_id}:{chat_id}
```

每个逻辑会话绑定独立Realtime Session；重连增加session_epoch，并映射Provider session/response/item/call身份与本地turn/generation。当前产品以robot作为身份边界，不另建user_id；切Chat/Persona先取消旧输出并切会话，不沿用旧上下文；同Persona revision更新仅更新会话指令。

复杂工作流thread_id在上述身份上增加task_id，避免同一会话两个任务共用checkpoint；仅在复杂任务启动时创建。

Robot / Chat runtime 严格隔离：

```text
history
pending inquiry
unresolved topic
short-term commitments
SocialState
```

Working Memory 与 Long-term Memory 必须分开：

```text
Realtime Working Memory
  = Realtime会话有界上下文
  + 本地Ledger / SocialState / WorldState相关快照
  + TurnCoordinator运行状态

Complex Task Working State（按需）
  = LangGraph State + AsyncSqliteSaver + task_id隔离checkpoint

Long-term Memory
  = LangMem 负责 extract / update / merge / delete
  + AsyncSqliteStore 负责持久化与查询
  + sqlite-vec 只负责需要语义检索的 namespace
```

Realtime Session不是持久化真源；重连只重建已确认的有界上下文，不能重发旧PCM、旧response.create或旧副作用。Checkpoint不保存完整历史聊天。最近真实对话、`assistant_spoken_text`、cancel/interrupted 等事实继续以 Conversation Ledger 为准；Graph State 只保存当前回合真正需要的有界工作状态。

长期记忆 namespace 必须由 `robot_id` 与显式共享配置决定。默认按机器人隔离；当前产品不另建user_id维度。未来若要跨机器人共享，必须由用户重新确认明确scope，不能隐式共享 Persona 或 episodic memory。

第一版 namespace 采用最小固定结构：

```text
("memory", robot_scope, "semantic")
("memory", robot_scope, "persona", persona_id)
("memory", robot_scope, "persona", persona_id, "episodes")
```

Episodic memory默认随Persona隔离，避免人格专属故事经公共episodes泄漏。确需跨人格复用的客观事实，经显式筛选后进入semantic scope；暂不新增第二套公共经历库。所有读取都采用服务器侧确认的完整scope，不接受模型自行扩大范围。

本期身份边界已确认就是`robot_id`；Room连接和显示姓名不再提升为第二层自然人身份。不同机器人默认不共享Chat、Persona、Ledger或长期记忆；未来若增加多人身份或跨机器人共享，必须作为新业务需求重新确认。

thread_id各身份段使用明确校验或无歧义编码，覆盖分隔符碰撞；namespace检索覆盖前缀相似、大小写和特殊字符，不只测试完全不同的名字。

### 9.2 Global User Memory

保存稳定、可复用的用户事实与偏好。结构化字段优先 exact lookup；只有模糊表达、近义偏好或无法稳定键控的内容才进入 semantic search。

### 9.3 Persona / Episodic Memory

Persona memory 保存：

```text
用户对这个人格的反馈
Persona 专属关系状态
Persona 专属故事
```

Episodic memory 保存过去真正有复用价值的经历摘要，不保存完整逐字聊天。

召回按 scope 分开：

```text
Structured / Global Search
+ Current Persona Search
+ Episodic Search（仅在当前问题需要时）
        ↓
dedupe / rerank / relevance filter
        ↓
Context Packet
```

## 10. Memory 的陪伴原则

Memory 不是召回越多越好。

普通回合：

```text
Recall candidates
    ↓
relevance filter
    ↓
0~4 条进入 Prompt
```

很多普通回合 0 条 Memory 是正常的。

禁止把以下内容长期写进 Long-term Memory Store：

```text
当前槽位
当前 HOLD
最近几轮逐字聊天
临时视觉
机器人当前动作
短时情绪
```

它们分别属于Ledger / Realtime Working State / WorldState / SocialState。

LangMem 只运行在回合结束后的后台记忆整理链，不进入 Companion hot path。已实现的简单记忆查询由Realtime工具或受预算约束的上下文更新直接读Store；复杂记忆组合才进入LangGraph，不在每轮前强制检索；禁止为“要不要记住”在主链额外调用 memory judge LLM。

### 10.1 检索截止时间与前台优先

“后台写记忆”不代表“前台检索无耗时”。结构化键查询优先，按需触发语义检索；query embedding、Store查询、过滤/重排分别计时，并受同一总deadline约束。普通陪伴默认不额外调用LLM重排；不为召回每轮增加模型判定。

Phase 6在开发开始时声明候选数、0–4条入Prompt上限、记忆token预算与检索deadline，先用慢embedding/锁竞争测试验证，再用真实样本校准；数值记录在该阶段验收参数中，不提前新增未使用配置。一般闲聊超时无记忆继续；明确依赖旧记忆的问题应坦诚信息未取到或做必要澄清，不编造。上一轮新事实由近期Ledger/Working State立即提供，不等待后台抽取。

后台候选按会话去抖/合并，队列、并发、重试均有上限；前台LLM/TTS优先，记录后台积压、Provider等待、SQLite争用与deadline命中率。禁止用全局回合锁或新增常驻服务解决尚未证实的性能问题。参见[LangMem后台处理指南](https://langchain-ai.github.io/langmem/guides/delayed_processing/)。

### 10.2 更正、遗忘与来源一致性

- 记忆至少有来源回合、事实/推断类别、有效时间或更新版本；助手虚构表达不得抽取成用户经历，短时情绪不写长期事实。
- 用户更正先在当前Working State生效；后台按来源版本合并，迟到的旧候选不得覆盖新事实。
- 用户删除/遗忘必须先使目标记忆在读取路径失效，再完成Store与向量索引清理；删除标记/版本阻止旧任务及Ledger重新抽取将其复活。
- Phase 6明确遗忘范围：事实、Persona还是用户scope；完整删除请求覆盖相应Ledger/派生记忆/导出与备份保留策略，不把仅删除向量当作彻底遗忘。界面区分已失效、清理完成、失败待处理。
- merge/delete后原记录和索引一致；中断重试幂等，失败可恢复。会话事实和删除请求不用可丢弃Trace队列承载。

### 10.3 依赖接入门槛

Phase 6先在Python 3.11、macOS/Windows验证LangMem + AsyncSqliteStore + sqlite-vec的安装、CRUD、语义查询、并发关闭和删除一致性，再锁入实际依赖；本次仅更新规划，不提前安装依赖。选用包含namespace边界修复的兼容版本，针对项目scope自行回归，不以使用官方Store替代隔离验收。

## 11. Conversation Ledger

Ledger 是下一轮上下文的真实来源之一。

至少记录：

```text
robot_id
room_id
turn_id
persona_id
chat_id
user_text
assistant_planned_text
assistant_generated_text
assistant_published_text
assistant_spoken_text
playback_evidence_status
generation
interrupted
cancelled
cancel_source
timestamps
```

发生small-brain cancel或用户打断后，下一轮必须优先使用实际播出的`assistant_spoken_text`，不能把用户未听到的剩余生成文本当成已发生事实。

独立TTS下，Realtime只知道生成文本，不知道实际播放进度。本地Ledger修正还不够：取消后须将Provider会话中的未播助手内容移除/以确认已播内容重建；若更新不可用或失败，受控重建Session并加载有界已确认上下文。该策略是本项目设计，Phase 4B用真实接口验证；无播放证据保持unknown，不能把完整生成文本留在远端后宣称已修复。记录Provider item到本地可播片段的映射；不套用未经该型号证实的音频truncate字段。

### 已播证据与两级验收

planned、generated、published、confirmed played分开记录。Room publish只证明发布，`assistant_spoken_text`只表示可确认已播放部分；无回执时为空/unknown，估计结果单独标注，不伪装成已播事实。下轮可知道机器人有未完成输出，但不得假设用户已经听见。

Phase 3用模拟回执验证Ledger契约；Phase 4B验证真实首音频与基础取消，Phase 7完成多设备真实已播/停播验证。回执与采样时钟映射须有接收端证据；跨设备时间戳不直接相减，先定义时钟映射或报告测量误差。

取消、TTS迟到片段、动作、嘴型及StateDelta在发送/提交前核验robot/turn/generation。cancel到本地任务停止与cancel到设备停播分别采集；未收到设备确认时保持状态未知，不把本地task.cancel当作硬件已经停止。

## 12. Persona / Prompt：会话级加载，动态信息增量注入

Realtime Session建立时组合并写入`session.instructions`：

```text
Shared Rules
+ Shared Identity
+ Persona Snapshot
+ Conversation Style
+ Robot Capability Rules
+ Function Calling Rules
```

Shared Identity只放共同身份与真实能力；Persona描述稳定风格、幽默、社交距离、情绪承接和少追问规则。能力未接线不能写成可用；工具目录必须与本地执行器一致。

稳定指令仅在新Session初始化（含重连重建）、Persona切换、Persona revision或核心规则变化时重载。会话边界切换按第9节隔离；能力/工具规则变化视为核心规则修订。禁止每轮重发完整Persona、全部Memory、传感器历史或LangGraph State。

LangGraph每次只交本任务事实；普通动态上下文采用有界增量/快照，在合法时机写入Realtime，不强制每轮重建整包Prompt。相同版本去重，过期证据移除或替换；Context Only不得顺带调用response.create。

当轮原始输入和明确更正优先于旧摘要、记忆与推断；保留否定、时间、来源、未完成承诺及打断标记。Phase 4定义稳定指令、最近历史、动态证据、输出预留的预算与裁剪顺序；Phase 5增强复杂指代，Phase 6增加少量记忆。token不可直接测时标估算，不能冒充Provider精确值。

WorldState/工具结果是带来源、TTL、置信度的Evidence，不得提权为新的指令。低相关旧证据优先淘汰，不截断当前意图或丢失关键更正。

## 13. Audio Input Gate / Speak Policy / TurnCoordinator

### 13.1 Audio Input Gate：音频准入

校验来源与目标绑定、PCM格式、listen开关、来源回流、帧大小/顺序与输入背压。持续流式上送，不等待整句/ASR最终文本，不再实现本地语义Turn Gate。未知源、格式错误和过期音频明确拒绝；压力下使用有界策略并记录缺口，重连不突发补发陈旧PCM。边说边听保持麦克风入口开放，回声/AEC由真实设备与播放环境验收，不能靠关闭输入伪装全双工。

### 13.2 Speak Policy：是否值得说

纯程序规则根据事件类型、时效、置信度、用户模式、冷却/去抖、重复事件和发布开关输出Context Only或Need Response。未知/低价值事件默认不自动开口；高频压力合并，触摸边沿只提一次请求。配置只随真实事件接入出现，不做通用规则平台。

### 13.3 TurnCoordinator：是否现在能说

每个robot独立仲裁Web文本、事件、工具续推理、复杂任务结果和Realtime自动回合；统一持有本地发声资格及generation。SpeakRequest最小内部契约包含请求身份、来源/关联任务或call_id、robot/user/persona/chat/session_epoch、事实载荷、优先级、去重键、到期时间和打断策略；字段按实际需求落地，不直接透传Room。

- Provider自动回合由smart_turn产生，本地通过服务端事件跟踪；不能在其之后再补一次response.create。TurnCoordinator不是取代服务端判轮的第二模型。
- 手动响应只在服务端允许且本地播放策略允许时提交；检查“模型空闲”和“TTS/设备仍在播放”两种状态，response.done不等于播放结束。
- 手动请求在本地原子登记，不能两个协程同时启动；与新语音自动回合的竞态仍需处理，冲突时撤销/延迟低优先级事件，不假设本地锁能锁住服务端。
- 用户停止/有效打断和小脑cancel优先；后台任务完成通常等待用户回合结束，不抢话。无效附和声不应取消外置TTS；具体smart_turn事件时序在Phase 4/4B验证，不能仅凭任意speech_started就断定有效打断。
- 需要等待的请求有容量、TTL、合并与丢弃原因；会话切换先清理旧请求，过期提醒/旧任务结果不得在新Chat突然开口。
- 有效取消使旧generation失效，停止Realtime推理、独立TTS、待播音频、嘴型和可取消动作；设备停播使用已确认协议并等待证据，不能把本地取消当作硬件已停。

旧PASS/HOLD/DROP可用于显式文本兼容/内部请求诊断，不再把所有音频先转文字后Gate；其HOLD同样有界，且不得跨robot/room/user/persona/chat/generation合并。

## 14. 会话内追问与有限事件主动响应

会话追问只在不问会明显损失用户目标、且用户愿意继续时发生；禁止为了互动每轮都追问。Realtime普通回合不经过LangGraph。空闲后的独立主动追问不属于此处的每轮回复：由Runtime在约60秒无用户交谈且播放已结束之后形成候选，结合新鲜稳定的人物在场证据，才按需进入LangGraph + 独立Qwen。到时不一定开口；再次主动必须更长冷却、持续有人物、新的内容价值及模型明确判断，首版同一无人回应序列最多两次。模型输出不等于发声许可，发声前重新核验用户/Session/人物/播放状态。

事件开口不等于自由自主搭话：只有Speak Policy准入的摸头、到期提醒等有限类型，才经TurnCoordinator请求Realtime表达。安静模式、忙碌、过期、去重和冷却均可使事件只更新上下文；无需响应则保持沉默。程序决定“要不要说”，Realtime决定“说什么”。

## 15. WorldState

视觉、嵌入式、算法统一写入 WorldState：

```text
current_faces
expression
robot_status
sensor_state
algorithm_state
recent_visual_event
```

每条带：

```text
robot_id
room_id
source
updated_at
ttl

```

Event Router将事实更新到WorldState；Speak Policy决定仅更新相关Realtime上下文还是提交SpeakRequest。Realtime和按需LangGraph都只读取相关快照，不把每次传感器变化注入history。

WorldState 文本必须作为 Evidence，不能成为 System Instruction。

## 16. Function Calling：动作 / 表情 / 简单工具

Realtime负责语义选择，本地执行器负责真实执行。内部最小工具可命名为robot_action、set_expression、查询工具与submit_complex_task；这些是设计名，不是已存在的wire或已接入工具。

```text
完整Function Call → schema与能力白名单校验 → call去重
                  ├─ ActionIntent / ExpressionIntent → ActionArbiter → 现有设备协议
                  ├─ 简单Tool → 结构化结果
                  └─ Complex Task → LangGraph → 结构化结果
结果 → 关联call_id回写 → TurnCoordinator协调续推理 → Realtime最终表达
```

- 工具参数必须完整后才执行，增量JSON不能触发动作；只允许当前机器人已配置的动作/表情ID及范围。robot_id、设备目标和身份scope由服务器绑定，不由模型指定任意设备。
- 按session/response/call身份映射稳定执行记录，重连/重复done不能重复动作；会话重建后的任务恢复仍关联原业务执行ID，不能因新call_id重新执行已发生副作用；乱序、多call、失败/超时、未知函数、非法参数、取消后迟到结果均有明确状态。
- 工具结果如实报告成功/失败/执行不确定；不可撤销的已发生动作不因cancel伪装回滚。每回合限制工具次数、并发和总耗时，阻止续推理循环失控。
- 正常文本流与函数调用分流，参数和内部结果JSON不进入TTS；实际动作状态未确认前，不能依据模型文案记为“已执行”。
- 小脑继续提供低延迟动作和cancel。ActionArbiter只处理冲突、去重、冷却和优先级：`cancel/safety > 小脑即时动作 > Realtime语义动作`，不演变为大状态机。
- 最终文案仍由Realtime生成；LangGraph和工具实现不再返回另一份“小安妮式回复”。

## 17. 独立TTS / ForcedAligner / Viseme

保留目标模型`qwen-audio-3.0-tts-flash`与既有ForcedAligner方向；配置与旧listener存在不等于V2已接入。Realtime使用纯文本输出，唯一播报源是独立TTS，避免双音轨。

```text
Realtime可播文本片段 → 独立TTS → 同一份实际PCM
                                    ├─ Room音频发布
                                    └─ PCM + 对应合成文本 → ForcedAligner
                                                              ↓
                                                       时间对齐结果
                                                              ↓
                                                       Viseme映射 → Room
```

ForcedAligner不是只吃PCM就能直接吐嘴型：输入需对应文本和音频，对齐结果还需映射viseme。分段绑定robot/turn/generation/chunk与采样时钟；对齐分支必要重采样须保留时间映射，不能另合成一份音频做时间基准。

Phase 4B实现最小分段对齐与取消；Phase 9仅观测现有单头嘴型链耗时与异常，不在此阶段重构多头对齐或算法。首音频不等待整轮对齐；嘴型若需短缓冲则显式预算并测量音画偏差，算法慢/失败时按已声明策略禁用迟到嘴型或中性嘴型，不阻塞主聊天、不沿用旧generation。

sidecars/tts_viseme是未多头化的listener副本；须避免它再调用一次TTS，与Runtime争抢合成/发布所有权。SidecarSupervisor只在实际接入时启动和监控；依赖、超时、required标志、失败原因和降级状态进入health与日志，不静默失败。正式设备放行必须有嘴型关联与取消证据。

## 18. SQLite 优先

默认尽量使用 SQLite：

```text
runtime.db          # 本地会话事实与执行记录
langgraph.db        # 仅Phase 8实际工作流checkpoint需要时创建
observability.db    # 观测量确有必要时分库
```

高频 Trace 不能同步逐条写数据库，应：

```text
in-memory queue
  ↓
async batch writer
  ↓
SQLite WAL
```

只有已经通过数据证明 SQLite 无法满足实时要求时，才允许引入 Redis/其他服务。

### 22.6 Phase 4C动效规范：GSAP主库，动效服务操作

**选型：React + TypeScript沿用现有工程，统一采用GSAP作为主动画库，React接入使用`@gsap/react`。** 简单hover/焦点/颜色过渡用CSS；复杂面板转场、列表入场等用GSAP。不是要求同时安装多个动画库，4C实施时才加入必要依赖，不修改正在开发的4B。

**版本基线（2026-09-20核验，尚未安装）：** `gsap@3.15.0` + `@gsap/react@2.1.2`；来源为[npm GSAP版本元数据](https://registry.npmjs.org/gsap/3.15.0)与[npm React接入包元数据](https://registry.npmjs.org/@gsap/react/2.1.2)。接入包声明的peer范围覆盖本项目现有React，但仍须完成类型/构建/浏览器验证。实施时使用精确版本并更新唯一`web/package-lock.json`，不写latest、不顺便升级React/TS/Vite；版本调整须说明兼容依据并重验。

| 场景 | 要达到的效果 | 边界 |
|---|---|---|
| 侧栏、诊断抽屉、页签 | 短距离位移与淡入淡出，切换有连续感 | 默认180–280ms，支持快速反向切换；不等待动画结束才发请求或取消 |
| 会话列表、结果卡片 | 新增项轻量入场、删除后位置平顺变化 | 稳定业务key；只动画变更项，刷新历史不让整列表重播；不擅自改变排序 |
| 按钮与状态反馈 | hover/按下/禁用反馈统一，成功失败标签变化清楚 | 默认120–180ms；颜色同时配文字/图标，停止按钮始终可达 |
| 收音与播放状态 | 收音指示和音量/波形随真实信号变化，有正在工作之感 | 有实际音频幅度才画音量/波形；无幅度数据只显示“收音中”等真实状态，禁止随机跳动假波形；设备已播需真实证据 |
| 消息与实时回复 | 消息容器轻量入场，流式文字及时可读 | 不逐token反复播入场动画、不加假打字延迟；用户查看旧消息时不强制滚回底部 |

以上是交互时长默认值，不是业务响应等待预算；常规单次转场控制在350ms内。目标是有质感、层次明确，不是常驻粒子、全屏炫光、页面晃动或滚动劫持。不额外引入Motion、Anime.js、Lottie、Three.js等第二套动画引擎；确有不同需求再单独说明用途。GSAP插件按真实场景选用，不为了展示库能力开启全套插件。

**React接入和可访问性：** 组件内用`useGSAP`与局部ref scope管理动效；异步/事件中创建动画需纳入`contextSafe`或显式清理，卸载、换机器人/会话时撤销旧动画与监听，防止StrictMode重复执行留下副作用。通过`gsap.matchMedia`尊重`prefers-reduced-motion`；减少动效时取消位移/弹性/循环效果，保持状态可读、全部功能可用。见[GSAP React官方接入](https://gsap.com/resources/React/)与[matchMedia官方文档](https://gsap.com/docs/v3/GSAP/gsap.matchMedia()/)。

**业务与性能：** 优先transform/opacity，避免流式更新反复触发布局测量；不可用动画onComplete决定发请求、删会话、取消或发布音频。状态先真实生效，动画可中断且结束后与最新状态一致；隐藏页/卸载时暂停或清理展示性循环。波形/指标限频或按帧绘制，不每个PCM帧触发全工作台重渲染；绘图取已有采样/统计，不另建第二采集或合成链。

**验收：** 第25节P4C-W6/W7为必验项，覆盖正常/减少动效模式、快速交互、切换/卸载、真实音频并发与性能对照。只加依赖或录一段漂亮动画不算通过；动效不能破坏WEB-01～08和4B语音链。回退时移除本次GSAP接线并保留无动画可用的界面，不回退用户数据或4B实现。

### 24.2 实时主链瀑布

```text
PCM received → input queue → PCM sent
→ speech_started / speech_stopped / turn有效性（服务端可见事件）
→ response.created → first_text_delta → first_speakable_chunk
→ tts_request → first_pcm → room_publish → playback_confirmed
                          ↘ align_request → alignment_ready → viseme_publish
cancel_received → generation_invalidated → local_cancel_done → device_stop_confirmed
```

服务端事件时间不直接与本机时钟相减；同时记录本地单调接收时间及来源时钟/映射误差。缺少明确有效轮次时点就留空，不伪造smart_turn耗时。ASR转写单列，不作为热链LLM请求起点；文本模式单独测输入到首文本。

Realtime服务端完成生成、独立TTS完成、Room已发布、设备已播放是四种状态。首音频、首发布、设备起播/停播分别报告；对齐延迟、音画偏差、输入缺帧/积压、语义误打断/漏打断、无效轮比例单列。

queue_wait/service/end_to_end、Provider容量等待、工具执行/续推理、事件等待、Graph任务耗时、检索/embedding、SQLite/checkpoint成本分别记录。普通无工具、简单工具、复杂任务、主动事件分组，不以复杂任务均值掩盖普通首响。

## 25. 阶段任务卡：按目标实施，不按模块数量推进

### 25.1 所有阶段共同的执行规则

1. **开工先复述，不明先问。** 模型先用人话给出“当前阶段、目标效果、输入→输出、拟改文件、保留项、明确不做、验收方法、未决问题”，再修改。已确认的一Room/六通道/一路PCM不重复询问；业务语义、删配置、换模型/协议、跨阶段扩展及真实硬件行为缺证据时，问用户一个具体问题，说明选项差异；相关改动等答复，能独立验证的既定部分可继续。
2. **先核当前实现，不重复造轮子。** 阶段README记录实际状态，任务卡定义目标。已有实现先回归，不因为文档新增要求就覆盖当前代码；并行任务的未提交修改不是本任务可清理内容。不得为了通过测试修改用户目标。
3. **必须保留项也是验收项。** 每卡都继承“一机器人独占一个Room、六通道全保留、单路PCM、不同Room隔离”及已通过能力。阶段暂不使用的配置仍是已确认资产；只有真正废弃且用户确认的内容才删除，不能援引KISS/YAGNI自行砍功能。
4. **实现按小步验证。** 将本卡“必须实现”逐项转为失败测试→最小实现→回归；本阶段开始才核实精确模块/测试文件和API字段，禁止为未开始阶段预建包、表、服务或占位目录。内部函数命名等不改变业务含义的细节可自主决定。
5. **结果至少分四层。** 单元/fixture、模拟业务、测试PCM经过真实Room、物理麦克风/设备验收分别记录。`WELCOME/ACK`只证明连接订阅；`accepted`只证明音频进入队列；生成/发布/设备起播/设备停播也分开。缺哪个就标哪个待验，不能统称“闭环完成”。
6. **未达标不自动升级阶段。** 缺真实设备时保留该项待验；用户明确同意可先做后续不依赖部分，但不得把前阶段改为完成。4B设备待验允许纯Context开发的既有例外，仍须明确未放行项。未来卡片没有状态记录时按未开始处理，不以文档为完成证据。
7. **规划先写网页验收。** Phase 4起必须按第22.5节与本卡网页用例列清页面入口、操作、预期、证据级别和待问问题；缺网页验收标准的规划不作为完整实施任务卡。
8. **收尾交付固定。** 实现/未实现清单、变更文件、精确命令与结果、人工操作及预期、证据级别、待问事项、临时产物清理结果。更新当前阶段README与入口的状态，不另开平行总计划，不擅自启动下一阶段。

Phase 1–5（含4B/4C）沿用`tests/html/phaseN-*.html`验收页安排，已有`phase1.html`/`phase2.html`可沿用，4B/4C临时页只作验收入口与必要诊断，正式能力仍在第22节React工作台。**Phase 6及以后不新建独立HTML测试/验收页：新增功能及诊断随阶段直接接入现有工作台，在对应功能区完成本卡网页用例；交付工作台入口、操作→预期→实际结果和阶段README证据。** 自动化回归、WEB-01～08、浏览器/设备/人工验收及未通过不自动跨阶段的要求不变。页面复用当前接口与已确认协议，不复制业务逻辑或创建第二套前端；需发送麦克风时明确选中Room，并避免与机器人真实麦克风同时向同一Room发声。既有临时页不提前删除，按Phase 10最终整合安排、用户确认后清理`tests/html/`及挂载，保留长期回归；Phase 11及以后不重建。

### Phase 3 — 管住会话：谁在聊、用什么人格、现在能否回复

**目标与可见效果：** 网页选择A/B、切Chat或Persona，能看到对应会话；模拟回复时执行取消/切换，旧回复不再冒出来，也不影响另一机器人。本阶段展示规则，不展示真实AI能力。

**当前状态：** 自动化实现已落地，人工浏览器验收待确认；实际证据见`docs/phase3/2026-09-18/README.md`。

**输入→处理→输出：** robot/Room绑定 + 网页文本/会话操作 + Fake Provider/播放事件 → Session、Ledger与TurnCoordinator → 可追踪的会话状态、响应许可/等待/取消结果。

**必须实现：**
1. 本期以robot作为身份边界，绑定chat、persona及revision；不另建user_id，也不把room_id或设备名自动当自然人。
2. 每机器人独立session_epoch、turn/generation、队列和取消；切Chat/Persona先停止旧输出并隔离上下文。
3. Ledger记录用户输入、生成/发布/确认已播及unknown；本地更正/取消立即可见，重启不重放旧副作用。
4. TurnCoordinator协调自动回合、网页输入、未来事件/工具的响应请求；Fake测试覆盖模型结束但设备仍播放、重复请求、TTL和并发取消。只落当前必需字段，不提前建真实Provider。

**必须保留：** Phase 2持续PCM接收、六通道配置、默认无密钥回归、机器人隔离；会话名相同不代表可共享状态。

**明确不做：** 不接真实Realtime/TTS/设备动作、不接LangGraph/checkpoint或LangMem；不改变Room归属，不用模拟播放回执声称设备已播放。

| 操作 | 必须观察到的结果 |
|---|---|
| A/B使用相同Chat/Persona名称提交输入 | 两份记录、队列和取消仍独立 |
| A回复中切换Chat或Persona，随后旧结果到达 | 旧结果被丢弃，B继续工作 |
| 同时模拟事件请求和用户输入 | 不重复起响应；需等待的请求有原因、容量和TTL |
| 模拟部分播放后取消、再重启 | 已播/未播/unknown区分正确，不补播旧剩余文字 |

**已确认无需再问：** robot就是本期身份边界；默认Persona来自机器人配置；切Chat/Persona不删旧历史；SQLite完整历史保留到显式删除；Realtime只取当前Chat最近20轮有效对话。除非用户另行提出多人身份或共享需求，不得自行增加user_id、人脸/声纹身份识别。

### Phase 4B — 真正说出来：独立TTS、基础嘴型与打断

**目标与可见效果：** 对机器人说话，它能用既定音色回答并动嘴；有效打断使旧语音/嘴型停止，下一轮不假装说过用户没听见的内容。这是首个真实语音体验里程碑。

**必须实现：**

4. 有效取消覆盖Realtime、TTS、待播PCM、嘴型和generation；区分response.done、合成完成、发布、设备播放完成。
5. 用Ledger实际播放证据修正远端未播上下文；无回执保持unknown。边说边听验证回声与误打断，不关麦伪装全双工。

**目标与可见效果：** 可信绑定的同一用户换Chat后仍可召回已确认偏好；用户能更正和要求忘记；另一个机器人不会默认继承这些记忆。

**输入→处理→输出：** 有来源的Ledger事实 → 后台记忆候选/合并/删除 → 按robot/user/persona scope保存 → 有截止时间的按需检索 → 少量Evidence交给Realtime。

**必须实现：**
1. 默认按robot、可信用户与Persona scope隔离；匿名不并入具名用户，Global指明确用户scope，不等于全机器人全局。

3. LangMem后台整理有界、去抖和前台资源优先；简单查询不经Graph，不每轮先跑memory judge。
4. 更正先前台生效，后台按来源版本合并；遗忘先使读取失效，再清Store/向量，迟到旧候选不得复活。
5. 真正需要复杂记忆组合时只留清楚输入契约，待Phase 8已确认任务接入，不提前造工作流。

**必须保留：** 短期会话与Ledger事实、用户更正/删除记录、既有语音性能；默认跨机器人隔离不因“同用户”自动放开。

**明确不做：** 不保存全部逐字音频/对话为长期记忆，不写入助手虚构经历/瞬时情绪；不接旧记忆双写兼容层或提前加记忆平台。

### Phase 7 — 真正执行：动作、表情、简单工具与小脑协同

**目标与可见效果：** 对A说“挥挥手”，在已确认动作目录中有此能力时A真实执行；A的表情和语音对应，B保持不动；执行失败不会被说成成功。

### Phase 8 — 该说才说：外部事件与按需复杂工作流

**目标与可见效果：** 摸头可得到自然回应；压力连续变化或看到微笑不刷屏。明确的语音/文字提醒必须建立真实任务而非口头承诺；用户选定的工作流可暂停/恢复。后续8C在有人的空闲场景中按需思考是否主动说话，不机械定时催问；最终仍由Realtime以小安妮风格表达。

**当前状态：** 8A 事件策略与 8B 网页单次提醒工作流软件链路已实现；2026-09-23 修补Realtime创建提醒工具，但真实用户语音→任务→到期物理播放尚待统一验收，不能把模型口头答应当作任务创建。8C主动规划已接入默认关闭的可选首版，真视觉与真实模型/音频/隐私验收仍待完成，详情见Phase 8阶段README。Phase 8不能据软件测试标记整体PASS。

**开始条件：** Phase 3协调、Phase 7执行链通过；先问清事件开口规则与首个真实复杂任务，未选任务前不建通用Graph。

**输入→处理→输出：** 所属Room传感器/视觉/定时事件 → Event Router/WorldState → Speak Policy → Context Only或SpeakRequest；明确提醒请求 → Realtime Function Calling → LangGraph/SQLite真实任务 → 到期后TurnCoordinator → Realtime → 既有TTS。8C新增Runtime空闲候选 → 新鲜人物证据 → 按需LangGraph+独立Qwen → 结构化NO_SPEAK/候选 → 发声前复核 → Realtime。

**必须实现：**
1. 保留8A简单事件、8B提醒工作流，新增8C异步主动规划子项，均属于Phase 8，不另起通用Agent；8A不依赖Graph。

4. Speak Policy判断值不值得说，TurnCoordinator判断什么时候能说；事件重复、过期、用户正在说话时等待/丢弃有原因。

6. 8C由Runtime管理约60秒空闲候选、人物存在新鲜度与稳定性、冷却、机器人/Chat/Persona/session_epoch隔离、说话/播放中的取消；LangGraph按需调用独立Qwen判断不说/说什么/第二次是否值得说。首次候选不必开口；二次要求更长冷却、人物持续在场、不同于上一句的内容价值和模型明确许可；首版最多两次，用户未回应不自动连环催问。

### Phase 9 — 性能与诊断完善（暂不做双头嘴型）

**目标与可见效果：** 在现有React工作台选择机器人和一轮对话，即可定位「麦克风没进来、ASR没结束、模型慢、TTS排队、Room发布慢、设备未回执」哪一步造成延迟；长时间运行后能判断排队、内存、CPU或重连是否退化，不用重启碰运气。

**开始条件：** 8C的软件回归收束，真实音频验收缺口单独列出；复用Phase 2–8的typed trace、Ledger和现有Developer，不复制状态机。

**输入→处理→输出：** Room PCM、Realtime、TTS、Room输出、设备回执及进程资源统计 → 有界事件和分轮耗时归因 → 统一诊断API/工作台、可复跑性能报告与故障定位结论。

**必须实现：**
1. **按轮端到端时延：** 展示PCM接收/排队、speech_started、ASR final、LLM请求与首文本、TTS排队/首PCM、Room首帧发布、speaker started/drained/stop等已知事件；时间线带`robot_id/turn_id/generation`和数据来源。跨机器时钟不得直接相减，无数据用`unknown`，不补假平均数；同进程耗时用单调时钟。
2. **P50/P95与失败样本：** 按Robot、交互类型、最近固定窗口聚合样本量、成功/取消/超时/无效轮；对各段及端到端分别报P50/P95、排队等待、缺回执数量。失效或不完整回合不能被静默剔出整体失败率；小样本只给样本数，不以均值承诺稳定性。
3. **拥塞与运行时：** 有界低频采样队列深度/丢帧/背压、Realtime和TTS重连/超时、SQLite写队列与错误、Trace丢弃；采集CPU、RSS内存和事件循环滞后并给出进程级来源。不得将写死的CPU/健康分、Demo数据或猜测的语音能量标为实时。
4. **诊断闭环：** 对选中turn关联实际下发的指令快照、历史注入预算、记忆召回、FC工具/动作、事件抑制、TTS/嘴型耗时和设备回执；网页/日志/JSON统一口径。每个断点给出时间、证据、故障或不可测原因，不自造另一个Web前端或追踪服务。
5. **低开销和生命周期：** 高频PCM不上报到React State，低频批量/有界Trace；用户关闭工作台不影响Runtime。测量新埋点前后P50/P95、资源增长与取消延迟，观测不得反向拖慢热链。

**必须保留：** 现有单头ForcedAligner与viseme发布、独立TTS、机器人独立Room和六通道、长期SQLite事实以及所有Phase 8事件/提醒/空闲策略。多个机器人仍须隔离诊断数据，但不因此追加双路声学模型并发调优。

**明确不做：** 不做双头嘴型、旧listener多实例化、嘴型算法精度专项、设备协议重构、第二套TTS或新业务；不把浏览器试听当真机起播。尚无可信设备时只能报告Room发布和回执缺失。负载生成、Fake Provider、故障注入及性能比较脚本只能放`tests/`；正式Runtime仅保留有界必要采样和业务诊断。待全部阶段结束且用户确认清理，可删除一次性压力脚本和临时测试代码，不影响正式程序。

## 27. 验收标准

### Architecture

```text
V2 可独立搬走运行
V2 不 import V1
core 无 LangGraph/Pipecat/provider SDK
第三方 SDK 被 Adapter 隔离
普通聊天LangGraph调用数 = 0
Realtime纯文本 → 独立TTS；无双音轨
简单动作/表情/工具 = Function Calling + 本地校验
Context Only不触发推理；手动响应全部经过TurnCoordinator
复杂任务只交结构化结果，Realtime统一最终表达
```

### Companion Experience

必须建立固定测试集并长期回归：

```text
上下文连续性
情绪承接
是否先理解再建议
无效追问
回复自然度
Persona 一致性
不想说时是否收住
改口是否立即生效
```

目标是同一Realtime模型下上下文/记忆等改动带来可复现改善；与V1比较须明确模型和输入链不同。评测按以下规则实施：

- Phase 4将现有11类设计样例扩成固定多轮脚本，增加否定/改口/打断/长历史/承诺与反例；记录模型版本、采样参数、Persona、历史/记忆快照及原始回答。Phase 5补复杂上下文，Phase 6补记忆，分别比较无/有该能力的增益。
- 机器硬契约（隔离、已播证据、过期输出、删除一致性）在固定回归集必须100%通过；语义质量不以精确字符串匹配代替评分。
- 人工按明确量表匿名A/B，分别统计上下文正确率、情绪承接、必要/无效追问、自然度和Persona一致性；报告胜/平/负、样本数与分歧处理。模型裁判仅辅助，不作为唯一依据。
- Phase 4先建立实测起点，不提前宣称明显优于V1；Phase 5/6冻结本阶段质量门槛后验证增益，已通过核心样例不得无解释退化。Phase 10须确认收益不是以明显首响退化换取。
- 质量集与逐回合结果可复跑；测试参数/预期属于测试资产，不新增评测常驻平台。

### Isolation

```text
Chat history 泄漏 = 0
Persona runtime 泄漏 = 0
Persona memory 跨人格泄漏 = 0
Robot runtime / Realtime Session / SpeakRequest / generation / task checkpoint / Ledger 串线 = 0
默认长期记忆跨机器人隐式共享 = 0
```

### Multi-Robot Concurrency

```text
同一项目、同一 Python 主进程至少并发两个机器人头
每个机器人绑定唯一 room_id；roomv2/roomv3 等不同Room PCM只进入各自实例
每个Room保留main/tts/mic/visualdata/vision/sam完整通道集合
每Room只有一路PCM输入；本期无同房间多机器人/多音源分流
同 user/persona/chat_id、不同 robot_id：状态完全隔离
音频/嘴型/动作/cancel：接收端目标可验证，无串设备
cancel/超时/积压/停止 A：B 仍正常接收、响应与输出
重连不重发旧PCM/动作，自身音频输出不回流触发新Realtime回合
Dashboard/Developer 按机器人查看健康、事件与 P50/P95
```

### V1 Freeze

原版冻结基线及当前已有修改被保留；V2 任务仅在 `brainv2/` 写入，复用逻辑先复制再独立改造，不回写或运行时依赖 V1。

### Protocol

已确认的External Contract fixtures须由真实Adapter的自动化测试100%通过；另做fixture数据形状/来源/预期校验，禁止只解析JSON就宣称合同通过。模拟样例、真实wire及设备联调结果分列；必需但未获证据的协议项保留待验并阻止对应能力切换。

### Performance

必须按第24节同时记录P50/P95、样本数和失败率，包含排队及Provider等待；Developer展示与原始trace一致。真实设备起播/停播和本地音频/取消分列；缺少播放证据不得宣称端到端设备体验达标。

### Startup

```text
macOS ./start.sh
Windows start.bat
```

Sidecar/Provider 启动失败必须明确显示，不允许“看起来启动成功但某模块其实没起来”。

## 29. 主要风险

### 风险 1：V2 架构更漂亮，但陪伴体验没提升

解决：沿用Phase 0设计样例，Phase 4开始Realtime同模型消融；V1/V2另列产品体验差异。

### 风险 2：为了“情商”堆超长 Persona Prompt

解决：情绪/关系/回复需要进入 SocialState；Persona 只描述稳定表达差异。

### 风险 3：Memory 召回让回答更乱

解决：0 条 Memory 允许且常见；Relevant Memory 才进入 Context Packet。

### 风险 4：复杂任务拖慢普通聊天

解决：Realtime默认短链，LangGraph按需旁路；复杂任务资源限额，结果经协调后再表达。

### 风险 5：把服务端smart_turn误当成设备全双工已完成

解决：单独验回声、无效附和、有效打断、外置TTS清队列及嘴型停播；不复制第二套本地断句模型。

### 风险 6：Realtime上下文与实际播放分离

解决：Ledger记录实际证据，取消后同步修正Provider上下文；无回执保留unknown，不把生成当已说。

### 风险 7：自动回合、事件、工具续推理争抢

解决：TurnCoordinator跟踪服务端及本地播放双状态，手动请求有界、去重、过期；联合真实接口验证，不只测本地锁。

## 33. 工程原则硬约束

本计划所有阶段都受 `brainv2/PROJECT_RULES.md` 约束。以下原则优先级高于“架构完整度”和“未来扩展性”：

- **拒绝过度设计与无脑堆砌**：遵循 KISS、YAGNI 与奥卡姆剃刀，“如无必要，勿增实体”。实现目标是用最精简的代码和最清晰的链路稳定达成功能。
- **坚决克制抽象**：严禁为了所谓扩展性提前编写大量空心抽象层、冗余包装类和纯转发胶水代码。若原生逻辑已经清楚可靠，不得为了“统一形式”再包一层。
- **单进程轻量闭环优先**：默认单 Python 主进程、本地 SQLite、一键启动。没有明确证据前，不引入 Redis、Kafka、Docker 常驻服务或独立数据库服务。
- **外部依赖必须可解释**：现有 LLM/TTS Provider、小脑、视觉/嵌入式 WebSocket 与必要 sidecar 可以保留，但任何新增外部依赖都必须证明不可替代，并具备清晰日志、健康检查与失败降级行为。
- **实时主链最短化**：普通陪伴由Realtime直接响应，不经过LangGraph或额外LLM；工具调用允许必要续推理并单列成本；日志、长期记忆整理、非关键持久化和观测写入尽量异步后置。
- **原版冻结，V2 独立迁移**：原版从 2026-09-17 起默认不改，只读参考或复制逻辑到 `brainv2/` 后改造；不回写原版、不覆盖已有修改、不依赖原版运行。
- **多机器人并发是已确认基础能力**：单项目单进程运行多个机器人头；每个机器人绑定唯一Room并保留该Room六条通道，PCM输入按`room_id → robot_id`隔离；状态与取消按`robot_id`隔离，不能以后续扩展为由推迟。
- **先证明问题，再增加复杂度**：没有真实失败样本、性能数据或明确业务需求，不增加新的 Graph Node、状态机、路由器、缓存或服务。

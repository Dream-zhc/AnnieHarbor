# Phase 5｜启动卡顿与音频热链性能排查

## 现场证据与归因边界

2026-09-21 检查当前 macOS 本机进程与 127.0.0.1:8780/health；没有停止或重启正在运行的 Runtime，也没有向现场 Room 发布音频。

| 证据 | 结论边界 |
| --- | --- |
| Mac 内存 16 GiB，检查时已用 swap 约 6.55 GiB，浏览器 Renderer、WindowServer 等其他应用也在消耗资源 | 属于全机压力，不能把既有 swap 全部归因于 V2，未在现场运行的 V1 不算实测对照。 |
| V2 的 Runtime 和一套 roomv2 ForcedAligner 侧车运行中 | 此刻没有证据支持“两套侧车同时运行导致卡顿”；默认只启动首台机器人侧车。 |
| TTS 20ms 一个 Room PCM 帧，原先每帧又向 Realtime SSE 发布进度事件 | 持续说话会将 50Hz 音频时钟错误地转成约 50Hz 的 React 座舱渲染驱动。 |
| Sidecar 日志有一轮对齐 328320 样本（约 13.68 秒），耗时 3859.5ms，事件数 0，默认在线间隔 120ms | 对不断增长、尚未解析的长 PCM 反复运行 MLX 是明确热链负载。 |
| Sidecar 日志累计超过 16000 条逐帧 TTS_RX | 每 20ms 同步日志写盘放大负载并掩盖关键事件。 |

## 本轮最小修复

- Room PCM 不降帧，每 20ms 真实数据仍发布到 reb_tts；仅用于工作台的 tts.pcm_published 改为首帧和每 25 帧一次。首音频、首 Room 发布、停止和扬声器回执仍即时报告。
- 未解析 PCM 超过默认 3600ms 后，暂停反复在线 ForcedAligner 计算并只记录一次 ALIGN_BACKLOG；完整 PCM 和累计文本保留至 final 再尝试一次完整对齐。不捏造嘴型时间，不改变 turn_id/sample cursor/text 契约。可用 TTS_VISEME_MAX_UNRESOLVED_MS 调整。
- 仅在设置 TTS_VISEME_TRACE_PCM=1 时打开逐帧 TTS_RX 日志；重要 ALIGN、控制和故障日志照常记录。
- 保留两机器人 Room 与默认一套嘴型侧车，不以关闭功能掩盖性能问题。

**质量限制：**3600ms 在线灾难保护可能使长句尾段嘴型延迟或缺失。该保护不是完整的高性能嘴型算法；需先实测文本/PCM 对齐，再重构可验证的有限滑窗，不能提前标“嘴型 PASS”。

## 回归与现场验收

本轮自动化：Python 139 passed / 25 subtests；Sidecar 预算专项 2 passed；Ruff/diff check 通过。Mock 验证 51 帧 Room PCM 原样发布，仅第 1、25、50 帧发 UI 进度；假模型验证长未解析 PCM 不反复计算，短音频照常在线调用，final 仍可对齐。

检查时运行中的进程**尚未重启到本轮代码**，因此并无重启后 CPU/swap 降幅、真人嘴型、真实长句听感或 V1 同负载对照数据，不能宣称卡顿已彻底解决。

复核：先安全停止当前麦克风/TTS 再通过项目启动器替换 Runtime；分别测工作台静置 60 秒、耳机开麦 60 秒、连续回答 20 秒，记录 Runtime/侧车/浏览器 Renderer CPU、内存压力、ALIGN_BACKLOG、ALIGN compute、播放器 underflow、真实嘴型及 swap 趋势。关闭网页后 Runtime 仍应独立处理 Room。

# 对话动作、短句与嘴型同步（2026-10-22 晚）

用户反馈（看 10-22 日志）：对话里让她做动作有时不动；“向左看、向右看”这类能直接触发嵌入式脚本的短句容易被决策模型忽略；TTS 音素（嘴型）比声音晚很多，基本没有嘴型；唤醒后全双工在线时间偏短。实测中用户补充：嵌入式动作只认 `type=action_trigger`，坏笑发的是 `action_prepare`，所以不动。

```text
本次问题与范围：上面四个问题，只做最小修复；不改 Realtime/TTS/对齐模型，不做双头嘴型。
目标与用户可见效果：点名的动作和五个表情都会真的动；跟进窗口里不喊名字的动作短句直接执行；嘴型像旧项目一样提前于声音到达；回复后免唤醒多听 10 秒。
输入 → 处理 → 输出：用户话 → 动作规则/决策模型 → reb_main action_trigger；TTS PCM → reb_tts（最多提前 3 秒、合并成最大 800 ms 的包）→ tts_viseme 对齐 → reb_sam mouth_script。
拟改文件：actions.py、realtime.py、speech.py、__main__.py、annie_adapters/tts.py、decision_policy.py、config/runtime_defaults.toml、.env.example、web 嘴型卡片说明及测试。tts_viseme 不改（同一服务在旧项目上实时）。
保留项：动作白名单机制、一轮一个动作、撤销/幂等、动作回执、决策模型判断旁人对话、30 秒窗口上限校验。
不做事项：不实现嵌入式按字执行；不换模型；不改嵌入式和板端扬声器。
未决问题：现场 .env 是否自定义了 ANNIE_ACTION_ALLOWLIST。
结果：软件回归通过；真机待验（见文末）。
```

## 1. 对话里的动作不动

### 证据（docs/运行日志/2026-10-22）

| 轮次 | 用户 | 小安妮 | 动作记录 | 原因 |
| --- | --- | --- | --- | --- |
| 627/629/632/637/638/639 | 向左看、向右看、点点头… | 好嘞，看我的～ | `action_trigger` → `device_finished` | 正常 |
| 643 | （…）的表情 | 坏笑… | `smirk` → `published_unknown`，无设备回执 | 五个表情走 `action_prepare`，嵌入式不认 |
| 647 | 小安妮摇摇头。 | 摇头？行，这就给你摇一个。 | 无 | `shake_head` 不在默认白名单，提示词却说会摇头 |
| 628 | 小安妮，你看看上面有什么东西？ | … | 无 | `look_up` 不在默认白名单 |
| 644 | 小安妮做一个惊。 | 惊讶？行，给你来个夸张版的！ | 无 | 识别把“惊讶”截成“惊”，规则只认“惊讶/吃惊/震惊” |
| 646 | 你做一个疑惑的表情。 | 疑惑？眉头一皱… | 无 | “疑惑”没有对应说法 |
| 641 | 小安妮向右看。 | 好嘞，看我的～ | `look_right` → `send_unknown ConnectionClosedError` | reb_main 连接空闲时已被 Room 关掉，发送才发现 |

历史上 `shake_head` 一次也没执行过（10-20～10-22 全部动作记录）。

### 修改

- **表情改发 `action_trigger`**（`actions.py`）：带 `anchor_text` 的动作不再发 `action_prepare`，改发和普通动作一模一样的 `action_trigger`（`script_id`、`offset_ms=0`、`conversation_id`、`anchor_source`）。发送时机：回复里已经出现目标词，并且本轮第一帧 PCM 已发出（不再在开口前就发）。设备回执照旧按 `conversation_id + script_id` 匹配。代价：表情只能“随回复开口”，不能落在某个具体字上；按字执行要等嵌入式支持 `action_prepare`（见 [字级动作协议](../../规范/字级动作与嘴型同步协议.md) 顶部说明）。
- **默认白名单补上 `shake_head`、`look_up`**（`__main__.py` 的 `DEFAULT_ACTION_ALLOWLIST`，`.env.example` 同步）：对话里能点名的动作（点头、摇头、看左/右/上、眨眼和五个表情）都在默认白名单里。**现场 `.env` 若自己设了 `ANNIE_ACTION_ALLOWLIST`，需要手动加上这两个 ID。**
- **说法补充**（`decision_policy.py`）：句末单独的“惊”算惊讶（只在“做个/做一个/来个/表情”这类请求里）；“疑惑/困惑”算怀疑表情；“眨眨双眼”算眨眼。“我有点疑惑”“做一个惊悚的故事”“别摇头了”不算。
- **提示词只列能做的动作**（`realtime.py`）：【实体动作】改为“你能做的动作和表情只有：附和小点头、摇头、看左边…”，从白名单和动作目录生成；要求做不在里面的（如悲伤、跳舞）直说做不了，不假装在做。
- **Room 连接断了先重连**（`annie_adapters/tts.py`）：发送前发现 WebSocket 已不是 OPEN（Room 关了空闲连接），先关掉重连再发；连接正常时行为不变，发送中途失败仍不重试（避免重复执行）。

## 2. 短句动作被决策模型忽略

### 证据

- 15:17:32 “摇摇头”：smart_turn 判无效 → 回收 → qwen-flash 判 `not_robot`（置信 1.0），整句被当成旁人说话丢掉。
- 用户现场说“带上名字、向左看向右看它直接就忽略”：跟进窗口里不带名字的话一律先问决策模型；动作短句没有上下文，最容易被判成旁人在描述动作。

### 修改

- `realtime.py` 新增 `_motion_command`：话里点名了**已启用**的动作（同一套 `explicit_motion` 规则），就和喊名字一样跳过“说给谁听”的判断，直接回复并执行。两条路径都覆盖：正常终稿（`_addressee_check_needed`）和 smart_turn 判无效后回收（`_hold_dropped_call`）。没启用实体动作时不跳过。

## 3. 嘴型比声音晚

### 证据

- 嘴型由独立 tts_viseme 从 reb_tts 收同一份 PCM，ForcedAligner 要拿到一个字之后约 0.3–0.5 秒的 PCM 才能定下这个字的边界；它的发送节奏器以第一条嘴型发出的时刻为原点，后面每个字按与第一个字的间隔放行，**第一个字提前多少（或晚多少），整句都保持这个量**。
- 用户对照旧项目日志（同一嘴型服务能实时）：旧主脑把 TTS 音频一到就推到 reb_tts（首包就含 800 ms 音频，10.31 秒的回复 2.1 秒推完），首个嘴型在首包后 172 ms 就算出，比“好”字（400 ms 处）早 228 ms，之后每个字都提前约 220 ms 到达，42 字零丢。
- 小安妮只比播放提前 0.24 秒推 PCM，几乎按实时节拍发。10-22 上午 34 轮（旧内置嘴型服务，算法与 Windows 版相同）：首个嘴型在首包 PCM 后 286–2485 ms 才发出（中位 558 ms），第一个字本身在 0–560 ms（中位 320 ms）；发出时刻减去该字位置中位 255 ms，**19/34 轮第一个嘴型已经晚于它的声音**，节奏器再把这份迟到带到整句。
- 两项目另一处差别：旧主脑在 reb_sam 发 `llm_delta` 提前给嘴型服务文本做多音字 G2P；小安妮不发，嘴型服务改用 pypinyin 即时注音，只影响多音字准确度，不影响时延。

### 第二个原因（真机复测后，Windows 嘴型服务日志）

只加大提前量后，用户复测仍然“音素时间差很多”：工作台“上一轮”41 字、34 个口型全部收到，但**平均延迟 7746 ms、最大 9889 ms**。对照同一 Windows 服务的日志：

| | 小安妮 conv 0cc3caeb | 旧项目 conv 059eccfd |
| --- | --- | --- |
| 音频 | 8.39 秒 | 3.33 秒 |
| reb_tts 消息 | 约 420 条，每条 960 字节（20 ms） | 8 条，50～800 ms 不等（provider 原始分块） |
| ForcedAligner 次数 | 约 66 次在线对齐，每次 140～380 ms | 6 次，每次 250～440 ms |
| 对齐总耗时 | 约 13 秒，比音频还长 | 约 2 秒 |

tts_viseme 在收 reb_tts 的线程里**每来一条消息、只要新音频满 120 ms 就同步跑一次对齐**。小安妮把 PCM 切成 20 ms 一包，于是每 120 ms 音频就要算一次（Windows 上每次 140～380 ms），算得比播得慢，一句话越往后越晚，积压到 7～10 秒；旧项目直接转发 provider 的大块音频，每块只算一次，所以跟得上。这个差别与提前量无关：提前量再大，20 ms 一包照样要算这么多次。

### 修改

- **合并 reb_tts 包**（`speech.py`）：发布时把队列里已经排在后面的 20 ms 帧一起合成一包发出，最大 800 ms（旧项目最大分块）。首帧照样立即发出、不为凑包等待；provider 一次给出的大块自然成为一包，提前量顶满后稳定为约 800 ms 一包。对齐次数从每秒约 8 次降到 1～3 次。扬声器、回声消除、网页测试扬声器都按 `start_sample/end_sample` 拼接，不受包大小影响；默认关闭的混合模式后续句也同样合并。
- **PCM 提前量 0.24 秒 → 3 秒**（`speech.py` 的 `PCM_LEAD_SECONDS`），与旧主脑一样提前推送，让嘴型服务先拿到音频。上限 3 秒而不是不设限：云端 AEC 只保留最新 PCM 往前 15 秒参考，长回复（讲故事）不设限会把未播的参考挤掉；扬声器和网页测试扬声器都是 30 秒缓冲。开口时延不变；打断时多丢弃最多 3 秒未播音频。
- **工作台嘴型卡片说明**：原文“TTS 会提前约 240 ms 发出”改为“TTS 最多提前 3 秒发出，嘴型是否赶上声音看‘来晚’条数”。卡片里的“延迟”是相对 TTS 包**发出**时刻，提前量变大后它本来就会变大，判断是否跟上要看“来晚”（嘴型到达时设备已播过该字）。
- **tts_viseme 不改**：同一服务正给旧项目提供实时嘴型；曾考虑改它的发送节奏器，会让旧项目的嘴型从提前约 220 ms 变成几乎不提前，已撤回。Windows 服务无需更新。
- 旧项目也有的局限：首字太靠前（前导静音很短）时，整句嘴型仍可能略晚，这是嘴型服务算法现状，不在本次范围。
- 未做：小安妮不发 `llm_delta`（旧项目发，用于提前做多音字 G2P），只影响多音字准确度，不影响时延。

## 4. 唤醒后全双工在线时间

逻辑（`presence.py`，配置 `config/runtime_defaults.toml` 的 `[duplex]`）：

1. 本地唤醒词命中 → `WAKE_WAIT`，5 秒内开口（`wake_wait_ms`）。
2. 说的话被接受 → `ACTIVE`，她说话期间不计时。
3. **扬声器真正播完**（设备回执 drained）→ `FOLLOWUP`，免唤醒继续听 `followup_ms`；这期间开口就暂停计时，说完再给 10 秒等识别终稿。
4. 决策模型判为旁人交谈时窗口从此刻重新计时，但从窗口打开起最多 120 秒（`side_talk_listen_ms`）。smart_turn 判无效的声音、“嗯/对”不续时。
5. 窗口到期 → `SLEEP`，要重新喊“小安妮”。

日志：15:10–15:21 这轮里，回复后 25、28、51、54 秒又重新唤醒，用户也说动作时得“强制加上名字”。改为 **`followup_ms` 20 秒 → 30 秒**（现有校验上限）。若还嫌短，可再放宽，但窗口越长越容易接到旁人对话或电视声，需先确认上限再改校验。
